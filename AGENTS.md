# nullpad

A markdown note editor that feels like a terminal, built with Foldkit. Read [`FOLDKIT.md`](./FOLDKIT.md) before writing Foldkit code. Foldkit owns that file and replaces it on upgrade, so this file holds everything specific to nullpad.

`FOLDKIT.md` reads the line below to decide whether to offer to vendor the Foldkit source. Leave it in place.

subtree_prompted: false

## Layout

- `src/core/` is the pure core: domain logic such as the buffer, the parser and vim. It runs without a browser.
- `src/` outside `core/` is the shell: Model, Message, update, view and the runtime boot in `entry.ts`.
- New behavior goes in the core first. The shell routes messages to it.

## Colours

Every colour in `src/styles.css` is a `light-dark()` token on `:root` or `.doc`. The finder's backdrop is the one `light-dark()` written in place. `color-scheme: light dark` makes light the default and follows the system to dark. `index.html` declares the scheme and the theme colour before the stylesheet loads.

The cursor swaps two colours: the background under it becomes `--cur` and a letter under it becomes the background colour. `#caret` holds three layers that each blend with the page: `.cur-flip` (`difference`), `.cur-lift` (`plus-lighter`) and `.cur-cap` (`darken`). With a white flip, a channel `x` becomes `255 - x`, the lift adds `--cur` plus the background less 255, and the cap holds the result at the background colour. So `--cur-lift` is `--cur` plus `--bg` less white, and it changes with either. The dark theme flips with `--cur` alone and its lift and cap add nothing. No layer may sit in a stacking context of the cursor's own, or it would blend with the cursor and not the page.

## Editor

The editor types like a browser text box because the browser makes the decisions a text box makes. The core owns the text, the caret and which lines are drawn. The browser owns typed text, IME composition, line wrap, caret steps, hit testing and scrolling.

- `src/keyboard.ts` puts an EditContext on `#port`, the app's one focusable element, and turns every key, text, IME and paste event into an `Input`. The EditContext holds the caret's line, up to 1,000 UTF-16 units each side of the caret (`Frame.surrounding`, carried on the port's attributes), so an IME can convert letters already typed. A range an IME replaces becomes an `Erase` counted from the caret, so a copy a frame behind still erases the right letters. Chrome's EditContext ends a composition that goes empty, and one that an IME commits with no text ends without a `compositionend`, so a `textupdate` that leaves the composition empty ends it with an empty `Commit`. Without that, every key after such a commit arrived as a `Preedit`: NORMAL ignored it and plain typing never committed it. `update` passes the `Input` to `Editor.feed` in `src/core/editor.ts`. Only this file knows about EditContext; a fallback for browsers without one slots in here.
- Backspace deletes the whole letter (grapheme cluster) before the caret, as an EditContext does, where a textarea deletes one code point of an accent, a conjunct or a jamo. `fromKeyDown` takes Backspace in `keydown`, which keeps it in order with the other keys, and `backspaceTarget` in `src/core/buffer.ts` finds the letter with `Intl.Segmenter`.
- A key that needs layout (Left, Right, Delete, Home, End, Up, Down, Page Up, Page Down) or a click makes the core return a `Need` that holds a `Query` and queue every input after it. `src/surface.ts` answers it once the DOM shows the core's `revision`, with `Selection.modify` and `caretPositionFromPoint` on the drawn lines, and `CompletedLocate` lands the answer and replays the queue. The core never reads layout and the shell never moves the caret from a stale frame. A click is held as a line, client x and pixels below the line's top, so no scroll before its answer moves it off the line it was made on. The line is the one under the pointer in the frame on screen when the pointer went down. A scroll the app makes for a key or a click is on screen once the frame after it begins, so a click whose `timeStamp` is older than that is read without the scroll, however late Chrome hands it over. A wheel turn is the user's own scroll and a click is level with it. A click below the last line is the end of the text. The core keeps the line the shell has yet to read drawn: it draws a clicked line that has left the drawn lines, and it leaves out a scroll report that would undraw the line a key or a click is asking about.
- A `Need` is a question the core cannot answer alone: `Locate`, a `Query` for the layout (a caret step, a click's point, or `Screen`, the letters on screen, for vim's jump), or `ReadClipboard`, for vim's `"+p`. The editor has at most one out, held in `locating` with the input that caused it and the inputs queued behind it. Asking changes nothing else. The cause is planned again when its answer lands, so a put from the clipboard cannot run without an answer. Every `Need` carries a `ticket` from `Editor.asked`, which only counts up and outlives `reopen`. `CompletedLocate` and `CompletedReadClipboard` echo it, and `Editor.located` and `Editor.clipboardRead` ignore an answer whose ticket is not the one out. Without it an answer to one note's question landed on the next note's: in the core an old answer to End, taken for a Delete in a note opened meanwhile, erased five letters. `locating` clears only when its answer lands and in `reopen`, so every question gets an answer: `src/clipboard.ts` answers a read with `None` when the browser refuses or 3 seconds pass (no limit while Chrome asks for permission). An `Outcome` also carries `writeClipboard`, the text a `"+y` copied, and `update` runs a `WriteClipboard` Command for it.
- `src/surface.ts` draws the lines of `Editor.paint`: one `.line` per text line, wrapped by CSS, each piece between joins its own text node, one spacer row per undrawn line above and below, all in one `.sheet`, and a `#caret` overlay beside the sheet, placed from a Range rect after each patch. `.surface` scrolls natively and reports its first line and its height in rows. It scrolls a wheel turn itself, on the main thread, and only onto drawn lines: when the turn lands past them, the screen stays put until the patch that draws that place scrolls there. Chrome's own wheel scroll runs ahead of the drawn lines and paints blank screen. Chrome hands a wheel turn to the page at the next frame, after keys pressed later than it, so a turn whose `timeStamp` is not after the key that last aimed (`Model.aimedAt`, drawn as `data-aimed-at`) is dropped: the key came after it. `ReceivedInput.at` carries each key's `timeStamp`, the keydown's for the text it types, since `textupdate` is made when the page handles the key. `adopt` sets `aimedAt` to the latest `ReceivedInput.at` or `ClickedText.at` whenever the outcome moved the target's serial. A turn that is still pending when an aim is applied and lands past the drawn lines asks the core again with the new serial, since the report it made before carried the old one.
- Every scroll the app owes is data in `Editor.target`: `Aim`s, oldest first, at most 16, each a `Serial` and a `Place`. A `Place` is `At`, with an `Anchor` (a line's id, a column and whether the caret is drawn at the end of its row) and an `Align`, `Nearest` or `Top`, or `End`. Each outcome that reveals the caret appends an aim for the caret where it is then (`aimAtCaret`), and so do `resized` and `reopen`, so keys that land in one frame scroll as when typed one by one: Page Down and then Down is the caret's row at the top and then a row that is already in view. An aim whose place is absolute (`Top`, `End`) drops the aims before it, since they cannot change where it puts the screen. An aim names its line by id, so an edit to other lines does not move it, and an aim whose line is gone is skipped. `Serial` is a branded Int that only counts up and outlives `reopen`, as the ticket does. `Frame.target` is drawn on `.surface` as `data-target`, and the observer that already watches each patch (`applyTarget`) applies every aim newer than the last one it applied, in order, then reports once. `locate` applies them first, so an answer is read from a screen that has scrolled for every key before it. `scrollSurface` is the only writer of `.surface`'s scroll: the aims, the release of a thumb at the end and a wheel turn all go through it, and it says whether the app or the person scrolled. `bringOnScreen` is the one place a span is brought into view, by an `Align`. `ScrolledSurface` carries a `Scroll`: the first line, `atEnd` and the serial of the last aim the surface had applied when it measured. `Editor.scrolled` drops a report older than the newest aim, since Chrome fires a scroll event a frame late and such a report put the screen back where an earlier key had left it. An accepted report sets `Editor.applied` and changes nothing that is drawn, so it makes no patch; the next aim drops the aims at or below `applied`. `reopen` sets `applied` to the old target's serial and aims at the new caret, so aims and reports of the note it replaces are dropped.
- `.surface` shows a native scrollbar and has no padding. `.sheet` holds the padding and is at least as tall as the surface, so its children cover the whole text area, and a press whose target is `.surface` itself, while the note overflows, is on the scrollbar (`isOnScrollbar` in `src/surface.ts`). The scrollbar scrolls the surface as any scrollbar does. A press on it makes no click, so the cursor stays, and `keyboard.ts` does not commit an IME composition for it, as a textarea keeps composing. The press still keeps the keyboard on `#port`. A press in the reserved scrollbar lane of a note that fits the screen is a click on the text.
- During a thumb drag each patch draws wrapped lines above the screen in place of one-row spacer rows, and scroll anchoring would pull `scrollTop` back by the extra height, about 100,000 px over one drag through 3,000 lines of 3 rows. Chrome's next pointer move puts the thumb back under the pointer, but a pull after the last move stays, so a thumb dragged to the bottom stopped short of the end in 7 to 18 of 20 drags. So `.surface` scrolls without anchoring while the browser holds a press on the surface itself, which is its scrollbar (`.surface:active:not(:has(:active))` in `src/styles.css`). The browser ends `:active` with the press, on a release in or out of the window and at the first pointer move with no button, and anchoring comes back without moving the screen. While the thumb is held a patch can move the text under the screen, and the screen still shows drawn lines.
- The scroll height would also change under a held thumb, because a drawn line is as tall as its rows and an undrawn one is estimated at one row. Chrome places the thumb from the scroll height, so a drag to the bottom stopped short: at line 417 of a 450-line note where every fourth line wraps, in 3 of 3 drags. So a press on the scrollbar writes the sheet's height to `--held-sheet-height` on the root element (`holdThumb` in `src/surface.ts`), and while the browser holds the press `.sheet` keeps that height and clips what is past it. The thumb then stays under the pointer. At the held end the last lines can be past the clip, so when a press that ended at the held end is let go (`releaseThumb`, on `pointerup` or `pointercancel`), the surface scrolls to the real end. A thumb let go short of the end stays on the line it showed, and the thumb then moves to that line's place in the real height.
- A native scroll can land on the end of the note while the lines there are undrawn. Drawn, a wrapped line is taller than the one row it was estimated at, and after the patch the screen is no longer at the end. So `ScrolledSurface` carries `atEnd`, and when a report at the end changes the editor, the core appends an `End` aim, which scrolls to the end after the patch. Its scroll reports again, and once the drawn lines reach the end the report changes nothing. A wheel turn reports `atEnd` false, since it reads its pending turn again after the patch. A thumb flicked to the bottom in three pointer moves, on 2,700 one-row lines and then 300 of 3 rows, showed the last line in 20 of 20 flicks with this rule and 0 of 20 without it.
- A fast thumb drag through a huge note can show blank frames. Chrome scrolls the drag on its compositor, ahead of the patch that draws the lines there, as it does on a plain page of 120,000 lines, and the lines fill in once the thumb slows. This is accepted, as in the read view. Only a scrollbar the app draws itself could stop it.
- The test rig shows scrollbars: `playwright.config.ts` and the launches in `e2e/drive.ts` and `e2e/mcp.ts` (`launchOptions` in `e2e/steps.ts`) drop Playwright's default `--hide-scrollbars`. A hidden scrollbar takes no mouse input, so a scrollbar scenario in a rig that hides them tests nothing.
- A Ctrl or Meta chord whose key is not in `browserChords` becomes a `Chord`, and `keyboard.ts` cancels its keydown, so Ctrl-Z, Ctrl-Shift-Z and Ctrl-Y never reach the browser. Ctrl-R is in `browserChords`, so it reloads the page, except while the port's `data-chords` reads `vim` (vim on, from `Editor.isVimOn`): then Ctrl-R with no other modifier is a `Chord` and its keydown is cancelled. Ctrl-Shift-R, Cmd-R and F5 always reload. With Caps Lock on, Chrome reports Ctrl-R as the key `R` and Ctrl-V as `V` with no Shift, so `isControlAlone`, the one place that asks for Ctrl and a letter alone, reads the letter in either case and takes Shift from the modifier. The core reads a `Chord`'s letter in either case too. Headless Chromium does not reload on Ctrl-R, so a test reads whether the keydown was cancelled.
- A new key binding goes in `plainKeys` in `src/core/editor.ts`, a Ctrl or Meta chord with vim off in `plainChords`, or a row in `normal` in `src/core/vim/keymap.ts` for vim's Normal mode.
- `script()` in `src/core/input.ts` and `Editor.dump` run the editor without a browser for keys that need no layout, and print the drawn lines as text. Bundle a file that calls them with `pnpm dlx rolldown@1.2.19 <file>.ts --platform node -o <file>.mjs`, then run it with `node`.

## Notes and finder

- `src/core/notes.ts` holds the `Note` record, its title and the folder helpers. A folder is a note's path prefix and exists while a note is in it. A folder path drops empty, `.` and `..` segments. `src/core/fuzzy.ts` scores titles and paths fzf-style over graphemes. `src/core/finder.ts` is the finder's state, fed the same `Input`s as the editor.
- While the finder is open, `update` sends every `Input` to `Finder.feed` instead of `Editor.feed`, and the port's EditContext holds the finder prompt (`Finder.surrounding`), so `keyboard.ts` stays the one keyboard. The port's `data-control` and `data-selection` name the elements whose rects `keyboard.ts` hands the EditContext, so an IME window sits at the prompt. Ctrl-P opens it. Chrome keeps Ctrl-N for a new window, so that chord never reaches the page.
- `src/storage.ts` keeps one IndexedDB record per note in database `nullpad`, store `notes`. The `NoteStore` service holds the connection and the BroadcastChannel `nullpad-notes`, which carries every save and removal to the other tabs, and offers list, read, write and remove with an expected revision, and the stream of changes. `entry.ts` passes its Layer as the runtime's `resources`, so Flags, Commands and Subscriptions share one connection and the runtime closes it at teardown. Boot reads every note through the `flags` Effect before the first render and opens the one edited last. When IndexedDB cannot open or a write fails, the status line says notes are not being saved and the editor keeps working.
- A text change starts an 800 ms wait. A save goes out when no change came after it, at once on a switch of notes, and when the page hides. Saves of the open note go out one at a time, each expecting the revision the last one confirmed. A change from another tab that arrives while a save is out waits until it settles. A change from another tab that keeps the text this tab last saved, such as a move, takes its folder and revision under this tab's unsaved edits. Whenever the store moved to other text under text this tab has not saved, this tab's text goes into a conflict copy. A note that goes blank is removed from the store at its save moment and leaves the list, and typing again saves it anew.
- A note whose text is over 500,000,000 UTF-16 units is not saved (`Editor.isSavable`). V8 holds at most 536,870,888 units in one string, so joining such a note's lines throws. The save, the conflict copy and the draft at `pagehide` leave it out, the status line says notes are not being saved, and the editor keeps working. No one key makes such a note, since a put, a paste or a replay adds at most 4,000,000 units or one copy of its text, but nothing bounds the note itself: about 125 full puts reach it. A yank or delete of that whole note still joins its text and throws.
- Effect's runMain stops the app at `pagehide`, and an unloading page does not finish IndexedDB work. So `entry.ts` listens to `pagehide` before the runtime starts and writes the open note's unsaved text, and the text of notes left mid-save, to localStorage through Effect's `KeyValueStore` as `nullpad-draft:<tab>:<id>`, with the revision it was based on. Boot takes every draft. A draft whose note is still at that revision, or at the one its own save in flight made, reopens and saves. A blank one removes its note. Any other becomes a conflict copy.
- The finder draws at most 60 rows around the selection, ranks only the last matches while the query grows, and caches each text's graphemes and bonuses, so a keystroke over 2,000 notes stays near one frame.

## Read view

Ctrl-E, or the `read ^E` button at the end of the status line, swaps the editor for the note drawn as markdown. Ctrl-E or Esc swaps it back, with the cursor and the editor's scroll where they were. The status line's mode says READ.

- `src/core/reading.ts` turns `Markdown.parse` of the buffer's lines into a `Page`, a flat array of units in note order. A unit is one element the view draws: a paragraph, a heading, a rule, one line of a code or HTML block, or an item or quote with nothing else in it. Each unit holds its first source line, the first line of the outermost block it opens (a code fence, a bare `>` or `-` line, a definition before it in a quote), the holders around it outermost first (a quote, a list, an item, a code or HTML block, each keyed by where it starts). `Page.starts` holds the estimated top of each unit in pixels. A definition and a blank line make no unit. A soft break and a hard break are one `Break` inline, drawn as a `br`, so each typed line of a paragraph or heading starts its own visual line in the same element, where the HTML pane keeps the line feed CommonMark writes for a soft break. A code span or raw inline HTML that spans lines holds no break and draws on one line. An image drawn as its alt text draws its description's inlines, as a link drawn as its text does, so its breaks stay. Raw HTML stays text. A link whose destination starts with `javascript:`, `vbscript:`, `file:` or `data:`, read as a browser reads it (tabs and line feeds removed, control characters and spaces trimmed from the ends, any case), is drawn as its text. An image is drawn only from `http:`, `https:` or a `data:image/` gif, png, jpeg or webp, and otherwise as its alt text. `page` keeps its result for each lines array, so a text is parsed once.
- A list item whose first paragraph's source starts with `[ ]`, `[x]` or `[X]` and then a space or tab is a task. `readItem` reads the mark from the source line at the paragraph's start, because the inline pass splits `[ ]` into three texts and reads `[x]` as a link when the note defines `x`. The unit of its first paragraph carries the `Box` (the buffer line, the column of `[`, and whether it is checked) and loses the mark. The view draws the box as an empty `span` with `role=checkbox`, `aria-checked` and an `aria-label` of the task's text (`Reading.label`), never an `input`. In a bullet list CSS draws the square and its tick in the list indent, in place of the bullet, so the item's text and its nested blocks line up with the other items. In an ordered list the number stays and the box sits after it, in the text's first line.
- A click on a box is the one edit the read view makes. `ClickedTask` carries the box as drawn, and `update` takes it only while the screen is `Read`. `Reading.click` returns `Flip` when the note's page still holds that box in that state, and `Ignore` otherwise, so a second click from a stale frame does nothing. `Reading.flip` calls `Editor.overwrite` and keeps the old page, with that one box flipped, as the page of the new lines, so a click does not parse the note again. The flip changes one character of a mark that a space or tab follows, and no block or inline rule reads `[ ]`, `[x]` and `[X]` there differently. `Editor.overwrite` writes the one character with `Buffer.overwrite`, which keeps the line's length, its id and its joins, so the caret and a queued locate stay valid. The change saves as typing does, and the read view stays where it was.
- `act` in the core decides what an `Input` does in the read view. Esc and Ctrl-E close it, Ctrl-P opens the finder, Up, Down, Page Up, Page Down, Ctrl-Home and Ctrl-End scroll, and every other input does nothing. A new key goes in its `keys` table.
- The Model's `screen` is `Edit`, `Opening` or `Read`. Ctrl-E pressed while the editor waits for a layout or clipboard answer moves to `Opening`, which holds every input after it until the answer lands. `update` runs `finishOpening` after every message, so whichever message clears `locating` opens the read view. The keys before Ctrl-E reach the editor and the keys after it reach the read view.
- The Model's `Read` holds the index of the unit at the top. `Reading.drawn` takes the units within 125 units (or a screen, if that is more) of it and groups them back into their holders, so the view draws real `blockquote`, `ul`, `ol`, `li` and `pre` elements around only the drawn units. An `ol` starts at the number of its first drawn item, and an item or code block cut by the window's top draws no marker or info line.
- `src/reading.ts` draws the drawn units in `.read`, the scroll container, between two spacers, each as tall as the estimated pixels of the units it stands for. `Reading.metrics` holds every number that sets a height or a text width in the read view (the 680 px measure, the 16.5 px body size on a 27 px line, the gaps, each heading level's size, line, margins and rule, the code panel's padding, the indents, the quote's rule, the task box, and a code span's size and padding in ems), and `src/reading.ts` sets them as `--read-*` custom properties on `.doc`, so `styles.css` takes them from the core and repeats none. A code span has `line-height: 1`, so its own font does not grow the 27 px line. `pageOf` adds each unit's height to the space after it: the margins CSS collapses between it and the next unit (the largest bottom margin of the unit and the holders it closes, or top margin of the holders the next one opens), and a code panel's padding and border where a panel starts or ends. After the last unit that space is its bottom margin and those of the holders it closes. The first drawn unit draws its own top margins, and a code panel cut by the window's top draws its top edge, so the spacer above is that much shorter than the estimated top. An empty list item is one 27 px line, because its marker draws one. A unit's text height is its lines times its line height. A `br` starts a new line box, so `segmentsOf` cuts the unit's text at each break, across the edges of emphasis, strong and links, and its lines are the sum over the segments of each segment's width in ems over the column's width in ems, rounded up and at least one. In a width an ASCII letter counts as one of three widths of Inter (`glyphEms`), a code span as JetBrains Mono at its size with its padding, an East Asian wide grapheme or an emoji as 1 em, an image as a whole line, and a box in an ordered task as the indent past its inset, on the first segment only. Headings and `strong` scale the width (`widthScales`). Measured in headless Chromium as the advance of each printable ASCII character in Inter at 16.5 px, the class means are narrow 0.30 em, usual 0.56 em (0.58 over the letters of English words) and broad 0.72 em. Weight 650 draws English words 1.02 times as wide, and a heading's weight and tracking 0.99 times. `glyphEms` and `widthScales` sit at these or above them, because a line breaks before a word and leaves its end empty. To refit them, wheel a long mixed note from top to end at 1280x720, sum each drawn unit's top-to-next-top advance, and compare the sums with `Page.starts`: the estimate should stay a little over, never under. The column is the measure less each holder's indent. A spacer is taller than its units where a run of spaces collapses or letters draw narrower than their class, and shorter where a line breaks early before a long word, an image is taller than a line, a code block wider than the column shows its scrollbar, or the window is narrower than the measure. Every unit but a rule is at least `metrics.row` (22 px) tall, so `screenRows` units fill the screen. Each unit carries `data-unit`, its index, and `data-source-line`, the gutter's number for its first line.
- Only `.doc` draws in Inter (`@fontsource-variable/inter`, bundled, normal and italic); the editor, the status line and the finder keep JetBrains Mono. `entry.ts` loads Inter at boot, so the first open lays out in it.
- `.read` reports the unit at its top as it scrolls, or, when its top is inside a spacer, the spacer and the pixels past its top. The core takes the unit at that height and pins it to the top once it is drawn. When the screen would reach the estimated end it draws the last unit and scrolls to the end of the note, so a fling past the end shows the note's last line in one turn, even when the last unit is taller than the screen. A landing on the first unit scrolls to the top, as Ctrl-Home does. Chrome's scroll anchoring holds the place as units come and go above. Chrome skips anchoring at `scrollTop` 0, so the port's observer also remembers the top unit and its offset and puts it back after each patch. A scroll the app makes fires a `scroll` event on `.read` at once, since Chrome fires its own at the next frame, so the observer remembers the new place before the next patch.
- Opening the read view scrolls the unit that holds the cursor's line to the top: in a list the cursor's item, in a code block the cursor's line. On the first unit it scrolls to the top, as Ctrl-Home does, so a heading there keeps its top margin. It is the last unit whose first block line is at or before the cursor's line, so a cursor on a code fence or on a bare `>` or `-` line opens at the block that line starts. A cursor on a later typed line of a paragraph or heading, a lazy line included, opens at that line: `Reveal.Unit` carries how many breaks of the unit come before it (`revealLine`, at most the unit's breaks), and the shell scrolls the line after that `br` to the top. It reads the drawn `br`, not the estimate, so the line lands at the top at any window width, or as near as the end of the note lets it. Opening another note from the finder returns to the editor.
- The editor's `.surface` stays mounted, hidden under the read view in one `.stage`. A reveal the editor owes when the read view opens, such as Ctrl-End and Ctrl-E pressed in one frame, scrolls the hidden surface, and closing uncovers the surface as it is. `screenView` builds the stage in one return: Foldkit's Vite plugin stamps each function's return with its own identity, and the differ replaces a node whose identity changed, so a stage returned from two `Screen.match` arms would make a new `.surface` on every switch.
- While the read view is open the port's `data-control` names `.read`. Text typed there still reaches the EditContext and is thrown away, so `keyboard.ts` sets the EditContext's text again whenever `data-control` changes.
- On a 9,000-line note of headings, paragraphs of several typed lines, tasks, lists, quotes and code blocks (5,009 units), the estimated total is 0.3% over the drawn one, no unit's estimated top is under its drawn top, and the most it is over is 756 px (0.37% and 891 px on another 9,000-line note of 4,880 units), where the 22 px row estimate it replaced was 6.8% short. On notes of only headings, only code lines or only one-word items the estimate is exact. Opening the read view on that note takes about 250 ms to the next frame in headless Chromium and draws about 350 elements, and about 30 ms on the same text again. A 20,000-item task list opens at the cursor's item in about 580 ms with about 850 elements, where drawing the whole list took 1.4 s and 60,000 elements on the same machine. `Markdown.parse` is most of a first open. A click on a box of a 10,000-item task list takes 33 to 51 ms to the next frame, where parsing the note again took 610 to 1,000 ms.

## Vim

Vim is off until a person turns it on with Ctrl-, or the `vim off` button at the end of the status line (`.status .toggle-vim`, which then reads `vim on`). Turning it on lands in Normal mode, turning it off returns to plain typing. The setting is the localStorage key `nullpad-setting:vim` (`on` or `off`), written through Effect's `KeyValueStore` and read by the `flags` Effect at boot, so a reload keeps it and `openFresh` clears it. Other open tabs keep their mode until they reload. A change to the open note from another tab, a conflict copy and a removal re-show the note in the mode it had (pending keys drop), and a toggle still queued behind a layout answer lands with it. Opening another note from the finder starts in Normal.

- `src/core/vim.ts` is vim's public surface: the `Vim` state (`mode`, which is `Normal`, `Insert` with the stay's `recording` and, for a stay a block began, its `block` (see Block), or `Visual` (see Visual mode), the pending keys of `Keymap.Pending` (`outerCount`, `register`, `count`, `keys` and `innerCount`), `want`, the screen column `j` and `k` keep, and `last`, what `gv` brings back), `press`, which takes an `Input` and `Kept` (the registers, what dot repeats and the last find) and returns the new state, the new buffer, the new `Kept` and the input's fate, `again`, which does the same for one step of a replay, `putClipboard`, which runs a put with the clipboard's answer, and `rest`, the Normal clamp. The parts live under `src/core/vim/`: `cells.ts` cuts a line into cells (graphemes within the pieces between joins, as Backspace does), gives each a kind for word motions and a screen width (2 for an East Asian wide character or an emoji, a tab to the next multiple of 8, which is where `.line` draws it with `tab-size: 8`), `motions.ts` holds the motions and Vim's own cursor steps (`inc`, `dec`, `incl`, `decl`) with the two word walks an operator uses, pure over the buffer, `objects.ts` holds the text objects, `seek.ts` holds the find motions and `found`, the scan of one line, `targets.ts` turns a motion, a text object or a find's landing into a `Range`, `selection.ts` holds what a VISUAL selection covers, `operators.ts` applies a `Range` and puts, and `keymap.ts` holds the binding table and `advance`, which turns the pending keys and one more key into Run, Wait or Drop. Only `vim.ts` and those files import them, and vim imports nothing of the editor: it returns a buffer that `editor.ts` commits.
- `Editor.vim` is `Option<Vim>`, and `None` is vim off. With vim off, and in Insert for every input but Esc and Ctrl-[, `inputPlan` runs the plain path untouched, so Insert types exactly as the editor does with vim off and the typist's comparisons still hold.
- No Normal key but `s` asks the layout (see Jump). `j` and `k` move by numbered line, and from a tab they keep the tab's last screen column, as Vim does. Arrows, Home, End, Ctrl-Home and Delete are rows of the table (`h j k l 0 $ gg x`), so a count works on them. Home differs from `0` in one thing: it keeps the first column for `j` and `k`, where `0` on a tab keeps the tab's last column, as in Vim (`FirstColumn`). `j` on the last line, `k` on the first and a counted `$` on the last line fail and leave the cursor (`motionFails`), as in Vim, and that `$` still sends the next `j` or `k` to the line end. `h`, `l`, Space and Backspace that cannot move keep the column `j` and `k` keep. Ctrl-End goes to the last letter of the last line. Space and Backspace step a letter and cross to the next or previous line at a line's edge, as Vim's default `whichwrap=b,s` does. Page Up and Page Down take the plain path. A paste inserts its text before the cursor's letter and stays in Normal. Enter and Tab do nothing.
- A count is grammar, not a row: a digit is a count when no key is pending, and an inner count right after an operator key (`2d3w`), and `0` only after another digit of the same count. Each is capped at 7 digits, and the two multiply. A key that matches no row drops the pending keys with it, so `d.` does nothing.
- A register is grammar too. `"` with no key pending starts a prefix and the next key names the register: a letter, `"`, `0`, `_`, `+` or `*`. Any other key drops the pending keys. `Pending.register` holds the prefix as typed, `"` while the name is awaited and then `"a`. A count typed before the prefix moves to `outerCount`, and the three counts multiply. A second prefix replaces the first: `2"a3"b1x` deletes 6 letters into `"b`. After an operator key `"` matches no row, so `d"` drops at once and the key after it runs on its own, as in Vim. `Run` carries the register as a `RegisterName`: `Default` (no prefix), `Unnamed`, `Yank`, `Letter` (with `appends` for a capital), `BlackHole` or `Clipboard`.
- `d c y` are operators. Their rows are generated in `keymap.ts`: each operator key before every motion row, before itself (`dd cc yy`, target `Lines`) and before every text object, so `next(['d'])` lists what can follow `d`. `x X S D C Y` and Delete are rows over the same `Operate` command (`dl dh cc d$ c$ yy`). `s` is the jump (see Jump), so `cl` is the way to change one letter. `p` and `P` are `Put` rows. `Run` is plain data, a command, a count and a register, so an undo or a repeat can record it.
- `r` takes the next key as its argument. Its row ends in `<Any>` and holds `takes` in place of `command`: `takes` builds the command from the key (`letterOf` in `keymap.ts`), so the letter rides inside `Command.ReplaceLetters` and `.` and undo carry it with no plumbing of their own. One grapheme is a letter, `<Tab>` a tab and `<CR>` a line break. Any other named key (Esc, Ctrl-[, Ctrl-C, Backspace, Delete, an arrow, Home, End, Page Up, Page Down, a chord, Ctrl-V) gives `None`, which drops the pending keys, so `r` cancels and the count goes with it. `.status .pending` reads `r`, or `3r` with its count, while it waits. While a row waits on `<Any>` (`Keymap.awaitsArgument`) an IME `Commit` of one grapheme is the key, so a letter picked in an IME after `r` replaces; outside that IME text in NORMAL still does nothing. While it waits, typed text or a `Commit` of more than one grapheme is the key `Keymap.longerText`, which no `takes` reads, so it drops the pending keys, puts nothing, and `.status .pending` empties as after any key that cancels `r`. The empty `Commit` of a cancelled composition is no key, and `r` still waits, as it does through the `Preedit` before it.
  - `3rx` replaces three letters with one `Buffer.rewrite` and the cursor lands on the last. With fewer letters left on the line, and on an empty line, `r` fails and changes nothing. `r` then Enter replaces the letters with one line break, whatever the count, and the cursor goes to the start of the new line. `r` writes no register, a register name before it is ignored, and `dr` cancels both, as in Vim.
  - After `r` the column `j` and `k` keep is the letter put, even after `$`. `.` repeats it with its letter and count; a count before `.` replaces the count and stays, as for any command. `u` puts the cursor on the first letter replaced (`began`), and one `r` is one undo step.
  - One `r` adds at most 4,000,000 UTF-16 units (`lettersWithin`): a letter of several units, such as one picked in an IME with many marks, replaces as many letters as fit, and always one.

- `f F t T` take a letter and `;` and `,` repeat the last find. They are `Seek` commands, not motion names, because a find carries its letter, can fail and reads `Kept`: `Seek.Find` holds the way (`Forward` or `Backward`), `till` and the letter, and `Seek.Again` holds only `reverse`. `seekRows` in `keymap.ts` are the six rows, written once and lifted by `lifted` into NORMAL (`Command.Seek`), after each operator key (`Command.OperateSeek`) and into VISUAL (`VisualCommand.Seek`). `sought` in `vim/seek.ts` is the one place a seek meets the last find: it returns the new `Seek.Memory` and the landing, a spot and its reach, or `None`. NORMAL, the operators and VISUAL each take that pair, so a later motion that carries data and reads `Kept`, such as a search, is another case of `Seek` with its own field in `Memory`.
  - The letter is taken as `r` takes it (`takeLetter`, `letterOf`): one grapheme, a tab for `<Tab>`, a line break for `<CR>`, which no line holds, so `f` then Enter fails; any other named key cancels, and the count goes with it. A digit, `"` and `f` after `f` are the letter. A one-letter IME commit is the letter. `.status .pending` reads `f`, `2f` or `2df` while it waits.
  - `found` scans the cursor's line only, with `indexOf` or `lastIndexOf` for the letter and a check that the match is a whole cell, so an ASCII line is never segmented. A count finds the nth match. Fewer matches fail and the cursor, the column `j` and `k` keep and the pending operator stay as they were, with no register written. `t` and `T` land beside the match, so `tx` with the `x` beside the cursor stays, and that is a find. After `t` or `T`, a `;` or `,` with no count or a count of 1 passes over a match beside the cursor (`skipsBeside`, Vim without `cpo-;`).
  - A find typed in NORMAL, under an operator or in VISUAL is the last find, a failed one too; a cancelled one is not. `;` and `,` keep the stored way and `,` flips it for that move. `again`, which plays the steps of `.`, puts the last find back after a `Run`, so the dot of `dfx` finds its own `x` and leaves `;` as it was, and the dot of `d;` reads the newest find.
  - A forward move is inclusive and a backward one exclusive (`rangeToLanding` in `targets.ts`, which passes the private `rangeOf`). So `dfx` and `dtx` take the letter they land on, `dFx` and `dTx` leave the letter under the cursor, `dTx` with the `x` beside deletes nothing and is still what `.` repeats, and `yFx` moves the cursor to the start of the yank.
  - A find that lands sets the column `j` and `k` keep from the letter: the last column of a tab, the first of a wide letter. In VISUAL and V-BLOCK it moves the cursor end on its own line, from the line break too, where `f` fails and `F` works.
  - The comparison with Vim: `vim-pr7a/proof/vim-compare/fcompare.py` builds rows that mix finds (letters present and absent, counts, `;` and `,` with counts, cancels) with motions, `d c y` and a find, registers, `.`, `u`, Ctrl-R, `gv`, `r`, NORMAL edits and the three visual kinds, over the thirteen notes of the `r` comparison. A failed find does not throw away the keys after it in `feedkeys(keys, 'xt')`: Vim's beep flushes only mapped keys, so `fzx` deletes a letter there as a person's keys do. In headless Chromium at 1000x600 `fz` from the start of that line to its last letter takes 30 ms to the next frame, as `$` does (28 ms), and `9999999;` 49 ms, as `9999999l` does (47 ms). A `;` held at 30 Hz on that line makes no long task, as `l` makes none. `j` and `l` cost what they cost before the find: in Node 5.22 and 4.89 µs a key on 40 lines (5.10 and 4.91 before, the median of ten processes each), and in Chromium 17 ms to the next frame on 120,000 lines on both builds, with no long task while held at 30 Hz.
- `/ ? n N * #` search, with a prompt in the status line. Opening the prompt is its own command (`Command.OpenSearch` in NORMAL and after an operator key, `VisualCommand.OpenSearch` in VISUAL), lifted like the seek rows. The other search cases are more of `Seek` (`Search`, `Next`, `Word`), and `Seek.Memory.search` holds the last pattern, its offset and its way. `sought` runs them with the same lift as a find, so NORMAL, the operators and VISUAL take them with a count.
  - The prompt is core state, `Editor.prompt` (`Asking`: the `Prompt` in `src/core/prompt.ts` and the `Resume` of the key that opened it, a `Search` (way, operator, count, register) or a `Command`, which `opening` in `vim.ts` takes whole; `promptLead`, `promptHistory` and `withPromptHistory` in `vim.ts` are the one match over it that says the lead character and which history list it walks). `inputPlan` feeds it before the keymap, and `keyboard.ts` does not change. The `Run` of `/` returns the fate `OpenPrompt` and waits in `Resume` (way, operator, count, register) until Enter, and `.status .pending` keeps showing the pending operator. `Vim.resumed` runs it at Enter in the mode it was opened in. Esc, Ctrl-[, Ctrl-C, Backspace or Delete on an empty prompt and a click close it. Ctrl-E and Ctrl-P close it and then run (`isScreenKey`, one predicate built from `screenKeys` in `keymap.ts` and exported through `vim.ts`). A chord acts in the prompt only when it is Ctrl alone, with no Shift, Alt or Meta: Ctrl-U clears before the caret, Ctrl-C and Ctrl-[ close it, and Ctrl-Shift-U does nothing there. The shell opens the read view for any Chord of `e` and the finder for any Chord of `p`, so Meta-E and Ctrl-Shift-E open the read view and Meta-P the finder with the prompt open, and the prompt is not closed or cleared: it is still open under them and shows again with its text when Esc closes them (Alt-Ctrl-P is a typed character and does nothing). The vim toggle, opening another note and a change from another tab close it as they drop pending keys.
  - The prompt edits as the finder's does, with the same `Line` (`src/core/line.ts`: `text`, `caret`, `preedit` and `typeText`, `erase`, `left`, `right`, `home`, `end`, `backspace`, `delete`): text, IME text, a paste up to its first line break, Left, Right, Home, End, Backspace, Delete, which acts as Backspace at the end of the text, Tab, which types a tab letter, and Ctrl-U. Up and Down walk `Kept.history.search` (50 entries, `/` and `?` together, newest first, a typed line moves to the newest place). Text typed before Up is a prefix, Down past the newest brings it back and Up past the oldest stays. A line closed with Esc is in the history. `Frame.surrounding` holds the prompt's text and caret while it is open, and `data-control` and `data-selection` name `.status .prompt` and `.status .prompt-caret`, so an IME window sits at the prompt. `PromptLine` carries the letter under the caret, drawn in `.prompt-lead`, `.prompt-before`, `.prompt-caret` and `.prompt-after`. A long line scrolls the typed text and keeps the `/` or `?` in view (`.prompt-before` is a flex box that clips on the left). The editor's cursor is drawn dimmed meanwhile.
  - The matcher cannot backtrack. `src/core/vim/pattern.ts` reads a Vim pattern in `magic` mode (`\v`, `\m`, `\M`, `\V`, `\c`, `\C` too) token by token into a syntax tree (`Node` in `matcher.ts`: letter, any, class with ranges and negation, concat, alternate, repeat with `min`, `max` and `lazy`, group, and the assertions `LineStart`, `LineEnd`, `WordStart`, `WordEnd`), and `src/core/vim/matcher.ts` compiles the tree to a program (`Char`, `Any`, `Class`, `Split` with a preferred branch, `Jump`, `Back`, `Assert`, `Match`) and runs it as a Pike VM over one line, one code point at a time. The run keeps a list of threads in priority order, each with its start, and a visited mark for each instruction (an `Int32Array` of the step that last reached it, and `find` zeroes it and starts again from 0 when the step counter passes 1,000,000,000, so it can never wrap: one `find` adds at most two to the counter for each code point, a line is under 500,000,000 units, and 1,000,000,000 plus 1,000,000,000 is under 2^31), so a step costs at most the program's size and a line of n letters costs n times that. The first alternative that matches wins, a greedy repeat prefers more and a lazy one (`\{-}`) less, the leftmost start wins, and when a thread matches the threads of lower priority are dropped and the higher ones go on. A repeat whose body can match nothing leaves its loop when an iteration ends where it began (`Back`), as Vim's NFA engine does. A counted repeat expands in the program, and a program over 5,000 instructions is refused with `not supported in a search: a pattern this large`. The VM starts a new lowest-priority thread at each position, so it runs once over the line, not once for each start. No RegExp is built from a pattern.
  - Three fast paths keep a plain search as fast as `indexOf`: a pattern of letters only (no `\c`) is found with `indexOf`, with `\<word\>` checked at the hit, so `*` is fast; any other pattern derives, where there is one, a literal run every match holds and skips a line without it with `indexOf` before the VM runs; and where the code points a match can start with are few, threads start only there.
  - Case and words. `\c` folds with `toLowerCase` on the line's code point, the pattern's letter and a class's ranges, and `\u` and `\l` do not fold, as in Vim. `.` is one code point. `\<`, `\>`, `*` and `#` use one word test, `classOfCodePoint` in `matcher.ts` over `src/core/vim/classes.ts`, Vim's `utf_class` table read out of Vim itself: blank is 0, punctuation 1, and 2 and up are word letters, so an emoji and a CJK letter are word letters and a pattern `*` builds always finds its own word.
  - A token it does not read is refused with the notice `not supported in a search: <token>`, named as typed (for example `\@=`, `\%[`, `\z(`, `[[:alpha:]]`, `[\n]`), and Vim's own errors keep Vim's text (`E54`, `E55`, `E53`, `E554`, `E872`, `E944`, the last found in the collection parser). A collection reads its backslash escapes as Vim does (`\e`, `\t`, `\r`, `\b`, `\\`, `\]`, `\^`, `\-`, `\d123`, `\o40`, `\x20`, `\u20AC`), and a `\w`, `\s` and the like inside it is not a class, as in Vim (`collectionRows` in `e2e/vim-search.spec.ts` holds the rows, each from Vim). `$` is the line end before `\c`, `\C`, `\m`, `\M`, `\v`, `\V` and `\Z`, and always in `\v`. `^*` and `\(^*\)` are a literal `*`, `\<*` and `\<\+` repeat the assertion.
  - `src/core/vim/search.ts` holds the offset (`e`, `s`, `b` with a number, or a line count) and `find`, a port of Vim's `searchit` and `do_search` over one line at a time: a match under the cursor is skipped, a forward search on the first line takes the first match that starts past the cursor, a backward one the last match that starts before it, the wrap pass takes any match, and the note is never joined. A count loops from each found place. The next place depends only on the place, so once a step lands where an earlier step landed the places are a cycle, and the rest of the count is `remaining mod length` more steps taken from the table of places already visited, with the wrap notice on (a cycle always wraps, and Vim leaves `search hit BOTTOM, continuing at TOP` after a forward count that wraps any number of times, and the TOP one after a backward count). A count over many lines keeps each line's first match for the length of one `find` (`recalled`), so the second lap costs no matching, and the width of the cursor's cell is read without segmenting the line when the letter and the one after it are below U+0300. An offset is undone before the search runs, as Vim does, and the start is a tagged value (`At` a place, `BeforeNote` or `AfterNote`), so an undo that runs off the note's edge starts before the first line or after the last and makes no line of its own (`/^$/e-9`, `?^$?e+3`). With an `e` offset the end test applies to every candidate of the first count step and an empty match lands on its start, not one before it. A backward search from column 1 skips its own line. In VISUAL an offset that runs past the line end rests on the line break. `*` and `#` follow `find_ident_at_pos`: the word under the cursor or after it on the line, else the non-blank string, wrapped in `\<` and `\>` only for a word.
  - The reach is exclusive, inclusive with an `e` offset and linewise with a line offset (`Landing.reach`). An exclusive landing on the line break clamps to the last letter, as Vim's `oneleft` does for an operator, so `d/$`, `c/$`, `y/$` and `d/\s*$` leave the last letter of the line (`beforeLineBreak` in `targets.ts`), and in VISUAL `v/$<CR>d` and `d/$/e` take it. A failed search cancels an operator and keeps the selection in VISUAL. A failed search (E486 or a refused pattern, not E348) also drops the column `j` and `k` keep, so the next `j` or `k` starts from the cursor's column, as Vim's `w_set_curswant` does before it searches (`Sought.resetsColumn`). A refused pattern becomes the last pattern, as Vim's errors do (E54, E55 and the rest), so `n`, `N`, `dn`, `.` and an empty pattern refuse again with the same notice and move nothing. An unclosed `[` in a pattern swallows the rest of the command, so `/[/e` searches for `[/e` (`swallowsRest` in `pattern.ts`, Vim's `skip_anyof`), while a `]` later in the text still closes the collection over the `/`. `n` and `N` repeat a search that leaves the cursor where it was with a count one higher, as Vim's `nv_next` does (a found place that is not a line offset and did not wrap, and that equals the cursor after the cursor is put back on a letter, in NORMAL and under an operator, or as it is in VISUAL): an offset that runs off the note's last or first letter leaves the cursor on the edge letter, so `/\l/b+1` over `ab`, `abc` from 1:1 and four `n` lands on 1:2 (`repeated` in `seek.ts`). A typed `/` or `?` does not repeat. Every non-linewise landing under an operator clamps to the last letter before a line break, so `d?$?e` over `ab`, `cd` from 2:1 leaves `ad`. `Step.notice` carries the notice to `Editor.notice`: `E486: Pattern not found: <pattern>`, `E35: No previous regular expression`, `E348: No string under cursor` and the wrap notices. `.` after `d/two<CR>` searches again and makes `two` the last pattern again, and after `dn` it reads the newest pattern, since `again` restores only the find, not the search.
  - The comparison with Vim: `vim-pr7b/build-probes/cmp.py` runs 1,296 rows of patterns, offsets, counts, operators, `dn`, `*`, `#` and wraps against `vim -u NONE -i NONE -N -es` (`-i NONE`: a viminfo file leaks the last pattern into `3n` and `*n` rows), and `erows.ts` the 152 offset rows. None differs. `vim-pr7b/vim-compare/searchcompare.py` mixes searches, offsets, counts, `n N * #`, operators, registers, `.`, `u`, `gv`, finds and the three visual kinds over thirteen notes: three seeds of 8,000 rows, 21,227 counted, 1,341 differ, and 1,339 are classified: 1,088 refused tokens (a `;` offset 435), 22 `n`, `N` or `.` after a refused `;` offset (nullpad has no last pattern from it, where Vim ran both searches), and the accepted differences of the VISUAL, block and undo bullets that a search row reached. The other 2, both of seed 1, are two known classes that the explainer does not reach: a failed `c/zzz` after leaving VISUAL on a tab, where Vim keeps the screen column its cached cursor column holds from VISUAL, and a `gv` after a later `d?x?-1` took out the line of an end (the same row with `dk` differs the same way). `vim-pr7b/matcher-compare/` runs the matcher alone against Vim over generated patterns and lines (`gen.py`, `vim.vim`, `mc.ts`, `run.py`): 72,000 pairs of a pattern over the supported tokens and a line, comparing the first match's start and end, 0 unexplained. It explains by the rows where Vim's own two engines disagree, and accepts one shape: a repeat of a group whose body is itself a repeat that can match nothing and is followed by more of the same (3 rows in 72,000).
  - Speed, on 120,000 lines (`vim-pr7b/perf/`, run on this build; Chromium 158 headless at 1000x600, Node core). A huge count is bounded by the cycle of places: in the core on 120,000 lines `9999999/x` and `9999999n` with one match in the note take 16 to 23 ms, with a match on every line 140 to 190 ms (a cycle of 120,000 steps, each reading one line, where 60,000 such lines took 7.4 s in headless Chromium before), and with `[a-z]\+[0-9]`, one match, 90 ms for `9999999/` and 62 to 90 ms for the count after a `/` (211 ms in all with that `/`'s 121 ms). `9999999N` costs the same. 378 rows of counts (5 to 9,999,999, `n` and `N`, `?`, offsets, `d`, `\<two\>`, `^`, `$`) over three notes and all cursor places match Vim's place, text and wrap notice (`build-probes/count-rows.py`, `count-rows.ts`).   - The freeze cases, one line of letters with the literal the pattern needs at its end and a digit it lacks, so the VM runs: 100, 5,000 and 50,000 letters take, in ms, `a*a*a*a*a*b\d` 1.1, 5.5 and 19.9, `\(a\|a\)*b\d` 0.5, 2.8 and 10.4, `\(x\+x\+\)\+y\d` 0.3, 2.8 and 26.7, `[a-z]\+ing\d` 0.3, 1.2 and 8.5, `.*.*.*.*x\d` 0.3, 1.7 and 15.0, `.*.*.*.*.*x\d` 0.2, 2.1 and 18.2, `\w*\w*\w*\w*x\d` 0.3, 2.0 and 16.7. On a line of 48,000 letters (`ab ` 16,000 times) `.*c\d`, `.\{-}c\d`, `\w\+c\d` and `\(ab \)\+c\d` take 5.4 to 5.9 ms, and `\<c` with a `c` at the end that is not a word start 0.8 ms, as it starts threads only at `c`. Each grows in line with the line, and none takes over 6 ms at 5,000 letters.
  - Accepted differences from Vim: no `incsearch` and no `hlsearch`; the refused tokens above, a program over 5,000 instructions, and a pattern cannot cross a line break; no Ctrl-R in the prompt, no Ctrl-W (the browser closes the tab) and no `q/` window; no `''` mark, so Ctrl-O does not go back after a search; no `g*`, `g#`, `gn` or `gN`; a match that starts inside a letter lands on the start of that letter; no search in the read view, and no Ctrl-F with vim off; `\c` folds with `toLowerCase`, as above; where Vim's NFA and backtracking engines disagree on a nullable alternative, we follow the NFA engine; a repeat of a group that holds a nullable repeat followed by more of the same may take another path than Vim (3 rows in 72,000); Ctrl-E and Ctrl-P close the prompt, and the same keys with Meta or Shift open the read view and the finder and leave the prompt open under them; a search with a `;` offset is refused and is not the last pattern, so `n` after it reads the pattern before it or gives `E35`; a failed search right after leaving VISUAL on a tab sets the column `j` and `k` keep to the tab's last column (Vim keeps the first column its cached cursor column held in VISUAL).
- `:` opens the command line, a second prompt in the status line that is the search prompt with another `Resume` (`Resume.Command`) and its own history list. `Command.OpenCommand` is a row in NORMAL only (no row after an operator or in VISUAL, so `d:` drops the pending keys, and `3:` drops the count and opens empty). The shell draws the lead from `PromptLine`, so no shell code knows `:`, and `keyboard.ts` is unchanged. `src/core/vim/command.ts` parses a line into `Empty`, `Goto`, `Write`, `Unsupported` or `Unknown`, and `resolve` turns a `Goto`'s address against the line count and the cursor line. `Vim.resumed` runs it at Enter, and `commanded` in `vim.ts` builds the `Step`.
  - Leading spaces and colons are skipped. An address is `N`, `$` or `.`, then any chain of `+N`, `-N`, `+`, `-` and a bare `N` (a bare number after an address adds, so `5 3` is 8), with spaces between terms, read as `get_address` in Vim's `ex_docmd.c` reads it. Only the final value is judged: past the last line is the last line, 0 is line 1, below 0 moves nothing and shows `E16: Invalid range`. A number saturates at 1e15, so `:99999999999999999999` and `:+99999999999999999999` go to the last line. A move lands as `G` with a count does (`motions.LastLine`): the first non-blank letter, the column `j` and `k` keep from the landing place, a reveal, no undo step, `.` and the registers unchanged. A trailing colon or spaces are skipped.
  - `w`, `wr`, `wri`, `writ` and `write` with no argument return `Step.save`, which `Editor.Outcome.save` carries to `respond` in `src/main.ts`. `write` there sets `Model.writtenNotice` to `Owed` and saves as a page hide does (`saveIfDirty`, so one save at a time: an in-flight save finishes first). `settleWritten` sets the notice `written` (`Editor.noticed`) once the note is clean and no save is out, at once when nothing was unsaved, and drops the debt when the store is unavailable or the note cannot be saved. The debt ends at the person's next act, where a notice clears (`withoutNotice`, which runs before the message is handled, so the `w` Enter itself still leaves it owed), so `written` only shows between the Enter and the next act. Opening another note drops it too. Anything after `w` is the notice `not supported: <line, ends trimmed>`. Any other line, an address before a command included, is `E492: Not an editor command: <line without its leading spaces and colons>`.
  - The prompt, its history, its keys and the screen keys are the search prompt's. The `:` history and the search history are separate lists.
  - Accepted differences from Vim: no ranges and no Ex commands but `w` (`:5w`, `:1,3`, `:%`, `:'a`, `:/x/`, `:5|`, a `"` comment and a command modifier are `E492`, where Vim runs them); no `:` in VISUAL and none after an operator; a count before `:` is dropped, where Vim prefills `.,.+2`; no `q:` window, no Ctrl-R and no Tab completion (Tab types a tab); no `:` in the read view or with vim off; a number of 2^63-1 or more goes to the last line, where Vim does nothing for a plain one and goes to line 1 or gives `E1247` after `+` or `-`; `:w` with an argument, `!` or `>>` is refused; the `written` notice replaces Vim's file message.
  - On 120,000 lines in Node (the median of 15 runs on a fresh editor, three rounds), the keys `60000G` take 0.27 to 0.42 ms and `:60000<CR>` 0.35 to 0.48 ms, which includes opening the prompt and typing its six letters and Enter.
- A `Target` takes the buffer, the cursor's cell and the count and returns `Option<Range>`; `None` cancels the operator, an empty range still runs (`ch` at column 1 enters Insert). A `Range` is `from`, `to` and `Charwise` (half open, in cells) or `Linewise` (whole lines from `from.line` to `to.line`, and `from` is where a yank leaves the cursor). Each of Vim's rules that does not follow from the motion lives in one place:
  - `w` under an operator stops at the line end on its last step, so `dw` on a line's last word does not join the next line: `forwardWordStoppingAtLineEnd` in `motions.ts`, a port of Vim's `fwd_word` with its end-of-line stop.
  - `j`, `k`, a counted `$` and `Lines` fail where they cannot move, so `dj` on the last line and `2dd` on the last line do nothing (`motionFails`, `lines`), and a counted `b` fails only when one of its steps starts at the start of the note, so `d9b` deletes back to the start (`wordBackward`, a port of Vim's `bck_word`).
  - `l` reaches the slot past the last letter, so `x` is `dl` at a line end (`rightward`).
  - An exclusive range that ends in column 1 of a later line ends at the line end above it, or goes linewise when it starts in the indent (`rangeOf`, the one place every charwise target passes).
  - `cw` on a letter changes to the end of its word and keeps the space after it, and on a word's last letter changes that letter (`targetFor` swaps in `wordEndStay` for a change).
  - A delete over several lines that starts in the indent and leaves only blanks after its end goes linewise (`linewiseWhenBlankAround`, delete only).
  - A linewise change leaves one empty line with no indent (`emptyLine`).
- After a delete the cursor rests on a letter, after a linewise delete on the first non-blank of the line now there; after a yank at the range's start; after a change in Insert at the range's start. After a put of letters within one line it is on the last letter put, after a put that spans lines on its first letter, and after a linewise put on the first non-blank of the first new line. Deleting every line leaves one empty line (`Buffer.removeLines`, which keeps the ids of the lines left; `Buffer.insertLines` gives new lines new ids).
- Text objects port Vim's `current_word`, `current_par`, `current_quote` and `current_block` over cells, in `objects.ts`. Each object has `find`, which NORMAL's operators use, and `pick`, which VISUAL uses. An operator whose object is not there drops the column `j` and `k` keep. `diw`, `yiw` and `ciw` on an empty last line take the last letter of the line above and its line break, as Vim does. A bracket object finds its pair across lines and counts brackets inside quotes. When the cursor is in no pair, it takes the next opening bracket after the cursor, on any later line too, as Vim 9.1 does. Brackets and quotes are ASCII, so the bracket scan reads UTF-16 units and segments only the line where it lands.
- `Editor.kept` is what outlives a note: `registers`, `dot`, `seek`, the last find and the last search, and `history`, the prompt's lines: `search` for `/` and `?` and `command` for `:`, 50 each. It lives beside `vim` in the editor, so it survives vim off and `reopen` (opening another note), and a reload starts with none.
- `registers` holds the unnamed register, the yank register (`"0`) and `named`, a record from a lower-case letter to its register. A register is a text and a kind; linewise text ends in a line feed. `remembered` in `operators.ts` is the one function that writes them and `registerFor` the one that reads them, each a match over `RegisterName`, so a new kind of register is a case in both.
  - With no prefix a delete, a change and a yank write the unnamed register, and a yank the yank register too. `"a` writes the letter and the unnamed register and leaves `"0`. `"A` adds to the letter, and the unnamed register then holds all of it: letters after letters join, and when either part is whole lines the result is whole lines, each part on its own lines. `""` and `"0` before a command fill the unnamed and the yank register, for a delete too. `"_` writes nothing. `"+` and `"*` write the unnamed register and the system clipboard.
  - A put with no prefix or `""` reads the unnamed register, `"0` the yank register, a letter of either case its register, and `"_` nothing. A put from an empty register changes nothing and still becomes `dot`.
  - A yank of nothing writes an empty register. A delete of nothing writes none. A change of nothing writes an empty register only when its motion is inclusive (`C`, `c$` and `ciw` on an empty line, `Range.inclusive`), and none for `cl`, `ch` and `c0`. `cc` and `S` on an empty line write one empty line. Each is Vim's answer.
- `"+` and `"*` are the system clipboard, which only the shell reaches. A delete, change or yank into it returns the text in `Step.clipboard`. A put from it returns the fate `ReadClipboard`, and the editor asks with a `Need` (see Editor) and changes nothing: the prefix stays pending, so `.status .pending` shows `"+` while it waits, and keys typed meanwhile queue behind it. `Editor.clipboardRead` lands the answer through `Vim.putClipboard`, and the history takes where that put began, so `u` after `"+p` over a selection leaves the cursor where `u` after `"ap` does. `Some` text is put as whole lines when it ends in a line break, and otherwise as letters, with CRLF and CR read as LF (`fromClipboard`). `None` puts nothing. Either way the put becomes `dot`, and a `.` asks the clipboard again. A read writes no register. `src/clipboard.ts` holds the two Effects: `readText` gives `None` when the browser refuses, answers with something that is not text, or 3 seconds pass, and `writeText` gives whether the write worked. While the permission state of `clipboard-read` is `prompt`, Chrome is asking the person and the read has no time limit, so an Allow after second 3 still puts. A step's `WriteClipboard` goes out before its `ask`, so a `"+p` queued behind a `"+y` reads what the yank wrote.
- `Editor.notice` is one line of the status line, drawn as `.status .notice` and absent when there is none. A read that was refused or timed out and a write that failed set it to `clipboard blocked, use Ctrl-Shift-V`, the paste that works in every mode (see Block). `update` clears it before it handles the person's next act: an input, a click on the text, or the `read` or `vim` button, over the read view and the finder too. An input replayed from a queue does not clear it, so the notice of a read stays after the keys typed during its wait have run.
- `.` does the last change again, and a count on `i a I A o O` types the stay's text that many times at Esc. `dot` is a `Vim.Repeat`: the command, its count, its register and `typed`, the record of its INSERT stay. It is command data, not keys, so it holds when the keymap changes.
  - A delete whose target exists, an empty one included (`x` on an empty line), and `p` or `P`, with nothing to put included, become `dot` when they run. A stay becomes `dot` at Esc, a stay that typed nothing included, so after `xi<Esc>` a `.` inserts nothing. A stay that ends another way (vim off, another note) is forgotten. A yank, a motion, `u`, Ctrl-R, a paste in Normal and a command whose target fails leave `dot`.
  - A stay records itself in its mode, `Insert { recording }`: the command and count that began it, and each input that changes text (typed text, Enter, Tab, Backspace, Delete, a paste, IME `Commit` and `Erase`). Arrows, Home, End, Page keys, chords and `Preedit` are not recorded, and a click leaves the recording as it is. A Backspace at the start of the note is not recorded, as in Vim.
  - `typed` is a list of `Recorded` entries: `Keys` holds a run of printable ASCII typed key by key, and `Other` holds one input. A letter or a space typed by a key starts a run or adds to it, and so do longer text one key typed and a Tab's two spaces, except at the start of a run or of a line in it. An Enter after a key adds its line feed, and a Backspace takes back the run's last key when the run holds two or more and neither of its last two is a line feed. Every other input is an `Other`. So a held key copies nothing, and the record grows only where a run breaks. The mode is built as a plain record, with no Schema check, because a check of the whole record on every key made typing cost grow with the stay. A stay records at most 10,000 entries (`maxRecordedInputs`), and one more clears `dot` and records no more of it: above about 16,000 entries V8 keeps the list as a large object, and its copy on each key costs 9 ns an entry where it costs 1.5 ns below.
  - A run plays as at most five inserts: the line feeds it starts with, its first key alone, the rest up to the end of its first run of line feeds, the key after them alone, and the rest. A key typed before a lone combining mark joins it, and the caret moves past it, and a stay's first key and the first key after its first line break are the keys that meet one, so a run never starts a line with more than one key. Played this way a run left the lines, joins and caret its keys leave one by one in 30,000 random stays over notes of lone marks, flags, ZWJ, joins and lines that start with 70 and 100 marks, compared after every key. Not probed: a line with two joins that each have a lone mark after them, and a row of marks longer than 128 UTF-16 units, where a later key of a run could meet a mark too.
  - `.` and Esc return the fate `Replay`, a list of `Replayed` steps: `Run` (a command and a count), `Typed` (one input) and `Leave`. `.` is `Run`, the stay's steps, then `Leave`. Esc, and `Leave` in a recording stay, make the stay `dot`, then play its further copies and a last `Leave` with the recording off. A further copy of `o` or `O` starts with a typed Enter, a line break at the cursor, as Vim's redo does, so `2Ohi<Esc>` leaves the cursor on the second `hi`, and `2ox<Del><Esc>` at 1:1 of `one`, `two`, `three` leaves `one`, `x`, `xwo`, `three`.
  - The editor plays each step as a queued `Again` item with its `replay`, so a step passes `planOf`, the history and `plainPlan` as a typed key does. A recorded Delete asks the layout again, and keys typed meanwhile wait behind the steps left. While a step waits the editor is in INSERT, so the status line reads INSERT and the caret is the bar, one frame for each recorded Delete. A change to the open note from another tab in that wait re-shows the note and drops the steps left, `Leave` included, so the tab stays in INSERT and the next Esc makes the cut-short stay what `.` repeats. Outside a stay `Typed` and `Leave` do nothing, so a repeated change whose target fails types nothing.
  - A replay records as typing does, which is how Vim's redo works. So a count before `.` replaces the count when the command runs, and stays (`3x2..` deletes 3, 2, 2), a `.` whose command fails leaves the old count, and the counts given multiply first (`2d2w` then `3.` is `d3w`). A count on a change belongs to the operator, so a change has no further copies. A register typed before `.` is ignored and the repeat keeps its own. Vim does that when the command had a register, and writes the typed one when it had none.
  - The further copies of one replay hold at most 20,000 inputs (`maxReplayedInputs`), a run counting one for each key, and 120 Delete keys (`maxReplayedDeletes`), and stay within the bounds of a put of the same text. The count is lowered to fit. The copies of a stay that is one run go in as one run, so `9999999ix<Esc>` and `9999999ia<CR><Esc>` are a few inserts: in headless Chromium the first takes about 40 ms to the next frame on an empty note and on 120,000 lines, and a `9999999.` after `ia<CR><Esc>` 65 ms on both, where `x.` takes 34 ms (the two frames the measure waits). Played as 20,000 steps the first took 9.3 s in Node on 120,000 lines, because each step copies the lines array (0.46 ms). The copies of any other stay play step by step, and on a note of over 5,000 lines their bound is 100,000,000 over the line count (`maxReplayedLineCopies`), 833 on 120,000 lines: `9999999.` after `ia<BS>b<Esc>` takes 350 ms on an empty note (19,998 steps) and 133 ms on 120,000 lines (831 steps). A Delete waits one frame for the layout, so 120 take 2.0 s.
  - The first copy of a `.` has the same bound, counted in steps (`mostReplayed`), and a `.` whose stay plays more steps does nothing. With the record's 10,000 entries that bounds a `.` whatever was typed. In headless Chromium a `.` after a stay of 8,000 typed letters takes 36 ms to the next frame, and 7 to 8.6 s when the record was a list of inputs copied and checked on every key. In Node, typing the 10,000 keys of one stay costs the core 44 to 51 ms (34 to 47 on main), a letter typed after 100,000 keys of a stay about 6 µs (3.5 to 7 on main), and the `.` after it 0.8 to 1.5 ms. The slowest stay is one that never folds, such as `x` and Backspace in turn or IME commits, because each key copies the list of entries: at 10,000 entries a key costs the core 18 to 21 µs (3 on main), and in headless Chromium a `.` after 9,999 of them takes 231 ms on an empty note and after 800 of them 92 ms on 120,000 lines. A Backspace that folds, a Tab and longer text from one key read the run, which makes V8 flatten the string, where a letter only appends: `x` and Backspace in turn after 100,000 letters of one run cost 11 to 17 µs a key (6 on main), and after 1,000,000 letters 270 µs (22 on main).
- Accepted differences from `vim -u NONE -N`: `d` with Space or Backspace at a line edge acts as `dl` or `dh` (Vim crosses the line); a word object on an empty or blank line, in leading indent or reaching past a line end may differ (Vim moves the cursor when it fails); quote objects know no backslash escapes; counts on quote and bracket objects may differ; on a note that is one empty line, `d`, `c` and the delete a VISUAL `p` makes keep the store as it was, and a put over a selection leaves no empty last line (Vim does both only when the buffer was emptied by a delete or never filled); a counted `b` under an operator that fails after stopping on an empty first line leaves the cursor where it was (Vim moves it to 1:1); `p` and `P` put at most as many copies as keep the added text within 50,000 UTF-16 units when the register is letters with no line feed, and otherwise within 4,000,000 units and 200,000 lines, and always one, where Vim builds any size and fails only on overflow (a bigger put crashed `String.repeat` or made a note too big to save; 4,000,000 units stays under the about 5,200,000 that Chrome's localStorage holds, so a reload still brings back a draft of a put on a small note; and the browser lays out one long line slowly: in headless Chromium a put that makes one line of 50,000 letters takes about 80 ms to the next frame and each key after it about 60 ms, where 1,000,000 letters take 1.2 s and then 1.5 s for every key); emoji, flags and accented letters are one letter each, and `r` replaces and puts them whole (Vim replaces or puts their first code point); a find's letter is one grapheme, so `fe` does not find an `e` with a combining accent, and the first code point of a family or a flag does not find it (Vim matches the first code point); `f` then a Ctrl chord, Ctrl-V or Ctrl-K cancels and is no find (Vim searches for the control character, or with Ctrl-K makes a digraph); `f` then Ctrl-E or Ctrl-P opens the read view or the finder; `f` then Page Up or Page Down pages and drops `f`; text of more than one letter while `f` waits cancels `f` (Vim takes the first letter and runs the rest as keys); the last find dies on reload, as the registers and `dot` do; the `.` of a `d` or `c` with a find after a find for another letter, where either letter is outside ASCII, finds its own letter (Vim does not remember a redone letter and compares it with the byte length of the newest one, so after `dfc` and `f😀` its `.` finds nothing, and after `dfb` and `f😀` it deletes up to the next `😀`); `r` then a Ctrl chord or Ctrl-V cancels (Vim puts the control character, or takes the next key as typed); `r` then Page Up or Page Down pages and drops `r` (Vim cancels `r` and does not page); text of more than one letter while `r` waits cancels `r` and puts nothing (Vim takes the first letter and runs the rest as commands); one `r` adds at most 4,000,000 units, as above; no `o_v`, `gp` or `]p`, no `R` in NORMAL, no tag objects (`it`, `at`) and no sentence objects (`is`, `as`); arrows, Home, End and clicks in a stay do not split it, so `.` repeats all its typed text at one place (Vim repeats what was typed after the move); a paste and IME text in a stay are repeated; one `.` or counted insert is bounded as above, where Vim plays any count; after a stay that records more than 10,000 entries, and when its stay plays more steps than the note's bound, `.` does nothing, where Vim repeats a stay of any length; a stay ended by vim off or by opening another note is not what `.` repeats; `"A` leaves a letter's register as it was when the text would pass 500,000,000 units, and the unnamed register then holds the new text alone; no numbered registers (`"1` to `"9`), no small delete register (`"-`), no read-only registers (`".`, `":`, `"%`, `"/`) and no `q` macros, so those names drop the pending keys; `"+` and `"*` are one clipboard; a put from the clipboard waits for the browser, up to 3 seconds, and a refused one shows the notice where Vim puts nothing in silence; text read from the clipboard is whole lines exactly when it ends in a line break (the Vim we compare with has no clipboard to ask).
- `rest` runs on every outcome in Normal, from `done` in `editor.ts`: the caret is the start of a cell, never past the last cell of a line with text, never at the end of a wrapped row. So a click, a Page key, a paste and the toggle land on a letter without a rule of their own.
- Toggling is `Queued.ToggledVim`, queued with the inputs, so it waits behind a pending locate and every key before it is read with the old setting. It is not an `Input`, so the finder and the read view never see it. `update` takes Ctrl-, before it routes an input, so the chord toggles over the finder and the read view too, and the mode applies when the editor returns. `update` writes the setting whenever a message leaves vim on where it was off, or off where it was on. Ctrl-P and Ctrl-E are fed to the editor as well, in order, so they drop pending keys. A click drops them too.
- In Normal, typed text of one grapheme is a key, whatever key made it, so a dead key's `^` works. Longer text and IME text (`Preedit`, `Commit`, `Erase`) change nothing. Text the core swallowed is still in the EditContext, so `Editor.discards` counts it, the port carries it as `data-discards`, and `keyboard.ts` sets the EditContext's text again when it changes. Without that, an IME conversion in Insert erases letters counted from a text that holds the swallowed keys.
- The cursor is the block in Normal and with vim off, and a 2 px bar in Insert (`Frame.caret.shape`, carried as `data-caret-shape`). It does not blink. A space that hangs past a full row at a soft wrap draws one cell wide in the right padding of `.sheet`.
- `script()` names keys as Vim writes them, so `Editor.feed` over `script('3w')` or `script('ix<Esc>')` runs vim in Node, and the answers can be checked against `vim -u NONE -N -es` (`-N`, because Vi-compatible mode fails `9j` on a three-line note instead of going to the last line). Feed Vim the keys with `feedkeys(keys, 'xt')`: `:normal` drops every key after the first command that fails, where a person's later keys still run. A `"+p` in Node returns a `Need`, and `Editor.clipboardRead` with its ticket and the text, or `None`, lands it. Vim's `getreg` and `getregtype` give a register's text and kind to compare.
- A cell of an ASCII line is one UTF-16 unit and is never segmented. On a 120,000-line note `9999999w` takes about 0.5 s to the next frame in headless Chromium, a `j` about 2.3 ms when keys come back to back, and a `j` held at 30 Hz makes no long task. Segmenting every line made the first far jump take 3.9 s. On the same note `dG` from line 1 takes about 50 ms to the next frame, `p` of the 120,000 lines back about 100 ms, `1000dd` about 65 ms and `p` of 10,000 lines about 35 ms (a `gg` costs about 35 ms there), a `dd` about 8 ms when keys come back to back, and `d` held at 30 Hz makes no long task and lands 11 ms after the last repeat. Checking for an empty note by joining its text doubled the cost of a `dd`. `yy` then `9999999p` on a 100-letter line puts its 39,603 copies in about 80 ms, and on 120,000 lines of `line N é😀` with no brackets, `di(` from line 60,000 takes about 65 ms the first time and 35 ms after, where cutting every line it passed into cells took 1.5 s.
- A new key is a row in `normal` in `src/core/vim/keymap.ts`. A key that takes the next key as its argument, as `r` does, is a row whose keys end in `<Any>` and whose `takes` builds the command from that key. A motion that carries data, can fail or reads `Kept`, as a find does, is a case of `Seek` in `vim/seek.ts`, its arm in `sought`, and a row in `seekRows`, which makes its NORMAL, operator and VISUAL rows. A new motion is a case of `MotionName`, an entry in `motions`, its reach in `reachOf` in `targets.ts` (exclusive, inclusive or linewise) and a row in `motionRows`, which makes its operator rows too. A new text object is a case of `ObjectName`, an entry in `objects` in `objects.ts` with its `find` and `pick`, and a row in `objectRows`, which makes its operator rows and its VISUAL row. Every row carries `about`, which a which-key view will draw from `next`.
- A test may read `.status .mode` (`EDIT`, `NORMAL`, `INSERT`, `VISUAL`, `V-LINE`, `V-BLOCK` or `READ`), `.status .pending` (the count, register and keys waiting, such as `2g`, `d`, `2d3`, `ci` or `2"a3`, empty otherwise), `.status .notice` (absent when there is none), `.status .prompt` (the prompt's `/`, `?` or `:` and its text, absent when it is closed), `.status .toggle-vim`, and the selection as drawn (see Visual mode).

### Visual mode

`v` in NORMAL selects letters, `V` whole lines and Ctrl-V a block of screen columns. The mode reads `VISUAL`, `V-LINE` or `V-BLOCK`. This part is about `v` and `V`, and Block below says what a block does differently.

- `Mode.Visual` holds `kind` (`Letters`, `Lines` or `Block`), `anchor`, the end that stays, and `column`. The cursor end is `buffer.caret`, so every path that moves the caret moves the selection. In VISUAL the caret may rest on the line break, the column that equals the line's length: `l`, Space and `$` reach it, and `v` on an empty line is on it. `rest` clamps only in Normal. The motions are one table built twice, `motionsOn('LastLetter')` for NORMAL and `motionsOn('LineBreak')` for VISUAL.
- `Keymap.visual` is VISUAL's table, a list of `Binding<VisualCommand>`. `advance` is generic over the command, so counts, the register prefix and the pending keys work as in NORMAL and `.status .pending` shows them. The rows:
  - every row of `motionRows` as `Move`, every row of `seekRows` as `Seek` (see the find and search bullets above: the cursor end moves on its own line, a failed find keeps the selection, and `f` then Esc or Ctrl-C keeps it too), and every row of `objectRows` as `Pick`;
  - `o` (`Swap`), `O` (`SwapColumns`, which is `o` outside a block), `v`, `V` and Ctrl-V (`Select`: the same kind leaves, another kind switches and keeps both ends);
  - `s` (`OpenJump`, see Jump);
  - `d x` and Delete, `y`, `c` (`Operate` on the selection), and `X D Y C S R` (`Operate` on its whole lines, each row with the `Reach` a block takes in their place);
  - `p P` (`Replace`), `I A` (`Insert`);
  - Esc, Ctrl-[, Ctrl-C, Ctrl-E and Ctrl-P (`Leave`). Ctrl-E and Ctrl-P then open the read view and the finder, so they are `screenKeys` in `keymap.ts`: `advance` runs them from no pending keys whatever waits, an argument key, `r`, `i`, `g` or a register prefix included, and in NORMAL they drop the pending keys. Ctrl-C leaves with the cursor where it is and copies nothing, as in Vim. Ctrl-X does nothing.
  - `r` and a letter (`ReplaceLetters`), see below.
  - Any other key that takes an argument in Vim (`m`, `'`, a backtick, `@`, `q`, `z`, `[`, `]` and Ctrl-W) is an `Ignore` row that swallows the next key, so `rx` does not delete. A one-letter IME commit after one of them is taken as that key's argument, and longer IME text drops it. Any other key matches no row and drops the pending keys with it: `J ~ u U > < = : /` do nothing and stay in VISUAL.
  - Esc with a count or a register name pending leaves VISUAL (`v2<Esc>`, `v"a<Esc>`). Esc after `i`, `a`, `g` or a lone `"` drops that key and stays, as in Vim.
- `selection.ts` says what a selection covers, and nothing in it knows a key. `endsOf` gives both ends as cells, `shown` what the screen draws, `rangeOf` the `Range` an operator takes. A selection builds its own `Range` and does not pass `rangeOf` in `targets.ts`, whose rules are for motions:
  - `Letters`: from the first end through the letter under the last end.
  - With the last end on the line break the range takes the line break too: it ends at the start of the next line, and at the line end on the last line.
  - `Lines`, and `X D Y C S R` in either kind: the whole lines from the first end's to the last end's.
- An operator returns to NORMAL, or to INSERT for a change, with Vim's cursor and registers. A count before an operator is ignored. `p` and `P` put the register's text in place of the selection (`putOverStep`): `p` leaves the replaced text in the unnamed register and `P` leaves the registers as they were. Whole lines over letters, and letters over whole lines, go on lines of their own. A count puts that many copies. `V"_p` puts one empty line for each count, and a put from any other empty register only deletes the selection, each as Vim does. After a delete that emptied its buffer Vim's put leaves no empty last line. `putOver` and `putOverBlock` do the same (`withoutEmptyLastLine`) when `V` took every line and on a note that is one empty line: `dGvP` leaves an empty line and the lines put, and `dG<C-v>P` the lines put.
- A paste in VISUAL, which Ctrl-Shift-V makes (see Block), is our call, since Vim in a terminal has no paste key: it erases the selection as a change into no register, then pastes as INSERT's paste does, and lands in NORMAL. In V-LINE the text goes on a line of its own. It is one undo change, writes no register and leaves `dot`.
- `I` enters INSERT at the start of the anchor's line when the cursor end is past it, and at the cursor end otherwise. `A` enters INSERT after the cursor end's letter when the cursor end is past the start of the anchor's line, and after the anchor's letter otherwise. A count types the text that many times. The stay records `Command.InsertAsSelected`, so `.` inserts at the cursor or after it with the stay's own count, and a count before that `.` is ignored, as in Vim.
- `Pick` runs the object's `pick` on both ends and takes the ends and the kind it returns. A selection of one cell picks as NORMAL's object does. A longer one grows: a word object adds the next word, toward the cursor end; a paragraph object adds paragraphs; a quote object works within one line; a bracket object that would not grow takes the block around it. From a selection on one line `ip` and `ap` make whole lines. From one that spans lines they move the cursor end and keep the kind, as Vim's `current_par` does, so `vjip` stays VISUAL. The word, quote and bracket objects make letters, and an object that fails leaves the selection (a word object that fails moves the cursor end as Vim does).
- `r` and a letter replaces every letter of the selection, keeps the line breaks and empty lines, and returns to NORMAL with the cursor at the selection's start, at column 1 of the first line in V-LINE (`Operators.replaced`, one `Buffer.rewrite`). A count before `r` is ignored. `r` then Esc cancels and keeps the selection. `r` then Enter over VISUAL or V-LINE does nothing and keeps the selection: Vim puts a CR for every letter, and a note cannot hold one. `.` repeats on the same amount from the cursor (`Command.ReplaceAmount` with the selection's `Amount`), and `gv` selects the same place again. A visual `r` adds at most 4,000,000 units: it replaces as many lines from the top as fit (`rowsWithin`), and when the first line alone would pass that, nothing.
- `.` after a VISUAL `d x X D`, `c s C S R` or a put repeats on the same amount of text from the cursor, as Vim does. `dot` holds `Command.OperateAmount` with the operator and a `Selection.Amount`, measured when the operator ran (`amountOf`): `Lines` (a count of whole lines), `Width` (on one line, screen columns, so a tab counts its columns and a wide letter two), `Through` (several lines: the count, and the screen column of the last letter) and `ToLineEnd` (the end was set by `$`). `rangeFrom` builds the range from the cursor and cuts it short where the note is short. The dot of a put only deletes that amount, as in Vim. A count before the `.` is ignored. A VISUAL `y` leaves `dot`.
- `gv` in NORMAL brings back `Vim.last`: the kind, a `Selection.Mark` for each end (the line's id, its number and a column) and the column `j` and `k` kept. A mark follows its line by id through later edits. An operator moves the marks itself to where Vim leaves them (`movedBy`): after a put they span the text put, and after a put of nothing both sit where the delete began, on a letter. When the operator took out the line an end was on, the mark also keeps that end as it was (`removed`), and while that line is in the note again, as after `u`, `gv` selects from there (`broughtBack`): `ggVdugvd` deletes the first line again. Each end lands on the start of a cell (`marked`), so an edit that joined letters under a mark cannot leave an end inside a letter. A mark on a line past the end of the note never comes back, so `gv` then does nothing. `last` is dropped when the note is shown again from the store, and with vim off.
- The screen column `j` and `k` keep follows Vim's cursor column. `v` and `V` keep NORMAL's column. A cursor on a tab is in the tab's last column in NORMAL and, in VISUAL, in its first column while the cursor end is at or before the anchor. `column` says which holds: `AsInNormal` until the cursor end moves, since Vim works the column out when the cursor moves, and `AsInVisual` after. A motion that leaves the cursor where it is, such as `0` in the first column, reads the column the same way (`Selection.wantOf`). `o` on one cell, Esc, `y` and an object that fails read the column from it (`Selection.columnOf`). Esc and `y` then keep that column in NORMAL when the cursor did not move, and leaving with `v` or `V` keeps the column VISUAL had.
- A click, Ctrl-E, Ctrl-P, the vim toggle, opening another note and a change to the note from another tab leave VISUAL with nothing selected, and the editor comes back in NORMAL. IME text and longer typed text change nothing. Page Up and Page Down take the plain path and move the cursor end.
- Drawing. `Editor.paint` returns `Frame.selection` (`kind`, `from`, `to` and whether the last line break is in it), which costs the same for one letter and for 120,000 lines. `.surface` carries it as `data-selected`, and holds a `#selection` element with `data-kind` (`letters`, `lines` or `block`) only while there is a selection. After each patch `draw` in `src/surface.ts` reads the rects of the selected text on the drawn lines within one screen above and below the view, one `Range` for each line, then the caret's rect and the surface's scroll, and only then writes the boxes and the caret, so a key lays out twice in every mode (a write between the reads cost VISUAL two more layouts a key, and NORMAL one). The boxes are absolutely placed `div`s kept in a pool. Rects on one row join only where they touch (`joinedWhereTouching`), so in a line of mixed direction, where a selection is several runs on screen, no box covers a letter outside it, and a row holds at most a box for each run. A line whose selected letters all have no width, such as a ZWNJ, gets one box 2 px wide. A selected line break is a box one cell wide, marked `data-break`, so an empty line shows one cell. `lineBreakBox` places it: after the line's last letter, on that letter's row, and no further right than the view's edge, so the cell of an exactly full row is in the right padding and the cell after spaces that hang past a wrap stays in view. In VISUAL the caret on a line break takes the same box, so the cursor is a block on the highlight's cell. NORMAL, INSERT and vim off place the caret as before. A scroll of more than half a screen draws the boxes again. The cursor block is drawn over the boxes.
- Chrome snaps each box to CSS pixels and then scales, so at 125% and 175% two boxes that meet inside a device pixel each cover half of it and the page shows through. Each box carries a 2 px strip over its bottom edge, as wide as it shares with the boxes of the row below (`withSeams`, `--seam-left` and `--seam-width`), and a box of letters runs 1 px under the line-break box at its right. In forced colours the boxes are the system `Highlight` mixed with `Canvas`, since the letters over them keep the text colour, and `.line` takes `forced-color-adjust: preserve-parent-color`: Chrome otherwise paints a plate of the page colour behind forced-colour text, over a highlight drawn under the letters.
- A test may read `#selection` (present only while there is a selection), its `data-kind`, and the union of the client rects of its boxes. The fixture's `nullpad.selection()` returns the selected text as drawn: the letters whose centre a box covers, and `\n` for each line-break box, so every line of a `V` selection ends in `\n` and `v$` ends in one. A letter with no width is read as selected when a box holds its place, so one that touches the highlight from outside is read too. On the note's last line the highlight and `selection()` show a line-break cell that an operator does not take, since no line break is there (Vim draws that cell too). It reads only the lines drawn near the screen, and returns `''` when nothing is selected. An `expect` step of `e2e/steps.ts` takes it as `selection`.
- The comparison with Vim: `verify-out/vc/harness.py` generates about 13,800 rows for each seed from VISUAL keys mixed with motions, objects, operators, puts, registers, counts, `.`, `u`, Ctrl-R, `gv`, `o` and kind switches, over seven notes with tabs, wide letters, emoji, blank lines, brackets and quotes. It feeds Vim the keys one command at a time and has Vim work out the cursor's screen column between commands (a key mapped to `<Cmd>call wincol()<CR>`), as Vim does when it draws the screen for a person. Run with `-es` and no screen, Vim works the column out late, in whatever mode it is in by then, and a cursor on a tab reads another column. A row in which Vim reports an error is not counted, because Vim throws away the keys typed after it (E353, a put from an empty register). Of three seeds, 35,459 rows counted, about 310 a seed differ and each is one of the accepted differences below or of NORMAL's.
- Accepted differences from Vim in VISUAL:
  - A count before `v` or `V` is ignored, so `3v` is `v` (Vim selects the size of the last selection, three times).
  - `gv` in VISUAL does nothing (Vim swaps to the selection before).
  - `gv` after `u` or Ctrl-R brings back an end only when the selection's own operator took out its line and the line is in the note again. Vim keeps the marks with every undo step: an undo past an earlier selection's operator brings back that selection, its kind included, and an undo of a put inside one line brings back the ends from before the put, where ours selects where the marks are now. After a later command took out the line that held an end, `gv` keeps that end's line number (Vim moves the mark to the next line). After an operator on a line with letters outside ASCII the ends keep their letter columns (Vim keeps byte columns). After a `.` repeated a VISUAL `I` or `A`, Vim's `gv` selects whole lines, and ours keeps the kind. After `O` in NORMAL the marks stay on the line `O` opened (Vim moves them down with the text).
  - `A` follows the rule above. Vim's answer differs when the cursor end is not past the start of the anchor's line, after `$`, over several lines with the cursor end in the first screen column, in the `.` after an `A` over several lines or after another operator, and after an earlier operator: there Vim reads a column that the earlier operator left, which looks like a Vim bug.
  - `.` after a `v` operator on one line whose end `$` set takes text to the line end. From the third screen column on, Vim adds the column to its largest number, which overflows, and takes other text.
  - `u`, `U`, `~`, `J`, `>`, `<`, `=` and `:` are not built in VISUAL. `u` and `U` change case there in Vim.
  - No `gn`, no `:'<,'>`, no `'<` and `'>` marks, no select mode, no selection by mouse drag.
  - A paste replaces the selection (Vim has no such key).
  - `r` then Enter over VISUAL or V-LINE does nothing (Vim puts a CR for each letter), and a visual `r` stops at 4,000,000 added units.
  - Ctrl-End keeps the line end as the column for `j` and `k`, in NORMAL too, where Vim keeps the last letter's column: Ctrl-End then `k` from `xyz` up to `abcdef` is on `f`, and on `c` in Vim. So Ctrl-End, an `l` that cannot move and then `k` goes to the line end.
  - What NORMAL already differs in holds here: `d` or `c` on a note that is one empty line, a `u` after a command that changed nothing, puts above the bounds, and emoji, flags and accented letters as one letter each.
- In Node the keys cost what they cost on main (microseconds a key, the least and the median of 21 samples, main then this build): one `x` after 10,000 held keys of an INSERT stay 3.62 and 4.66, then 3.27 and 4.69; after 100,000 held keys 2.92 and 4.58, then 3.12 and 4.26; `l` or `h` in NORMAL on 40 lines 4.92 and 5.91, then 4.58 and 5.69, and on 120,000 lines 5.34 and 7.02, then 5.03 and 6.24. In VISUAL `l` or `h` costs 4.16 and 5.15 on 40 lines and 4.13 and 5.37 with all of 120,000 lines selected, and `j` or `k` in V-LINE with 120,000 lines selected 4.57 and 5.64. No key copies or checks anything that grows with the selection.

### Block

Ctrl-V in NORMAL selects a block: on every line from one corner's line to the other's, the letters between the corners' screen columns. The mode reads `V-BLOCK`. Ctrl-V in V-BLOCK leaves, `v` and `V` switch the kind and keep both ends, and Ctrl-V in VISUAL or V-LINE makes the selection a block.

- The key. Chrome turns Ctrl-V into a paste, and a keydown the page cancels makes no paste for INSERT. So `keyboard.ts` lets the paste event come and says how it came: `Paste` carries `byKey`, true when the event arrives while Ctrl-V is held with no other modifier. In NORMAL and VISUAL a `Paste` with `byKey` is the key `<C-v>` and its text is dropped. With vim off, in INSERT, in the finder and in the read view it pastes. Ctrl-Shift-V, Paste in the browser's menu and Cmd-V on a Mac make a `Paste` without `byKey`, which pastes in every mode. On a Mac Ctrl-V makes no paste event, so `keyboard.ts` sends its keydown as a `Chord` there (`controlVPastes`), and the keymap reads both as `<C-v>`. The fixture's `paste` presses Ctrl-V while the mode reads EDIT and Ctrl-Shift-V in every other mode, INSERT included: the status reads INSERT for a frame while a `.` replays a recorded Delete, and a Ctrl-V picked from that reading landed in NORMAL and started a block. A test of Ctrl-V in INSERT presses the key itself.
- The shape. `Selection.endsOf` gives `Ends`, a `Stretch` (`Letters` or `Lines`) or `Corners` (`Block`), and `Selection.byShape` is the match every reader goes through, so a command that reads a selection says what it does with a block. `blockOf` turns the corners into a `Block`: `first` and `last` (lines), `left` and `right` (screen columns, both in the block) and `toLineEnds`. `left` is the least first column of the two corners' letters and `right` the greatest last column, so a corner on a tab or a wide letter widens the block to all of it. After `$` the column `j` and `k` keep is `End`, and the block runs to the end of each line (`toLineEnds`, with `right` the widest line's width) until a key sets another column, such as `h`, `o` or `O`.
- `cutOf` cuts one line by a block as Vim's `block_prep` does: where the block starts and ends in the line, the letter each edge cuts in two (`CutLetter`) and the row a yank takes. A cut tab or wide letter counts as spaces: a yank takes its columns inside the block as spaces, and a delete leaves its columns outside as spaces. A line that ends before the left edge gives a row of spaces as wide as the block and loses nothing.
- Every VISUAL motion and count moves the cursor corner. `o` goes to the other corner, and `O` to the other corner of the same line (`otherColumns`). `iw aw iW aW` and the quote objects keep the block. A bracket object makes VISUAL. `ip` and `ap` make V-LINE from a block on one line, and from a block that spans lines they move the cursor corner and keep the block, so `<C-v>jlip` stays V-BLOCK. Each is Vim's answer.
- `blockOperators` holds the operators. `d x X` and Delete remove the block and `y Y` yank it. `D` and `C` take it to the end of each line. `c s` change it. `S` and `R` change its whole lines, as in V-LINE. The cursor lands on the block's top left. After `y` the column `j` and `k` keep is Vim's (`wantAfterYank`): when the cursor corner was on a tab at the block's top left and a letter starts at the block's right column on its last line, it is the right column, because Vim keeps the column it worked out for the other corner. Every line changes in one `Buffer.rewrite`, which copies the lines array once and keeps each line's id, so the history's change is the block's lines. A block delete of one empty line writes no register, as in Vim.
- A `Register` has a third case, `Blockwise`: `text`, the rows joined by line feeds, and `width`, which Vim shows as `^V2`. A block yank or delete writes one. `"A` onto a blockwise letter adds the new rows under the old and keeps the old width, a block added to letters makes letters, and a block and whole lines in either order make whole lines. `"+y` of a block writes its rows to the clipboard joined by line feeds, and read back they are letters, since a read from the clipboard never makes a block.
- `p` and `P` in NORMAL put a blockwise register as a rectangle (`putRows`): `P` at the cursor's column and `p` after the cursor's letter, one row a line going down. A short line is padded with spaces up to the column, a row is padded to the width only where text follows it, a tab the column falls in becomes spaces, and rows past the last line make new lines. A count puts the copies side by side, at most 50,000 UTF-16 units wide and 4,000,000 in all. The cursor lands on the first letter put.
- The bound of a block command counts every unit it adds, the spaces it pads with included, before any text is built. A block put, over a selection too, lowers its count until the rows, their copies and the padding fit in 4,000,000 units (`copiesWithin`), then puts as many rows from the top as fit (`rowsWithin`), and always the first. Letters put down a block do the same with the block's lines. A stay's copies go onto as many lines from the top as keep the text they add within 4,000,000 units. The first line of an `A` is padded as before, since its padding is no wider than a line the note held. Without the bound one key built a note the save could not join, and the app crashed 800 ms later with `Invalid string length`: `gg$p` of a 19,999-row block beside a line of 49,000 letters padded every row to column 49,000 (980,000,000 units), `A` at that column the same, and a counted `I` down 120,000 lines made 2,400,000,000.
- `p` and `P` over a block (`putOverBlock`) delete it and then put: letters of one line on every line of the block that has a letter starting at that column or ends there (`lettersDown`), longer letters once at the top left, whole lines above the block's first line for `P` and below the cursor corner's line for `p`, and a block as a rectangle at the top left. A blockwise register over `v` goes in as a rectangle at the selection's start, and over `V` as lines.
- `I`, `A` and `c` enter INSERT on the block's first line: `I` at the left edge, `A` after the right edge, after padding a short line with spaces, or at the line's end after `$`, and `c` where the deleted block was. `Mode.Insert` then holds `block`, a `BlockStay`: the rule (`Insert`, `Append` or `Change`), the block, and what the first line held (`Held`). The stay types on the first line by the plain path, as any stay does. At Esc `Operators.gained` reads the text the first line gained and `copiedDown` writes it to the other lines in one `Buffer.rewrite`. `I` and `c` skip a line that ends before the left edge, `A` pads a short line to the right edge, and an edge that cuts a tab makes the tab spaces around the text. A stay that added or took out a line, an `I` or `A` whose Esc is on another line, and a stay that gained nothing copy nothing. A `c` copies with the cursor on any line, as Vim's `op_change` does. The stay also holds `seen`, the lines array its own last input left. `tracked` in `editor.ts`, which every queued input, click and replayed step passes, moves `seen` on with `Vim.passed`, and only from the lines the stay held. Text that changes any other way leaves `seen` behind, and a stay whose `seen` is not the buffer's lines copies nothing and leaves the cursor where a plain Esc leaves it: another tab's change, a conflict copy, a removal, and a task box clicked in the read view (`Editor.overwrite`). Without it the Esc after another tab's save copied that tab's text into the lines below. A click or an arrow to another line and back, typing there included, still copies, as in Vim. A count types the text that many times before the copy. The stay and its copies are one undo change.
- `gained` is a port of Vim's `op_insert` and `op_change`, which do not look at what was typed. They compare the first line's length with the length it had (`Held.kept`, Vim's `pre_textlen`) and take that many letters at the block's edge. So a Delete, which shortens the line, makes the stay copy fewer letters or none: `<C-v>jjIxy<Left><Del><Esc>` copies `x`. Reading the gain as the new length less the old, with no floor, copied leftover letters down after a Delete.
  - Vim moves the edge to where the insert last started. `BlockStay.run` keeps what Vim's INSERT keeps: `at` (`Insstart`), `origin` (`Insstart_orig`), `hasMoved` (`arrow_used`), `originFollows` (`update_Insstart_orig`) and `isUntouched` (`ins_need_undo`). `Operators.runAfter` moves them on from `Vim.passed`, at every input of the stay: a move that changes no text sets `hasMoved`, the next change of text starts a new insert at the caret, a Backspace before the origin takes the origin back, and a Backspace that joins the insert's line to the line above moves the insert there.
  - `turnedBy` then turns the edge as `op_insert` does with `b_op_start_orig`. An `I` whose origin moved copies at the origin's column. An `A` whose insert started at or before the origin copies as an `I` there. So `<C-v>jjIxy<Left>z<Esc>` copies `xzy`, and `l<C-v>jlI<BS> y<Esc>`, whose Backspace took a letter before the block, copies nothing.
  - After `$A` the text is read from as far before the line end as the insert started (Vim's `offset`). A first line whose indent grew moves the edge with it (`Held.indent`). The cursor lands on the turned edge's column (`Copy.column`, Vim's `oap->start.col`).
  - Vim's answers here are the ones it gives keys typed one after another: on a pty, through `feedkeys(keys, 'xt')` in one piece and through `:normal`. A `<Cmd>` mapping run between the keys of a stay sets `ins_need_undo` (`K_COMMAND` in `edit.c`), and Vim then answers otherwise in 10 of 25 rows, so the comparison settles Vim's column only between commands, never inside a stay.
- `.` repeats a block's operator, `I` or `A` on the same number of lines and columns from the cursor (`Command.OperateBlock` and `Command.InsertInBlock` hold a `Selection.BlockAmount`, and `blockFrom` builds the block). After `$` in NORMAL the repeat runs to the line ends, as in Vim. `gv` brings a block back with its corners.
- `r` and a letter over a block replaces its screen columns, as Vim's `op_replace` does (`Operators.blockReplaced`, one `Buffer.rewrite`): a letter fills each line's columns inside the block, so a wide letter fully inside becomes two letters, and a wide letter put fills half as many columns with a space after an odd one unless the line ends there. A tab or wide letter an edge cuts keeps its columns outside the block as spaces. A short line is replaced to its end, a line that ends before the block stays as it is, and after `$` the block runs to each line's end. The cursor lands on the top left. `r` then Enter splits each line the block reaches once (`Buffer.split`, which keeps the head's id and gives the tail a new one): the head keeps the spaces of a cut letter's outside left columns, and the tail starts after the block. Vim then moves the marks of later lines one line down for each split above them, counted from the line after the next (its `appended_lines_mark` is off by one), and `gv` follows it (`lineAfterSplits`). `.` repeats on a block of the same size from the cursor (`Command.ReplaceBlock`), and a block `r` stops at 4,000,000 added units as a visual one does.
- A paste in V-BLOCK erases the block into no register, pastes the text once at the block's top left and lands in NORMAL, as one undo change.
- Drawing. For a block `Frame.selection` holds `spans`, one `line`, `from` and `to` for each drawn line of the block (`spansOf` reads only the lines `Editor.paint` draws, so a block down 120,000 lines costs what a block down a screen costs). `.surface` carries them in `data-selected` after `block:`. The boxes come from Range rects as for the other kinds, so a letter an edge cuts is highlighted whole and the right edge is ragged beside wide letters. A block has no line-break box. A line the block does not reach holds a box of no width, which shows nothing and lets a test count the line.
- A test may read `#selection[data-kind=block]`. For a block `nullpad.selection()` returns the letters covered on each drawn line of the block, joined by `\n`, with an empty string for a line the block does not reach: `ab\n\nab` is a block two columns wide over three lines whose middle line is short.

### Jump

`s` in NORMAL, in the three visual kinds and after `d`, `c` or `y` starts a jump, as flash.nvim does: type letters of a place on screen, then the label drawn beside it. `S` still changes the line.

- The state is `Editor.asking`, `Option<Asking>`, a `Prompt` (the search and command line) or a `Jump` (`Vim.Jumping`: the `Jump` of `src/core/vim/jump.ts`, the operator and the register). One field holds both, so a prompt and a jump are never open at once, and every path that closes a prompt ends a jump: a click, the vim toggle, opening another note and a change from another tab. `inputPlan` feeds an open jump before the keymap (`jumpPlan`).
- The `s` rows are `Command.OpenJump` (NORMAL and after an operator key) and `VisualCommand.OpenJump`. Their step has the fate `OpenJump`, and the editor asks the layout with `Query.Screen` before the jump opens. `screenAnswer` in `src/surface.ts` first brings the cursor's row on screen, then hit-tests the top and bottom rows of the view and answers `Landing.Screen`: the first and last letter on screen. Keys typed meanwhile queue behind the answer, so no key is read before the jump knows its screen. `.status .pending` reads the keys before `s` for that one frame. With no surface (a Node script) the region is the whole lines from `topLine` for `screenRows` lines.
- The region is fixed for the whole jump. A scroll or a resize changes no match and no label, and a label whose line is no longer drawn still jumps.
- `find` scans only the region, a line at a time with `indexOf`, and keeps a match that starts and ends on a letter edge (`isCellEdge` in `cells.ts`). A pattern with no upper-case letter matches any case: the text is folded one code point at a time, and a code point whose lower case has another length keeps its case, so columns hold. Matches may overlap. The match that starts at the cursor is highlighted and has no label.
- Labels are `asdfghjklqwertyuiopzxcvbnm` and then the same in upper case, 52 at most, nearest first: lines away, then letters away on the line, then a match after the cursor before one before it. A letter is no label when it is the single ASCII letter after some match (both cases when the pattern has no upper-case letter), so a typed letter is never both a label and more of the pattern. A lower-case label stays on its match while the pattern grows (`labelled` takes the labels shown as `held`), so labels are not handed out again from `a` after each letter.
- Keys (`feed`): text and IME text extend the pattern, or land when the text is a label shown. Backspace takes a letter back and on an empty pattern keeps waiting. Enter lands on the first match after the cursor, or the first on screen, and ends the jump on an empty pattern or when the only match is the cursor's. A pattern with no match ends the jump and that key does nothing more. Esc, Tab, a paste, any chord and any other named key end it. Ctrl-E and Ctrl-P end it and then run. A count before `s` is dropped. `.status .pending` reads `s`, `sfo` or `dsfo`.
- Landing (`Vim.jumped`). NORMAL moves the cursor to the match's first letter and sets the column `j` and `k` keep from it. It is no undo step and writes no register. VISUAL moves the cursor end and keeps the anchor. An operator takes `Targets.rangeToJump`: letters, inclusive at both ends in either direction, and never whole lines, as Vim's forced `v` (`dv/`). It runs through `operate` with nothing recorded, so `.` keeps what it repeated before, and `cs` starts a stay that `.` does not repeat. The register typed before the operator is the operator's.
- Drawing. `Frame.jump` holds `Marks` for the drawn lines: the matches and, for each label, its letter, where it jumps and the cell after the match (`over`, empty at a line end). `.surface` takes the class `jumping`, which dims `.line` to `--jump-dim`, and `data-jump-matches`. `markMatches` registers the matches as `StaticRange`s in the CSS highlight `jump-match`, which reads no layout and follows wraps and scrolls, and `::highlight(jump-match)` gives the letters back their colour on `--jump-match`. `#jump`, after `.sheet` and under `#caret`, holds one box for each label, placed from `cellBox`, the box the cursor would draw on that cell: a wide letter whole, a tab one cell, the line-break box at a line end. `draw` reads the label boxes in its one read pass and writes them in its write pass. The highlight is removed when the jump ends.
- A test may read `.surface.jumping`, `.surface[data-jump-matches]` (`line,from,to;` for each match, 0-based, UTF-16, half open), and `#jump > [data-label]` with `data-line` and `data-column` (where it jumps), `data-from` and `data-to` (the cell it covers) and its client rect. The fixture's `jumpLabels()`, `jumpMatches()` and `isJumping()` read them.
- `operate` after a jump was compared with Vim's `dv/\%Ll\%Cc<CR>`, `cv` and `yv`, forward and backward, over 699 cases with empty and indented lines and ranges of several lines: none differs.
- Speed. In Node `find`, `labelled` and `marks` over 3,000 matches on screen take 1.5 ms, and on 120,000 lines `s` costs the core 0.22 ms and a pattern letter 0.6 ms. In headless Chromium at 1000x600 `s` and each pattern letter reach the next frame in 33 ms (the two frames the measure waits) on 120,000 lines, and in 26 to 41 ms with about 2,000 matches on screen. On two lines of 50,000 letters with about 990 matches on screen a pattern letter takes 63 to 134 ms: Chrome spends about 0.1 ms registering each highlight range in a text node that long. A `j` held at 30 Hz in NORMAL makes no long task on any of the three.
- Accepted differences. From Vim: `s` no longer substitutes (`cl` does), in VISUAL too (`c` does). From flash.nvim: no labels on `f t F T`, no treesitter or remote jumps, no toggle from `/`, no fuzzy mode and no autojump on one match; an operator's range is inclusive at both ends; a jump under an operator is not what `.` repeats; only the letters on screen when `s` was pressed are searched; Tab ends the jump, so a pattern holds no tab.

## Undo

With vim off Ctrl-Z undoes and Ctrl-Shift-Z or Ctrl-Y redo (Cmd on a Mac). With vim on `u` undoes and Ctrl-R redoes in NORMAL, each with a count. Both read one history, `Editor.history`, so a change made in one mode undoes in the other.

- `src/core/history.ts` holds `past` (newest last), `future` (the next redo last), `base`, `open` and `units`. A `Change` is `at`, the Line records it `removed` and the ones it `added`, the cursor `before` the change and the caret `after` it. A change is found when its group closes: the lines between the longest shared prefix and suffix of `base` and the lines now, compared by identity, since every `Buffer` edit copies only the lines it touches. Undo puts the removed Line records back with `Buffer.spliceAll`, so ids, joins and the drawn rows' keys return, and undoing to the start gives the note exactly as it was opened. `nextLineId` never goes back.
- A change whose removed and added lines have the same texts and joins, such as a cancelled IME composition (its empty commit copies the caret's line), is not recorded and keeps the redo list. Only an INSERT stay is recorded even then, since Vim spends a `u` on `ixy<BS><BS><Esc>`.
- `base` is the lines the newest change left. When the lines differ from `base` and no group is open, some path changed the text without the history, and `record` makes that a change of its own, so a missed path costs a boundary, never a wrong splice.
- Every text change passes one choke point: `planOf` wraps each plan's outcome, and a layout answer's `land`, in `tracked`, and `overwrite` (the task box) calls `recorded`. An undo or redo changes the history itself, and the steps of a replay (`.`, a counted insert) each record themselves, so such a plan says `recordsItself` and `planOf` records nothing for it. `groupingOf` is the one table of boundaries, and each grouping names the kinds of open group it joins (`joinsOnto`) and whether its group stays open after it (`staysOpen`): an input in INSERT, or one that enters or leaves it, is `InsertStay` and joins the stay it is in; a step in NORMAL, a toggle and a click with vim off are `Command`, alone; with vim off a letter, a space or Tab is `Typing`, Enter is `Typing` that starts a new group, Backspace is `Backward`, Delete is `Forward`, `Erase` is `Replace`, which a following letter or composition joins, so an autocorrect's Erase and the text that replaces it are one change, `Preedit` is `Compose` and `Commit` closes the composition's group, and a paste is alone. A group continues only while each input joins its kind, so a move, a click, a change of kind, Enter and a paste end a typing change, with no time limit. A group opens at the first input that changes a line, so `i<Esc>` is no change and `o<Esc>` is one. One `.` and one counted insert are one change with no rule of their own: a replayed delete or put is a `Command`, and a replayed stay is an `InsertStay` that stays open through its copies until `Leave`.
- The cursor after `u` and Ctrl-R follows Vim's `u_undoredo`. Each change keeps where it began: for an operator `Vim.Step.began` (the range's start; for a one-line `dd`, `cc` or `S` the earlier of the cursor and the first non-blank; for a linewise change of several lines the line below the range's start), and otherwise the caret before the first changed line, so after `a` or `A` it is the caret after the placement. When that line is from the line above the changed lines to the line below them, the cursor goes there with that column, and otherwise to the first line whose text changed, at its first non-blank. Past the last line it is the last line's first non-blank. `rest` then clamps the column. With vim off, undo puts the caret where the change began and redo where it ended. The reveal is `Nearest`, so the cursor's line is on screen.
- The history keeps at most 1,000 changes (`maxChanges`, Vim's `undolevels`) and 64,000,000 units (`maxUnits`), a unit being one UTF-16 unit of a removed or added line plus 32 for each line. Past either bound the oldest changes drop. The newest change always stays, however large, so one `u` after `ggdG` brings back a note of any size. In headless Chromium a change of a fresh 120,000-line set costs about 1.03 bytes a unit (20 MB per `dG`, `P`, `Gdd` cycle on 120,000 lines of 49 letters), so the bound holds the history near 72 MB; 1,000 one-line changes cost 1.4 MB.
- `reopen` builds on `open`, so opening a note from the finder, coming back to one, another tab's change, a conflict copy and boot all start an empty history. A move from another tab keeps the text and the history. Undo and redo change `buffer.lines`, so the shell saves them as typing; a note that `ggdG` emptied and its save removed comes back with `u` and is saved anew.
- On a 120,000-line note in headless Chromium, `u` after `x` and after `dG` each take about 34 to 40 ms to the next frame (two frames), Ctrl-R of the `dG` 34 ms, Ctrl-Z after 200 typed letters 73 ms, and `x` or `u` held at 30 Hz makes no long task. `1000u` after 1,000 one-line changes takes 34 ms and `1000` Ctrl-R 38 ms (2.1 s and 1.3 s when each step copied the lines array): a counted undo or redo copies the lines once and splices each change into that copy. A typed letter costs the core 0.46 ms on that note before and after the history.
- Accepted differences from Vim: no `U`, no undo tree (`g-`, `g+`, `:undo N`) and no `Ctrl-G u`; arrows, Home, End, a click, a paste and IME text in INSERT stay in the stay's change (Vim splits at a move); Ctrl-Z, Ctrl-Shift-Z and Ctrl-Y do nothing in NORMAL and INSERT; a task-box click during an INSERT stay splits that stay's change; after `u` or Ctrl-R onto a line with letters outside ASCII the cursor keeps its letter column, where Vim keeps a byte column; a command that changes nothing, such as `x` on an empty line, `X` at a line start or `cc<Esc>` on an empty line, is no change, where Vim records an empty one that a `u` then spends; emoji and accented letters are one letter each.
- Feed Vim the keys of an undo row with `feedkeys(keys, 'xt')` and `--cmd 'set backspace=indent,eol,start'`. Keys read with `vim -s` merge undo steps (`xxx2u` undoes all three), and an empty `backspace` keeps INSERT's Backspace from deleting text typed before the stay.

## Markdown

The parser is written for nullpad, uses no library and follows CommonMark 0.31.2. It reads a note's lines and returns a tree in which every node knows its place in the note. The read view draws the tree. The default screen is the editor.

- `src/core/markdown.ts` is the whole public surface: `parse(lines)`, `toHtml(document)`, `outline(document)`, `positionOf(placed, point)` and the tree's types. The parts live under `src/core/markdown/`.
- A `Document` holds `lines`, `sections` and `definitions`. A section is one top-level block and the blank lines after it, so it holds whole lines. A place in a section is a `Point`: `lineInSection` and a UTF-16 `column`. `positionOf` is the one function that adds the section's first line. Every node has a half-open `span`. A paragraph or a heading keeps one slice per line.
- `parse` makes two passes. The block pass in `blocks.ts` folds over the lines with an immutable state and returns the sections. The inline pass in `inlines.ts` then reads each paragraph and heading: tokens, a delimiter stack for emphasis in `emphasis.ts`, and a bracket stack for links. A link reference definition is a block in the tree, and `toHtml` leaves it out.
- The parser has no `for`, no `while` and no `let`. A walk whose length follows the note is a fold or a regex, and no regex nests one quantifier in another. Recursion stops at `deepestNesting`, so parsing time grows in line with the note.
- `deepestNesting` is 100. It counts the levels of the tree: a block quote, a list and a list item are one level each, and so are emphasis, strong emphasis, a link and an image. A marker that would open level 101 stays text.
- `toHtml` writes the HTML of the spec's examples, character for character. nullpad draws that string as text and never puts it in the page as markup.
- `/?pane=html` and `/?pane=outline` draw `Editor.html` or `Editor.outline` as text in a `<pre class="pane">` under the editor. The `flags` Effect in `src/main.ts` reads the flag once at boot into the Model. The pane is there for tests. Without the flag the page has no pane, and the parser runs only when the read view opens.

### Outline

`outline` prints one row per node, in the order of the note. A line feed ends every row but the last.

```
<two spaces per level><tag> <line>:<column>-<line>:<column>[ <JSON string>]
```

```
Paragraph 3:0-4:12
  Text 3:0-3:4 "see "
  Emphasis 3:4-3:10
    Text 3:5-3:9 "this"
  SoftBreak 3:10-3:10
  Link 4:0-4:12 "/url"
    Text 4:1-4:5 "here"
```

- A top-level block has no indent. A child is one level under its parent.
- The tag is the node's `_tag`. A block is a `Paragraph`, `Heading`, `ThematicBreak`, `CodeBlock`, `HtmlBlock`, `Definition`, `Quote`, `List` or `Item`. An inline is a `Text`, `Escape`, `Entity`, `SoftBreak`, `HardBreak`, `Code`, `Emphasis`, `Strong`, `Link`, `Image`, `Autolink` or `Html`.
- The two places are the node's `span`, and the end is half open. The line is the note's line number as the gutter shows it, counted from 1. The column is a UTF-16 offset into that line, counted from 0.
- A `Text`, `Escape`, `Entity`, `Code`, `Html`, `Autolink`, `CodeBlock` or `HtmlBlock` shows its text as a JSON string. A `Link`, `Image` or `Definition` shows its destination. No other node shows a string.
- A JSON string holds no raw line feed, and the tag and the places hold no space. So the pane splits into rows at line feeds, and a row without its indent splits into tag, places and string at its first two spaces.

### Differences from commonmark.js

`commonmark@0.31.2` is the reference parser, a dev dependency that tests may call and `src` never imports. These are the known differences in the HTML.

- The nesting limit. commonmark.js nests without a limit. This is the one difference we chose.
- Emoji and other punctuation or symbols outside the Basic Multilingual Plane count as punctuation next to `*` and `_`, as sections 2.1 and 6.2 of the spec say. commonmark.js reads one UTF-16 unit there and takes them for letters.
- A paragraph and a heading lose only spaces and tabs at their ends, as sections 4.2 and 4.8 say. commonmark.js also takes off a form feed, a no-break space and other Unicode whitespace.
- `&#128;` to `&#159;` are the characters U+0080 to U+009F, as section 2.5 says. commonmark.js reads them as Windows-1252.
- A space written as `&#32;` before a line ending stays. commonmark.js drops it as it drops a typed space.
- The first definition of a label in the note wins, as section 4.7 says. In commonmark.js a later definition wins when it opens a paragraph that becomes a setext heading.
- A paragraph that holds only definitions and ends at a `---` line leaves no paragraph. commonmark.js leaves `<p></p>`.

## Testing

The only tests are end-to-end tests: Playwright Test drives the production build in headless Chromium with trusted input, the way a person types, clicks and scrolls. Write no unit tests and no Foldkit story or scene tests, and ignore the Testing section of `FOLDKIT.md`.

A test reads only the screen: the drawn rows (`[data-line-id]`, `[data-start]`, `[data-n]`, with `[data-ghost]` spans left out as not text), the drawn cursor `#caret`, the drawn selection (`#selection`, its `data-kind` and its boxes), the status line's `line:column NL`, its mode (`.status .mode`), pending vim keys (`.status .pending`), notice (`.status .notice`) and vim button (`.status .toggle-vim`), a jump's marks (`.surface.jumping`, `data-jump-matches`, `#jump`), the text of the pane (`.pane`) on a page opened with `/?pane=html` or `/?pane=outline`, and pixels from a screenshot. It never reads app state or a window global of the app. `burst` is the one exception: it sets `nullpadBurst` on the test page's own window, a record of the events it saw, and reads it back to check the burst landed as sent. It sends input only through `page.keyboard`, `page.mouse` and CDP `Input.*` (paste, IME, raw key events). A test may listen for an event on `window` to see what the browser was left to do, such as whether a keydown was cancelled. A test may stall the page's main thread so that Chrome queues the input sent meanwhile and dispatches it after the long task, as `burst` does. A test may add an element outside the app, such as an `<input>` that takes the keyboard, to stand for the rest of a page. The system clipboard is outside the app too: a test may grant or deny the clipboard permission on its browser context (`allowClipboard`), and read or write the clipboard from a second page to see what another app would (`outside`). Headless Chromium shows no permission prompt and refuses at once, so a test that needs a read to stay open holds the page's `navigator.clipboard.readText` (`holdClipboardReads`), the one browser function a test replaces.

nullpad keeps notes across reloads, so a test that loads the page again in the same browser context does it with `openFresh(page)` from `e2e/nullpad.ts`. It leaves the page, then clears the notes database and the localStorage drafts the leaving page wrote, as a fresh browser profile would. A plain reload brings the last note back, unsaved text included.

A bug fix starts with a scenario that fails on the bug. Run it on the broken build, see it fail, fix the code, see it pass.

### Run

```sh
pnpm test:e2e                       # builds, then runs the push gate: scenarios, named scripts and the every-push sweeps
pnpm test:all                       # builds, then runs everything, on demand only
pnpm test:e2e -g "huge wheel"       # tests whose name matches
pnpm test:e2e --trace on            # keeps a trace of each test; open one with pnpm exec playwright show-trace
NULLPAD_DIST=/path/to/dist pnpm test:e2e   # tests a build made elsewhere, such as an old commit, without building
```

Without `NULLPAD_DIST`, Playwright builds the working tree into `dist/` first, so a run always tests the current source. Traces are off by default. Pass `--trace retain-on-failure` to keep them for failing tests only.

Each pre-push gate run saves the time and outcome of every test to one JSON file in `.git/nullpad-gate-history/`, in the common git dir so that every branch and worktree shares it. `e2e/reporters/gate-history.ts` writes it only when `NULLPAD_GATE_RUN=1`, which the hook sets, so other runs save nothing. `NULLPAD_GATE_HISTORY` names another folder. `pnpm gate:history [--last N]` reads the last 20 runs, or N, and prints the slowest tests, the seconds of each spec file and the tests that failed in some run. A test is flaky when one commit, run from a clean tree, both passed and failed it. A failed write prints one line and leaves the run's status as it was.

Playwright runs one and a half workers for each core (`workers: '150%'` in `playwright.config.ts`). A test spends much of its time waiting for frames, so one worker for each core left about a quarter of the CPU idle. With 8 workers on 4 cores the slowest scenario took 49 of its 60 seconds.

On a machine without Playwright's Chromium, install it once with `pnpm exec playwright install chromium`. Cloud sessions have it at `/opt/pw-browsers` already. The `@playwright/test` version in `package.json` must match that browser's revision.

### Add a scenario

Put it in the spec file of its feature, or a new `e2e/<feature>.spec.ts`. Import `test` and `expect` from `./nullpad` and take the `nullpad` fixture. The test name says what a person sees, and each assertion message names the step. Expected values come from what the feature promises, not from a run of the app.

```ts

  nullpad,
}) => {
  await nullpad.paste('ab\ncd')
  await nullpad.press('Home')
  await nullpad.press('Backspace')
  expect(await nullpad.text()).toBe('abcd')
  expect(await nullpad.status()).toEqual({ line: 1, column: 3, lineCount: 1 })

```

The fixture fails any test whose page logs an error or throws. A known bug that is not fixed yet gets a scenario marked `test.fail(true, 'known bug: ...')`. It passes while the bug stays and fails once the bug is gone, so whoever fixes it removes the mark.

### The Vim oracle

The vim tables hold answers copied from Vim. `pnpm test:oracle` (`e2e/vim-oracle.ts`) plays each row's keys in Vim 9.1, with no browser, and compares the text, the line and column and the mode with the row's saved answer. A row passes when they agree, or when its `differs` names an entry of `vimDifferences` in `e2e/vim-rows/differences.ts` (an accepted difference, with one line on why) and Vim still differs. A run prints each row that differs, with its spec, row, keys, saved answer and Vim's answer, and each row marked `differs` that Vim now agrees with. Either fails the run. It also prints how many rows each difference excused.

- `e2e/vim-rows/all.ts` reads every table into one shape, `OracleRow`: the note, the place, the clipboard, and checkpoints, each a run of keys and the text, cursor and mode after it. A `vim-find` row with `afterP` checks the text after `P` as a second checkpoint, and a `visual-block` row with `readback` checks its readback. A new table gets an adapter there.
- `e2e/vim-rows/confirmed.txt` holds a fingerprint of each row Vim settled, a hash of the note, the place, the clipboard, the checkpoints and `differs`. A run checks only rows whose fingerprint is not there, adds the ones Vim settles and drops those of rows that are gone. Commit it with the rows. `--all` (`pnpm test:oracle --all`) checks every row and writes the file anew. With nothing new a run starts no Vim and takes about 0.2 s.
- Each row runs in its own `vim -u NONE -N -es`, several at once, so no register, `.`, undo, mark or last find carries from one row to the next. The note is a file, so `u` has nothing to undo at the start. The cursor goes to the row's letter with `cursor()`, and `wincol()` settles Vim's screen column before the first key. The keys go in with `feedkeys(keys, 'xt')`, and a `<Cmd>` typed after each checkpoint's keys reads the state. A typed `<Cmd>` survives a command that fails, where a mapped key typed right after a failed `f` can be thrown away.
- Vim runs with `backspace=indent,eol,start`, as nullpad's Backspace deletes before the stay, and Tab in INSERT types two spaces, as nullpad's does. This Vim has no clipboard, so `"+` and `"*` become `"q`, and a row's clipboard text is put in `"q` first.
- Vim's byte column becomes a letter column, graphemes counted as the status line counts them.
- Not checked: the notice a row of `vim-command` asserts (an Ex message is not a key answer), the selection, since this Vim (9.1, patches 1 to 16) has no `getregion()`, and the registers beyond what a put shows. Vim does not settle its screen column between commands, as the comparison harnesses did, and the tables pass without it, but a new row whose cursor rests on a tab or a wide letter can still read another column there.
- On 4 cores `--all` checks the 1,711 rows in about 5 s and 30 new rows take about 0.1 s: each row costs about 14 ms of one core, most of it starting Vim. With the machine busy (load average 15) the same took 26 s and 1 s.

### Robot typist

The typist types a script into nullpad and into a `<textarea>`, each in its own browser context, and compares the text, the cursor (line and grapheme column) and where each line breaks into rows after every step. The textarea is in nullpad's font and exactly as wide as nullpad's text column, so it wraps at the same edge. Rows are compared while nullpad's screen shows the whole text.

A script is a list of steps. A `text` step types one code point, or an ASCII run key by key. An `insert` step puts a whole string in at once, as an IME does. A `key` step presses Left, Right, Up, Down, Home, End, Ctrl+Home, Ctrl+End, Backspace, Delete or Enter. Page Up, Page Down and Tab are left out.

Backspace is judged against a bare EditContext element in a third browser context, not against the textarea. Before each Backspace the typist reads the textarea's own text nodes over the DevTools protocol, because Chrome keeps the halves of a joined line in separate nodes as nullpad keeps a join. The text node before the cursor goes into the EditContext, with the cursor moved to the next grapheme boundary, and the EditContext takes a real Backspace. The textarea takes its own Backspace too. Where the EditContext took more, the rest of that letter is deleted from the textarea as a selection, so the textarea holds the EditContext's result for the comparison and the steps after it. At a line start the textarea joins the lines itself.

Two kinds of script run. Named scripts run on every push. Sweeps run on demand, with `pnpm test:sweep` or `pnpm test:all`.

#### Named scripts

`namedScripts` in `e2e/typist/script.ts` holds every script that once broke, each as its shortest form. `pnpm test:typist` plays them.

#### Sweeps

A sweep covers one class of bugs with a grid of scripts. It plays the same scripts on every run, so a failing row fails again until the bug is fixed. `e2e/typist/sweeps.ts` holds the table and `e2e/sweep.spec.ts` plays it.

A sweep has a `name` that states its rule in plain words, `runs` that says whether it plays on every push or on demand, and these lists.

- `documents`. Each has a name and the steps that build it.
- `placements`. Each has a name, the steps that put the cursor in a document, and its `moves`. A move is a short script, such as one key and then `y`, so the text shows where the cursor stood.

A row is one document, one placement and one move. Its script is the document's steps, the placement's steps and the move, in that order. `scripts` holds the number of rows as a literal. A test fails when the grid has another size, so a grid that shrinks shows as a changed number in the diff.

A row types every step before its last placement step back to back, without comparing. It then compares after that step, where the placement left the cursor, and after each step of the move. A comparison at the end of the row alone would cost about as much: nullpad answers one layout key a frame, so the move's keys take their frames anyway, and a single wait after a burst of them reads a caret that has not landed yet. A row passes when nullpad and the textarea agree each time, or when an accepted difference covers the text. A failing row prints as `document | placement | move | differs after step N of M | nullpad L:C textarea L:C | text same: true`. A row that throws prints `threw:` and the error in place of the step. The rows go round-robin to `TYPIST_SHARDS` shards (8 by default), and each shard prints how many rows it checked, how many differ, and how many differences each accepted difference covered.

The sweeps today:

- Up or Down, any key, Up or Down lands where a textarea lands. Runs on demand. 6 documents (three short lines, a wrapped line of words, a long word that moved to the next row, one word longer than a row, a full row that ends in spaces, and rows of emoji and accents), 7 placements, and 52 moves in each: Up or Down, then any of 13 keys, then Up or Down. 2,184 rows, about 3 minutes on 4 cores.
- Keys sent in one frame leave the screen where the same keys sent slowly leave it: the status line, the line at the top and the cursor's row. Runs on demand, and compares nullpad with itself, not with a textarea, so `e2e/burst-sweep.spec.ts` plays it from `e2e/burst/sweeps.ts` with its own shards (`BURST_SHARDS`, 4 by default). Each row is a document and a list of frames: it plays the frames key by key and reads the screen, opens the note fresh, plays the same frames with `burst` and reads the screen again. The documents are numbered notes of 30, 40 and 200 short lines, 200 lines with every third wrapped, 200 and 3,000 lines with every fourth wrapped over six rows, with vim on and off. The frames are Page keys, arrows, Enter, Backspace, Delete, Ctrl-Z, vim `dd`, `5dd`, `gg`, `x` and `Ctrl+End`, a wheel turn, and a second frame after the first. 19 rows.
- One Backspace, Delete, Left or Right takes what a textarea takes around emoji, flags and accents. Runs on demand, as two sweeps. The documents are twelve pieces (a letter, an accent, two flag letters, a thumbs up, a skin tone, a man, a ZWJ, a heart, a variation selector, a Devanagari letter and a virama) in every ordered pair, and seven fixed documents (two of Hangul, a keycap, a family of three, a family of four and a kiss with skin tones, which are letters of 11 and 15 UTF-16 units, and a flag split by an x). Each move is one key and then `y`.
  - Typed in order: 151 documents, 3 placements (at the end, at the start, one Right from the start). 906 rows.
  - Met at a line join, or typed one in front of the other: 302 documents, the same 3 placements and where the build left the cursor. 3,020 rows.

The second rule has 54 named scripts on every push. Add a row only for a shape the grid does not reach. When a bug turns up, run the sweep on the broken build first and see the new row fail.

1. If the bug fits a sweep's rule, add the document that shows it. If the bug needs a cursor spot or a key the grid lacks, add a placement or a move too. Set `scripts` to the new count.
2. If the bug breaks another rule, add a sweep to `sweeps` with its own name, documents, placements, `scripts` and `runs`.
3. Add the shortest failing script to `namedScripts`. The sweep finds the neighbors of the bug, and the named script keeps the bug itself.

`pnpm test:sweep` plays every sweep alone, the typist sweeps and the burst sweep.

#### Accepted differences

Where a malformed sequence makes Chrome's textarea or EditContext disagree with `Intl.Segmenter`, nullpad follows `Intl.Segmenter`. A mismatch counts as accepted, not failed, only when the text before the step, the textarea's text after it, or the piece a Backspace was judged on holds one of these. A piece that starts at a line join can be malformed where the whole line is not, such as a ZWJ that starts one. nullpad's own text after the step does not count, so a bug that leaves a broken letter behind is not excused. They are listed in `acceptedDifferences` in `e2e/typist/script.ts`:

- ZWJ next to a non-pictograph.
- A mark, ZWJ or skin tone on a flag letter.
- A skin tone after a character that takes none.
- A virama with no letter before it.
- A variation selector not after a pictograph.
- A mark on a space.

Each sweep shard reports how many mismatches each accepted difference covered.

### The nullpad MCP server

`.mcp.json` registers `nullpad`, a stdio MCP server (`node e2e/mcp.ts`). It keeps one headless Chromium open on the build in `dist/`, so a key press answers in about 50 ms, where a `drive.ts` run spends several seconds on a build, a server and a browser first. It is not a test. Use it to explore, then replay its recording with `drive.ts` as the proof.

- **One driver.** The server plays each step with `play` from `e2e/steps.ts` and the fixture's driver, the code that `drive.ts` runs. `type`, `press`, `paste`, `compose`, `commit`, `click`, `wheel`, `resize` and `screenshot` each play one step, and `batch` plays a list. A `burst` step, such as `{"burst": [[{"press": "End"}, {"type": "x"}], [{"type": "y"}]], "stall": 300}`, plays the fixture's `burst` and goes in a `batch`; a wheel turn in it is checked for being held, not for its frame. A new kind of step goes in `e2e/steps.ts`. It gets a row in `tools` in `e2e/mcp.ts` only if it needs a tool of its own.
- **Recording.** The server appends each step that plays to `verify-out/mcp-<time>-<pid>/<n>/steps.json`, and `checkpoint` appends an `expect` of the current screen. `node e2e/drive.ts <that file>` replays the recording on a fresh build. A recording belongs to one page. `reset` and a reload each start the next recording in the next numbered folder, so every recording starts from an empty editor. `reset` takes `steps_file` to write the recording elsewhere. A step that throws and an `expect` that fails are not recorded.
- **Reload.** Every `vite build` ends by writing `dist/build-stamp` (`scripts/build-stamp.ts`), the first 12 hex digits of the SHA-256 of the built `index.html`. Before each tool call the server compares that file with the stamp of the page it has open. If they differ, it opens a fresh page and starts its result with `reloaded:`. A `batch` is one call, so no reload lands inside it. While a build is being written, `dist/` has no stamp, and the server waits up to 10 seconds for one.
- **No build.** The server never builds. While a file under `src/` is newer than the stamp, each result ends with `stale:` and the fix, `pnpm build`.
- **Page errors.** A result that carries `PAGE ERROR` is marked as an error, because a `drive.ts` replay of that recording fails.
- **Another build.** `NULLPAD_DIST=/path/to/dist` serves that build, which needs its own `build-stamp`.

The `verify-nullpad` skill lists the tools and their arguments.

#### Grids against the reference

A grid has a `name` that states its rule in plain words, `rows` as a literal that the test checks, and `units`, the notes that are pasted. A test fails when the grid has another size, so a grid that shrinks shows as a changed number in the diff. `e2e/markdown/grids.ts` holds the table and `e2e/markdown-sweep.spec.ts` plays it.

A unit is one paste. Where a case cannot reach its neighbour, many cases share a note, each followed by a blank line, a sentinel block (`<!-- -->`) and a blank line. The note's HTML is compared with the reference's HTML for the same note, and both are cut at the sentinel's HTML into one piece per case. The first pieces that differ are printed with their source. A case joins a batch only when the reference shows it alone with the sentinel after it as its own HTML plus the sentinel's, so no case can open a comment or a list that swallows the next. A case that fails this test is pasted alone in the definition grid, and left out of the raw HTML, entity and link grids. Every stack of line shapes is pasted alone. A row passes when the pane shows the reference's HTML, or an accepted difference covers the case.

- Raw HTML parts: `<a`, `</a`, `<!--`, `-->`, `<?`, `?>`, `>`, `/>`, ` b`, `=`, `"x"`, `'x'`, `x`, `!` and `--`, one to three of them after `x `.
- Entities: every name of the entity table spelt seven ways (with and without the semicolon, with a letter after it, case flipped, in a link title and destination and in a code span), and 90 numeric references at the edges of their ranges, each alone, between letters and in a link title.
- Definition parts: one to three lines of `[a]: /u`, `[a]:`, a bare and a pointy destination, three kinds of title, two broken titles, a definition with a title, `[a]`, `a`, a blank line, and a definition indented by two spaces, by four and in a quote.
- Line shapes: `a`, a blank line, tabs at the start, after a space, after `-`, after `> ` and after `1.`, a quote, a bullet, an indent, `1.`, `0.` and `2.` items, `---`, `===` and a definition.
- Link parts: `[a](` or `![a](`, one of 9 destinations (none, bare, pointy, an unclosed pointy, empty pointy, with a space, with parentheses, with an escaped parenthesis), a gap of none, a space, a tab, a line end or both, one of 6 titles (none, three kinds of quote, an unclosed one, one followed by `x`) and a space, a line end or nothing before `)`, with and without a definition of `[a]`. A gap between the destination and a title is the case the grid is for: `[a](<b>"t")` is text.

`MARKDOWN_SHARDS` sets the number of parallel tests per grid (4 by default). Each shard prints how many rows it checked, how many differ, and how many differences each accepted difference covered. The grids take about 3.7 minutes on 4 cores, and with the slow inputs and the every-push tests the markdown files take 4.6 minutes. The every-push markdown tests alone take about 9 s of the gate with 6 workers.

When a bug turns up, first ask whether a spec example, a place rule or a scenario catches it. Add the shortest note to the grid whose rule it breaks only when none can, and set `rows`.

#### Accepted differences from the reference

`acceptedDifferences` in `e2e/markdown/differences.ts` has an entry for each difference under "Differences from commonmark.js" that a grid can meet: the numeric references from U+0080 to U+009F (entities), and a definition repeated before a setext heading and a paragraph of only definitions that ends at a `---` line (line shapes). The nesting limit, a symbol outside the BMP beside `*` or `_`, Unicode whitespace at the end of a line and a `&#32;` before a line ending have no entry, because no grid has a note that shows them. An entry has a `covers(markdown)` that reads the note the case came from, never nullpad's output, and an `example` that the spec text decides. A test pastes each example, and the pane must show the spec's HTML where the reference shows something else. Another test checks that no entry covers an example of the spec, so an entry cannot grow wide unseen. A mismatch that no entry covers fails the row. A grid that can meet another difference gets its entry in the same diff.

#### Outline places

`e2e/markdown/places.ts` reads the outline pane by its documented format and checks each row against the note that was pasted. The notes are the 652 spec examples, grouped into notes of up to 40 that the reference shows do not run into each other (the rest alone). The rules:

- Every place lies in the note, and the start is not after the end. Only a `SoftBreak` is empty.
- A top-level node is a block, and each node sits under a parent that can hold it. A child lies inside its parent, and siblings are in order and do not overlap.
- Every character of a `Paragraph`, a `Heading`, an `Emphasis` or a `Strong` is under a child or is a marker, a space, a tab or a `>`.
- The first child of a `Paragraph` starts where it starts and the last ends where it ends. The children of `Emphasis` and `Strong` lie between their delimiters, and those of a `Link` or an `Image` after its opening bracket.
- The source under a `Text` is its text. An `Escape` is a backslash and one ASCII punctuation character. An `Entity` starts with `&`, ends with `;`, and its text is what the entity table decodes. A `Code` starts and ends with backtick runs of one length, and its text is its source less the runs and less one space at each end when both have one. A `SoftBreak` is empty or one space, and a `HardBreak` is a backslash or two or more spaces.
- `Emphasis` starts and ends with one `*` or `_` and `Strong` with two. A `Link` starts with `[`, an `Image` with `![`, both end with `)` or `]`. An `Autolink` and an `Html` start with `<` and end with `>`.
- A `Quote` starts with `>`. An ATX `Heading` (one line) starts with `#`, a setext one ends at its underline. A `ThematicBreak` is three or more of one of `- * _` and spaces. An `Item` starts with its marker, and the items of a `List` share a bullet or a delimiter. A `Definition` starts with `[`, and an `HtmlBlock` with `<` after up to three spaces that belong to it.
- Every line with text lies in a top-level block.

#### Scenarios with an exact value

`e2e/markdown-limits.spec.ts` holds the checks whose expected value is not in a reference. Each assertion message gives its derivation.

- A setext heading ends where its underline ends (section 4.3 lets spaces and tabs follow the underline), so `Foo` over `===   ` is `Heading 1:0-2:3`.
- The nesting limit is 100 levels, and a quote, a list and an item are one level each. A quote and 49 lists make 99 levels and the 50th list marker stays text. 50 lists alone make 100. 100 quote markers open 100 quotes and the 101st stays text.
- An autolink scheme is 2 to 32 characters (section 6.5), so 32 letters make a link and 33 stay text.

#### Slow inputs

`e2e/markdown/slow.ts` holds the generators: unclosed pointy destinations, unclosed comments, block quote markers on one line, many definitions, a run of `*` around a letter, backtick runs of growing length, a run of n backticks and then `a` and one backtick, a backtick and a letter n times, n openers `*a ` then n closers `b_ `, nested list markers and blank lines, nested brackets, unclosed brackets before links, alternating openers, unclosed attribute values, links opened inside destinations, entity-like runs, and a lazy line under deep quotes. Each is pasted at n and 4n, three times each on a page with the pane and on a page without it, from the paste to the status line showing the line count. The parser's share is the best time with the pane less the best time without. A test fails when the share at 4n is over 8 times the larger of the share at n and 200 ms, so the editor's own cost, which is large on one very long line, cancels and tiny shares cannot flake. An input that nests deeper than the limit has its growth judged only, and every other input must show the reference's HTML at both sizes, except one whose reference is itself quadratic at 4n. A quadratic parser that costs under about 0.2 s at n is not caught. n is 1,250 for the two inputs that the editor itself draws slowly (5,000 `>` on one line takes about 0.6 s, 5,000 `*` about 0.3 s, and 20,000 of either 2 to 7 s), 40,000 for the backtick and letter input, 2,500 for the opener and closer input and 5,000 for the rest. On this build the backtick and letter input shares 504 ms at 40,000 and 2,040 ms at 160,000, and the opener and closer input 94 ms at 2,500 and 305 ms at 10,000. A parser that is quadratic on them takes about 17 s at 160,000 backticks and 50 s at n=20,000 openers, which is over 8 times the share at n.

## Process

- Tests are end-to-end only. See Testing.
- Prove a change in the running app with the `verify-nullpad` skill (`node e2e/drive.ts`) before calling it done. The `nullpad` MCP server is for trying things out. Its recording is a proof once `drive.ts` replays it.
- Every PR passes the pre-push hook: quick checks and the push gate, about 3 minutes, and about 4.5 when the push changes vim code and runs the vim tables. Nothing else runs as a gate. `pnpm test:all` runs on demand, such as after a change to the area a sweep covers.
- A PR adds a test only when it fixes a real bug (one scenario that fails on the bug) or opens a kind of bug no test can catch. Most PRs add none.
- A PR that changes app behavior gets one break-it pass: an agent that did not write the change drives the app, about 10 minutes, and reports what broke. A PR that only changes tests or tooling skips it.
- A PR that changes app behavior gets a recording: its proof with `caption` steps, replayed by `node e2e/drive.ts <steps.json> --record`. The break-it pass, the recording and the no-comments pass do not wait for each other.
- No planted-bug runs, random scouts or nightly runs.
- Few comments. Name things better instead. Keep a comment only for a fact we cannot change, such as a browser rule. Skip the `// MODEL` section headers that `FOLDKIT.md` suggests.
- Before a PR is ready, a no-comments pass (`/pstack:no-comments`) runs on its diff.
