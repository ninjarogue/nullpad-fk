# nullpad

A markdown note editor that feels like a terminal, built with Foldkit. Read [`FOLDKIT.md`](./FOLDKIT.md) before writing Foldkit code. Foldkit owns that file and replaces it on upgrade, so this file holds everything specific to nullpad.

`FOLDKIT.md` reads the line below to decide whether to offer to vendor the Foldkit source. Leave it in place.

subtree_prompted: false

## Layout

- `src/core/` is the pure core: domain logic such as the buffer, the parser and vim. It runs without a browser.
- `src/` outside `core/` is the shell: Model, Message, update, view and the runtime boot in `entry.ts`.
- New behavior goes in the core first. The shell routes messages to it.

## Colours

Every colour in `src/styles.css` is a `light-dark()` token on `:root` or `.doc`. The finder's backdrop is the one `light-dark()` written in place. `color-scheme: light dark` makes light the default and follows the system to dark. `index.html` declares the scheme and the theme colour before the stylesheet loads.

## Editor

The editor types like a browser text box because the browser makes the decisions a text box makes. The core owns the text, the caret and which lines are drawn. The browser owns typed text, IME composition, line wrap, caret steps, hit testing and scrolling.

- `src/keyboard.ts` puts an EditContext on `#port`, the app's one focusable element, and turns every key, text, IME and paste event into an `Input`. The EditContext holds the caret's line, up to 1,000 UTF-16 units each side of the caret (`Frame.surrounding`, carried on the port's attributes), so an IME can convert letters already typed. A range an IME replaces becomes an `Erase` counted from the caret, so a copy a frame behind still erases the right letters. `update` passes the `Input` to `Editor.feed` in `src/core/editor.ts`. Only this file knows about EditContext; a fallback for browsers without one slots in here.
- Backspace deletes the whole letter (grapheme cluster) before the caret, as an EditContext does, where a textarea deletes one code point of an accent, a conjunct or a jamo. `fromKeyDown` takes Backspace in `keydown`, which keeps it in order with the other keys, and `backspaceTarget` in `src/core/buffer.ts` finds the letter with `Intl.Segmenter`.
- A key that needs layout (Left, Right, Delete, Home, End, Up, Down, Page Up, Page Down) or a click makes the core return a `Need` that holds a `Query` and queue every input after it. `src/surface.ts` answers it once the DOM shows the core's `revision`, with `Selection.modify` and `caretPositionFromPoint` on the drawn lines, and `CompletedLocate` lands the answer and replays the queue. The core never reads layout and the shell never moves the caret from a stale frame. A click is held as a line, client x and pixels below the line's top, so no scroll before its answer moves it off the line it was made on. The line is the one under the pointer in the frame on screen when the pointer went down. A scroll the app makes for a key or a click is on screen once the frame after it begins, so a click whose `timeStamp` is older than that is read without the scroll, however late Chrome hands it over. A wheel turn is the user's own scroll and a click is level with it. A click below the last line is the end of the text. The core keeps the line the shell has yet to read or reveal drawn: it draws a clicked line that has left the drawn lines, and it leaves out a scroll report that would undraw the clicked line, or the caret's line while a key's query or a reveal has yet to run.
- A `Need` is a question the core cannot answer alone: `Locate`, a `Query` for the layout, or `ReadClipboard`, for vim's `"+p`. The editor has at most one out, held in `locating` with the input that caused it and the inputs queued behind it. Asking changes nothing else. The cause is planned again when its answer lands, so a put from the clipboard cannot run without an answer. Every `Need` carries a `ticket` from `Editor.asked`, which only counts up and outlives `reopen`. `CompletedLocate` and `CompletedReadClipboard` echo it, and `Editor.located` and `Editor.clipboardRead` ignore an answer whose ticket is not the one out. Without it an answer to one note's question landed on the next note's: in the core an old answer to End, taken for a Delete in a note opened meanwhile, erased five letters. `locating` clears only when its answer lands and in `reopen`, so every question gets an answer: `src/clipboard.ts` answers a read with `None` when the browser refuses or 3 seconds pass (no limit while Chrome asks for permission). An `Outcome` also carries `writeClipboard`, the text a `"+y` copied, and `update` runs a `WriteClipboard` Command for it.
- `src/surface.ts` draws the lines of `Editor.paint`: one `.line` per text line, wrapped by CSS, each piece between joins its own text node, one spacer row per undrawn line above and below, all in one `.sheet`, and a `#caret` overlay beside the sheet, placed from a Range rect after each patch. `.surface` scrolls natively and reports its first line and its height in rows. It scrolls a wheel turn itself, on the main thread, and only onto drawn lines: when the turn lands past them, the screen stays put until the patch that draws that place scrolls there. Chrome's own wheel scroll runs ahead of the drawn lines and paints blank screen. Chrome hands a wheel turn to the page at the next frame, after keys pressed later than it, so a turn whose `timeStamp` is older than the moment an input last asked for the caret on screen is dropped: the key came after it.
- `.surface` shows a native scrollbar and has no padding. `.sheet` holds the padding and is at least as tall as the surface, so its children cover the whole text area, and a press whose target is `.surface` itself, while the note overflows, is on the scrollbar (`isOnScrollbar` in `src/surface.ts`). The scrollbar scrolls the surface as any scrollbar does. A press on it makes no click, so the cursor stays, and `keyboard.ts` does not commit an IME composition for it, as a textarea keeps composing. The press still keeps the keyboard on `#port`. A press in the reserved scrollbar lane of a note that fits the screen is a click on the text.
- During a thumb drag each patch draws wrapped lines above the screen in place of one-row spacer rows, and scroll anchoring would pull `scrollTop` back by the extra height, about 100,000 px over one drag through 3,000 lines of 3 rows. Chrome's next pointer move puts the thumb back under the pointer, but a pull after the last move stays, so a thumb dragged to the bottom stopped short of the end in 7 to 18 of 20 drags. So `.surface` scrolls without anchoring while the browser holds a press on the surface itself, which is its scrollbar (`.surface:active:not(:has(:active))` in `src/styles.css`). The browser ends `:active` with the press, on a release in or out of the window and at the first pointer move with no button, and anchoring comes back without moving the screen. While the thumb is held a patch can move the text under the screen, and the screen still shows drawn lines.
- The scroll height would also change under a held thumb, because a drawn line is as tall as its rows and an undrawn one is estimated at one row. Chrome places the thumb from the scroll height, so a drag to the bottom stopped short: at line 417 of a 450-line note where every fourth line wraps, in 3 of 3 drags. So a press on the scrollbar writes the sheet's height to `--held-sheet-height` on the root element (`holdThumb` in `src/surface.ts`), and while the browser holds the press `.sheet` keeps that height and clips what is past it. The thumb then stays under the pointer. At the held end the last lines can be past the clip, so when a press that ended at the held end is let go (`releaseThumb`, on `pointerup` or `pointercancel`), the surface scrolls to the real end. A thumb let go short of the end stays on the line it showed, and the thumb then moves to that line's place in the real height.
- A native scroll can land on the end of the note while the lines there are undrawn. Drawn, a wrapped line is taller than the one row it was estimated at, and after the patch the screen is no longer at the end. So `ScrolledSurface` carries `atEnd`, and when a report at the end changes the editor, `update` issues `ScrollSurfaceToEnd`, which scrolls to the end after the patch. Its scroll reports again, and once the drawn lines reach the end the report changes nothing. A wheel turn reports `atEnd` false, since it reads its pending turn again after the patch. A thumb flicked to the bottom in three pointer moves, on 2,700 one-row lines and then 300 of 3 rows, showed the last line in 20 of 20 flicks with this rule and 0 of 20 without it.
- A fast thumb drag through a huge note can show blank frames. Chrome scrolls the drag on its compositor, ahead of the patch that draws the lines there, as it does on a plain page of 120,000 lines, and the lines fill in once the thumb slows. This is accepted, as in the read view. Only a scrollbar the app draws itself could stop it.
- The test rig shows scrollbars: `playwright.config.ts` and the launches in `e2e/drive.ts` and `e2e/mcp.ts` (`launchOptions` in `e2e/steps.ts`) drop Playwright's default `--hide-scrollbars`. A hidden scrollbar takes no mouse input, so a scrollbar scenario in a rig that hides them tests nothing.
- A Ctrl or Meta chord whose key is not in `browserChords` becomes a `Chord`, and `keyboard.ts` cancels its keydown, so Ctrl-Z, Ctrl-Shift-Z and Ctrl-Y never reach the browser. Ctrl-R is in `browserChords`, so it reloads the page, except while the port's `data-chords` reads `vim` (vim on, from `Editor.isVimOn`): then Ctrl-R with no other modifier is a `Chord` and its keydown is cancelled. Ctrl-Shift-R, Cmd-R and F5 always reload. Headless Chromium does not reload on Ctrl-R, so a test reads whether the keydown was cancelled.
- A new key binding goes in `plainKeys` in `src/core/editor.ts`, a Ctrl or Meta chord with vim off in `plainChords`, or a row in `normal` in `src/core/vim/keymap.ts` for vim's Normal mode.
- `script()` in `src/core/input.ts` and `Editor.dump` run the editor without a browser for keys that need no layout, and print the drawn lines as text. Bundle a file that calls them with `pnpm dlx rolldown@1.2.19 <file>.ts --platform node -o <file>.mjs`, then run it with `node`.

## Notes and finder

- `src/core/notes.ts` holds the `Note` record, its title and the folder helpers. A folder is a note's path prefix and exists while a note is in it. A folder path drops empty, `.` and `..` segments. `src/core/fuzzy.ts` scores titles and paths fzf-style over graphemes. `src/core/finder.ts` is the finder's state, fed the same `Input`s as the editor.
- While the finder is open, `update` sends every `Input` to `Finder.feed` instead of `Editor.feed`, and the port's EditContext holds the finder prompt (`Finder.surrounding`), so `keyboard.ts` stays the one keyboard. The port's `data-control` and `data-selection` name the elements whose rects `keyboard.ts` hands the EditContext, so an IME window sits at the prompt. Ctrl-P opens it. Chrome keeps Ctrl-N for a new window, so that chord never reaches the page.
- `src/storage.ts` keeps one IndexedDB record per note in database `nullpad`, store `notes`. The `NoteStore` service holds the connection and the BroadcastChannel `nullpad-notes`, which carries every save and removal to the other tabs, and offers list, read, write and remove with an expected revision, and the stream of changes. `entry.ts` passes its Layer as the runtime's `resources`, so Flags, Commands and Subscriptions share one connection and the runtime closes it at teardown. Boot reads every note through the `flags` Effect before the first render and opens the one edited last. When IndexedDB cannot open or a write fails, the status line says notes are not being saved and the editor keeps working.
- A text change starts an 800 ms wait. A save goes out when no change came after it, at once on a switch of notes, and when the page hides. Saves of the open note go out one at a time, each expecting the revision the last one confirmed. A change from another tab that arrives while a save is out waits until it settles. A change from another tab that keeps the text this tab last saved, such as a move, takes its folder and revision under this tab's unsaved edits. Whenever the store moved to other text under text this tab has not saved, this tab's text goes into a conflict copy. A note that goes blank is removed from the store at its save moment and leaves the list, and typing again saves it anew.
- Effect's runMain stops the app at `pagehide`, and an unloading page does not finish IndexedDB work. So `entry.ts` listens to `pagehide` before the runtime starts and writes the open note's unsaved text, and the text of notes left mid-save, to localStorage through Effect's `KeyValueStore` as `nullpad-draft:<tab>:<id>`, with the revision it was based on. Boot takes every draft. A draft whose note is still at that revision, or at the one its own save in flight made, reopens and saves. A blank one removes its note. Any other becomes a conflict copy.
- The finder draws at most 60 rows around the selection, ranks only the last matches while the query grows, and caches each text's graphemes and bonuses, so a keystroke over 2,000 notes stays near one frame.

## Read view

Ctrl-E, or the `read ^E` button at the end of the status line, swaps the editor for the note drawn as markdown. Ctrl-E or Esc swaps it back, with the cursor and the editor's scroll where they were. The status line's mode says READ.

- `src/core/reading.ts` turns `Markdown.parse` of the buffer's lines into a `Page`, a flat array of units in note order. A unit is one element the view draws: a paragraph, a heading, a rule, one line of a code or HTML block, or an item or quote with nothing else in it. Each unit holds its first source line, the first line of the outermost block it opens (a code fence, a bare `>` or `-` line, a definition before it in a quote), the holders around it outermost first (a quote, a list, an item, a code or HTML block, each keyed by where it starts). `Page.starts` holds the estimated top of each unit in pixels. A definition and a blank line make no unit. A soft break and a hard break are one `Break` inline, drawn as a `br`, so each typed line of a paragraph or heading starts its own visual line in the same element, where the HTML pane keeps the line feed CommonMark writes for a soft break. A code span or raw inline HTML that spans lines holds no break and draws on one line. An image drawn as its alt text draws its description's inlines, as a link drawn as its text does, so its breaks stay. Raw HTML stays text. A link whose destination starts with `javascript:`, `vbscript:`, `file:` or `data:`, read as a browser reads it (tabs and line feeds removed, control characters and spaces trimmed from the ends, any case), is drawn as its text. An image is drawn only from `http:`, `https:` or a `data:image/` gif, png, jpeg or webp, and otherwise as its alt text. `page` keeps its result for each lines array, so a text is parsed once.
- A list item whose first paragraph's source starts with `[ ]`, `[x]` or `[X]` and then a space or tab is a task. `readItem` reads the mark from the source line at the paragraph's start, because the inline pass splits `[ ]` into three texts and reads `[x]` as a link when the note defines `x`. The unit of its first paragraph carries the `Box` (the buffer line, the column of `[`, and whether it is checked) and loses the mark. The view draws the box as an empty `span` with `role=checkbox`, `aria-checked` and an `aria-label` of the task's text (`Reading.label`), never an `input`. In a bullet list CSS draws the square and its tick in the list indent, in place of the bullet, so the item's text and its nested blocks line up with the other items. In an ordered list the number stays and the box sits after it, in the text's first line.
- A click on a box is the one edit the read view makes. `ClickedTask` carries the box as drawn, and `update` takes it only while the screen is `Read`. `Reading.click` returns `Flip` when the note's page still holds that box in that state, and `Ignore` otherwise, so a second click from a stale frame does nothing. `Reading.flip` calls `Editor.overwrite` and keeps the old page, with that one box flipped, as the page of the new lines, so a click does not parse the note again. The flip changes one character of a mark that a space or tab follows, and no block or inline rule reads `[ ]`, `[x]` and `[X]` there differently. `Editor.overwrite` writes the one character with `Buffer.overwrite`, which keeps the line's length, its id and its joins, so the caret and a queued locate stay valid. The change saves as typing does, and the read view stays where it was.
- `act` in the core decides what an `Input` does in the read view. Esc and Ctrl-E close it, Ctrl-P opens the finder, Up, Down, Page Up, Page Down, Ctrl-Home and Ctrl-End scroll, and every other input does nothing. A new key goes in its `keys` table.
- The Model's `screen` is `Edit`, `Opening` or `Read`. Ctrl-E pressed while the editor waits for a layout or clipboard answer moves to `Opening`, which holds every input after it until the answer lands. `update` runs `finishOpening` after every message, so whichever message clears `locating` opens the read view. The keys before Ctrl-E reach the editor and the keys after it reach the read view.
- The Model's `Read` holds the index of the unit at the top. `Reading.drawn` takes the units within 125 units (or a screen, if that is more) of it and groups them back into their holders, so the view draws real `blockquote`, `ul`, `ol`, `li` and `pre` elements around only the drawn units. An `ol` starts at the number of its first drawn item, and an item or code block cut by the window's top draws no marker or info line.
- `src/reading.ts` draws the drawn units in `.read`, the scroll container, between two spacers, each as tall as the estimated pixels of the units it stands for. `Reading.metrics` holds every number that sets a height or a text width in the read view (the 680 px measure, the 16.5 px body size on a 27 px line, the gaps, each heading level's size, line, margins and rule, the code panel's padding, the indents, the quote's rule, the task box, and a code span's size and padding in ems), and `src/reading.ts` sets them as `--read-*` custom properties on `.doc`, so `styles.css` takes them from the core and repeats none. A code span has `line-height: 1`, so its own font does not grow the 27 px line. `pageOf` adds each unit's height to the space after it: the margins CSS collapses between it and the next unit (the largest bottom margin of the unit and the holders it closes, or top margin of the holders the next one opens), and a code panel's padding and border where a panel starts or ends. After the last unit that space is its bottom margin and those of the holders it closes. The first drawn unit draws its own top margins, and a code panel cut by the window's top draws its top edge, so the spacer above is that much shorter than the estimated top. An empty list item is one 27 px line, because its marker draws one. A unit's text height is its lines times its line height. A `br` starts a new line box, so `segmentsOf` cuts the unit's text at each break, across the edges of emphasis, strong and links, and its lines are the sum over the segments of each segment's width in ems over the column's width in ems, rounded up and at least one. In a width an ASCII letter counts as one of three widths of Inter (`glyphEms`), a code span as JetBrains Mono at its size with its padding, an East Asian wide grapheme or an emoji as 1 em, an image as a whole line, and a box in an ordered task as the indent past its inset, on the first segment only. Headings and `strong` scale the width (`widthScales`). Measured in headless Chromium as the advance of each printable ASCII character in Inter at 16.5 px, the class means are narrow 0.30 em, usual 0.56 em (0.58 over the letters of English words) and broad 0.72 em. Weight 650 draws English words 1.02 times as wide, and a heading's weight and tracking 0.99 times. `glyphEms` and `widthScales` sit at these or above them, because a line breaks before a word and leaves its end empty. To refit them, wheel a long mixed note from top to end at 1280x720, sum each drawn unit's top-to-next-top advance, and compare the sums with `Page.starts`: the estimate should stay a little over, never under. The column is the measure less each holder's indent. A spacer is taller than its units where a run of spaces collapses or letters draw narrower than their class, and shorter where a line breaks early before a long word, an image is taller than a line, a code block wider than the column shows its scrollbar, or the window is narrower than the measure. Every unit but a rule is at least `metrics.row` (22 px) tall, so `screenRows` units fill the screen. Each unit carries `data-unit`, its index, and `data-source-line`, the gutter's number for its first line.
- Only `.doc` draws in Inter (`@fontsource-variable/inter`, bundled, normal and italic); the editor, the status line and the finder keep JetBrains Mono. `entry.ts` loads Inter at boot, so the first open lays out in it.
- `.read` reports the unit at its top as it scrolls, or, when its top is inside a spacer, the spacer and the pixels past its top. The core takes the unit at that height and pins it to the top once it is drawn. When the screen would reach the estimated end it draws the last unit and scrolls to the end of the note, so a fling past the end shows the note's last line in one turn, even when the last unit is taller than the screen. A landing on the first unit scrolls to the top, as Ctrl-Home does. Chrome's scroll anchoring holds the place as units come and go above. Chrome skips anchoring at `scrollTop` 0, so the port's observer also remembers the top unit and its offset and puts it back after each patch. A scroll the app makes fires a `scroll` event on `.read` at once, since Chrome fires its own at the next frame, so the observer remembers the new place before the next patch.
- Opening the read view scrolls the unit that holds the cursor's line to the top: in a list the cursor's item, in a code block the cursor's line. On the first unit it scrolls to the top, as Ctrl-Home does, so a heading there keeps its top margin. It is the last unit whose first block line is at or before the cursor's line, so a cursor on a code fence or on a bare `>` or `-` line opens at the block that line starts. A cursor on a later typed line of a paragraph or heading, a lazy line included, opens at that line: `Reveal.Unit` carries how many breaks of the unit come before it (`revealLine`, at most the unit's breaks), and the shell scrolls the line after that `br` to the top. It reads the drawn `br`, not the estimate, so the line lands at the top at any window width, or as near as the end of the note lets it. Opening another note from the finder returns to the editor.
- The editor's `.surface` stays mounted, hidden under the read view in one `.stage`. A reveal the editor owes when the read view opens, such as Ctrl-End and Ctrl-E pressed in one frame, scrolls the hidden surface, and closing uncovers the surface as it is. `screenView` builds the stage in one return: Foldkit's Vite plugin stamps each function's return with its own identity, and the differ replaces a node whose identity changed, so a stage returned from two `Screen.match` arms would make a new `.surface` on every switch.
- While the read view is open the port's `data-control` names `.read`. Text typed there still reaches the EditContext and is thrown away, so `keyboard.ts` sets the EditContext's text again whenever `data-control` changes.
- On a 9,000-line note of headings, paragraphs of several typed lines, tasks, lists, quotes and code blocks (5,009 units), the estimated total is 0.3% over the drawn one, no unit's estimated top is under its drawn top, and the most it is over is 756 px (0.37% and 891 px on another 9,000-line note of 4,880 units), where the 22 px row estimate it replaced was 6.8% short. On notes of only headings, only code lines or only one-word items the estimate is exact. Opening the read view on that note takes about 250 ms to the next frame in headless Chromium and draws about 350 elements, and about 30 ms on the same text again. A 20,000-item task list opens at the cursor's item in about 580 ms with about 850 elements, where drawing the whole list took 1.4 s and 60,000 elements on the same machine. `Markdown.parse` is most of a first open. A click on a box of a 10,000-item task list takes 33 to 51 ms to the next frame, where parsing the note again took 610 to 1,000 ms.

## Vim

Vim is off until a person turns it on with Ctrl-, or the `vim off` button at the end of the status line (`.status .toggle-vim`, which then reads `vim on`). Turning it on lands in Normal mode, turning it off returns to plain typing. The setting is the localStorage key `nullpad-setting:vim` (`on` or `off`), written through Effect's `KeyValueStore` and read by the `flags` Effect at boot, so a reload keeps it and `openFresh` clears it. Other open tabs keep their mode until they reload. A change to the open note from another tab, a conflict copy and a removal re-show the note in the mode it had (pending keys drop), and a toggle still queued behind a layout answer lands with it. Opening another note from the finder starts in Normal.

- `src/core/vim.ts` is vim's public surface: the `Vim` state (`mode`, which is `Normal`, `Insert` with the stay's `recording`, or `Visual` (see Visual mode), the pending keys of `Keymap.Pending` (`outerCount`, `register`, `count`, `keys` and `innerCount`), `want`, the screen column `j` and `k` keep, and `last`, what `gv` brings back), `press`, which takes an `Input` and `Kept` (the registers and what dot repeats) and returns the new state, the new buffer, the new `Kept` and the input's fate, `again`, which does the same for one step of a replay, `putClipboard`, which runs a put with the clipboard's answer, and `rest`, the Normal clamp. The parts live under `src/core/vim/`: `cells.ts` cuts a line into cells (graphemes within the pieces between joins, as Backspace does), gives each a kind for word motions and a screen width (2 for an East Asian wide character or an emoji, a tab to the next multiple of 8), `motions.ts` holds the motions and Vim's own cursor steps (`inc`, `dec`, `incl`, `decl`) with the two word walks an operator uses, pure over the buffer, `objects.ts` holds the text objects, `targets.ts` turns a motion or a text object into a `Range`, `selection.ts` holds what a VISUAL selection covers, `operators.ts` applies a `Range` and puts, and `keymap.ts` holds the binding table and `advance`, which turns the pending keys and one more key into Run, Wait or Drop. Only `vim.ts` and those files import them, and vim imports nothing of the editor: it returns a buffer that `editor.ts` commits.
- `Editor.vim` is `Option<Vim>`, and `None` is vim off. With vim off, and in Insert for every input but Esc and Ctrl-[, `inputPlan` runs the plain path untouched, so Insert types exactly as the editor does with vim off and the typist's comparisons still hold.
- No Normal key asks the layout. `j` and `k` move by numbered line, and from a tab they keep the tab's last screen column, as Vim does. Arrows, Home, End, Ctrl-Home and Delete are rows of the table (`h j k l 0 $ gg x`), so a count works on them. `j` on the last line, `k` on the first and a counted `$` on the last line fail and leave the cursor (`motionFails`), as in Vim, and that `$` still sends the next `j` or `k` to the line end. `h`, `l`, Space and Backspace that cannot move keep the column `j` and `k` keep. Ctrl-End goes to the last letter of the last line. Space and Backspace step a letter and cross to the next or previous line at a line's edge, as Vim's default `whichwrap=b,s` does. Page Up and Page Down take the plain path. A paste inserts its text before the cursor's letter and stays in Normal. Enter and Tab do nothing.
- A count is grammar, not a row: a digit is a count when no key is pending, and an inner count right after an operator key (`2d3w`), and `0` only after another digit of the same count. Each is capped at 7 digits, and the two multiply. A key that matches no row drops the pending keys with it, so `d.` does nothing.
- A register is grammar too. `"` with no key pending starts a prefix and the next key names the register: a letter, `"`, `0`, `_`, `+` or `*`. Any other key drops the pending keys. `Pending.register` holds the prefix as typed, `"` while the name is awaited and then `"a`. A count typed before the prefix moves to `outerCount`, and the three counts multiply. A second prefix replaces the first: `2"a3"b1x` deletes 6 letters into `"b`. After an operator key `"` matches no row, so `d"` drops at once and the key after it runs on its own, as in Vim. `Run` carries the register as a `RegisterName`: `Default` (no prefix), `Unnamed`, `Yank`, `Letter` (with `appends` for a capital), `BlackHole` or `Clipboard`.
- `d c y` are operators. Their rows are generated in `keymap.ts`: each operator key before every motion row, before itself (`dd cc yy`, target `Lines`) and before every text object, so `next(['d'])` lists what can follow `d`. `x X s S D C Y` and Delete are rows over the same `Operate` command (`dl dh cl cc d$ c$ yy`). `p` and `P` are `Put` rows. `Run` is plain data, a command, a count and a register, so an undo or a repeat can record it.
- A `Target` takes the buffer, the cursor's cell and the count and returns `Option<Range>`; `None` cancels the operator, an empty range still runs (`ch` at column 1 enters Insert). A `Range` is `from`, `to` and `Charwise` (half open, in cells) or `Linewise` (whole lines from `from.line` to `to.line`, and `from` is where a yank leaves the cursor). Each of Vim's rules that does not follow from the motion lives in one place:
  - `w` under an operator stops at the line end on its last step, so `dw` on a line's last word does not join the next line: `forwardWordStoppingAtLineEnd` in `motions.ts`, a port of Vim's `fwd_word` with its end-of-line stop.
  - `j`, `k`, a counted `$` and `Lines` fail where they cannot move, so `dj` on the last line and `2dd` on the last line do nothing (`motionFails`, `lines`), and a counted `b` fails only when one of its steps starts at the start of the note, so `d9b` deletes back to the start (`wordBackward`, a port of Vim's `bck_word`).
  - `l` reaches the slot past the last letter, so `x` is `dl` at a line end (`rightward`).
  - An exclusive range that ends in column 1 of a later line ends at the line end above it, or goes linewise when it starts in the indent (`rangeOf`, the one place every charwise target passes).
  - `cw` on a letter changes to the end of its word and keeps the space after it, and on a word's last letter changes that letter (`targetFor` swaps in `wordEndStay` for a change).
  - A delete over several lines that starts in the indent and leaves only blanks after its end goes linewise (`linewiseWhenBlankAround`, delete only).
  - A linewise change leaves one empty line with no indent (`emptyLine`).
- After a delete the cursor rests on a letter, after a linewise delete on the first non-blank of the line now there; after a yank at the range's start; after a change in Insert at the range's start. After a put of letters within one line it is on the last letter put, after a put that spans lines on its first letter, and after a linewise put on the first non-blank of the first new line. Deleting every line leaves one empty line (`Buffer.removeLines`, which keeps the ids of the lines left; `Buffer.insertLines` gives new lines new ids).
- Text objects port Vim's `current_word`, `current_par`, `current_quote` and `current_block` over cells, in `objects.ts`. Each object has `find`, which NORMAL's operators use, and `pick`, which VISUAL uses. An operator whose object is not there drops the column `j` and `k` keep. `diw`, `yiw` and `ciw` on an empty last line take the last letter of the line above and its line break, as Vim does. A bracket object finds its pair across lines and counts brackets inside quotes. When the cursor is in no pair, it takes the next opening bracket after the cursor, on any later line too, as Vim 9.1 does. Brackets and quotes are ASCII, so the bracket scan reads UTF-16 units and segments only the line where it lands.
- `Editor.kept` is what outlives a note: `registers` and `dot`. It lives beside `vim` in the editor, so it survives vim off and `reopen` (opening another note), and a reload starts with none.
- `registers` holds the unnamed register, the yank register (`"0`) and `named`, a record from a lower-case letter to its register. A register is a text and a kind; linewise text ends in a line feed. `remembered` in `operators.ts` is the one function that writes them and `registerFor` the one that reads them, each a match over `RegisterName`, so a new kind of register is a case in both.
  - With no prefix a delete, a change and a yank write the unnamed register, and a yank the yank register too. `"a` writes the letter and the unnamed register and leaves `"0`. `"A` adds to the letter, and the unnamed register then holds all of it: letters after letters join, and when either part is whole lines the result is whole lines, each part on its own lines. `""` and `"0` before a command fill the unnamed and the yank register, for a delete too. `"_` writes nothing. `"+` and `"*` write the unnamed register and the system clipboard.
  - A put with no prefix or `""` reads the unnamed register, `"0` the yank register, a letter of either case its register, and `"_` nothing. A put from an empty register changes nothing and still becomes `dot`.
  - A yank of nothing writes an empty register. A delete of nothing writes none. A change of nothing writes an empty register only when its motion is inclusive (`C`, `c$` and `ciw` on an empty line, `Range.inclusive`), and none for `s`, `cl`, `ch` and `c0`. `cc` and `S` on an empty line write one empty line. Each is Vim's answer.
- `"+` and `"*` are the system clipboard, which only the shell reaches. A delete, change or yank into it returns the text in `Step.clipboard`. A put from it returns the fate `ReadClipboard`, and the editor asks with a `Need` (see Editor) and changes nothing: the prefix stays pending, so `.status .pending` shows `"+` while it waits, and keys typed meanwhile queue behind it. `Editor.clipboardRead` lands the answer through `Vim.putClipboard`. `Some` text is put as whole lines when it ends in a line break, and otherwise as letters, with CRLF and CR read as LF (`fromClipboard`). `None` puts nothing. Either way the put becomes `dot`, and a `.` asks the clipboard again. A read writes no register. `src/clipboard.ts` holds the two Effects: `readText` gives `None` when the browser refuses, answers with something that is not text, or 3 seconds pass, and `writeText` gives whether the write worked. While the permission state of `clipboard-read` is `prompt`, Chrome is asking the person and the read has no time limit, so an Allow after second 3 still puts. A step's `WriteClipboard` goes out before its `ask`, so a `"+p` queued behind a `"+y` reads what the yank wrote.
- `Editor.notice` is one line of the status line, drawn as `.status .notice` and absent when there is none. A read that was refused or timed out and a write that failed set it to `clipboard blocked, use Ctrl-V`. `update` clears it before it handles the person's next act: an input, a click on the text, or the `read` or `vim` button, over the read view and the finder too. An input replayed from a queue does not clear it, so the notice of a read stays after the keys typed during its wait have run.
- `.` does the last change again, and a count on `i a I A o O` types the stay's text that many times at Esc. `dot` is a `Vim.Repeat`: the command, its count, its register and `typed`, the record of its INSERT stay. It is command data, not keys, so it holds when the keymap changes.
  - A delete whose target exists, an empty one included (`x` on an empty line), and `p` or `P`, with nothing to put included, become `dot` when they run. A stay becomes `dot` at Esc, a stay that typed nothing included, so after `xi<Esc>` a `.` inserts nothing. A stay that ends another way (vim off, another note) is forgotten. A yank, a motion, `u`, Ctrl-R, a paste in Normal and a command whose target fails leave `dot`.
  - A stay records itself in its mode, `Insert { recording }`: the command and count that began it, and each input that changes text (typed text, Enter, Tab, Backspace, Delete, a paste, IME `Commit` and `Erase`). Arrows, Home, End, Page keys, chords and `Preedit` are not recorded, and a click leaves the recording as it is. A Backspace at the start of the note is not recorded, as in Vim.
  - `typed` is a list of `Recorded` entries: `Keys` holds a run of printable ASCII typed key by key, and `Other` holds one input. A letter or a space typed by a key starts a run or adds to it, and so do longer text one key typed and a Tab's two spaces, except at the start of a run or of a line in it. An Enter after a key adds its line feed, and a Backspace takes back the run's last key when the run holds two or more and neither of its last two is a line feed. Every other input is an `Other`. So a held key copies nothing, and the record grows only where a run breaks. The mode is built as a plain record, with no Schema check, because a check of the whole record on every key made typing cost grow with the stay. A stay records at most 10,000 entries (`maxRecordedInputs`), and one more clears `dot` and records no more of it: above about 16,000 entries V8 keeps the list as a large object, and its copy on each key costs 9 ns an entry where it costs 1.5 ns below.
  - A run plays as at most five inserts: the line feeds it starts with, its first key alone, the rest up to the end of its first run of line feeds, the key after them alone, and the rest. A key typed before a lone combining mark joins it, and the caret moves past it, and a stay's first key and the first key after its first line break are the keys that meet one, so a run never starts a line with more than one key. Played this way a run left the lines, joins and caret its keys leave one by one in 30,000 random stays over notes of lone marks, flags, ZWJ, joins and lines that start with 70 and 100 marks, compared after every key. Not probed: a line with two joins that each have a lone mark after them, and a row of marks longer than 128 UTF-16 units, where a later key of a run could meet a mark too.
  - `.` and Esc return the fate `Replay`, a list of `Replayed` steps: `Run` (a command and a count), `Typed` (one input) and `Leave`. `.` is `Run`, the stay's steps, then `Leave`. Esc, and `Leave` in a recording stay, make the stay `dot`, then play its further copies and a last `Leave` with the recording off. A further copy of `o` or `O` starts with a typed Enter, a line break at the cursor, as Vim's redo does, so `2Ohi<Esc>` leaves the cursor on the second `hi`, and `2ox<Del><Esc>` at 1:1 of `one`, `two`, `three` leaves `one`, `x`, `xwo`, `three`.
  - The editor plays each step as a queued `Again` item with its `replay`, so a step passes `planOf`, the history and `plainPlan` as a typed key does. A recorded Delete asks the layout again, and keys typed meanwhile wait behind the steps left. While a step waits the editor is in INSERT, so the status line reads INSERT and the caret is the bar, one frame for each recorded Delete. A change to the open note from another tab in that wait re-shows the note and drops the steps left, `Leave` included, so the tab stays in INSERT and the next Esc makes the cut-short stay what `.` repeats. Outside a stay `Typed` and `Leave` do nothing, so a repeated change whose target fails types nothing.
  - A replay records as typing does, which is how Vim's redo works. So a count before `.` replaces the count when the command runs, and stays (`3x2..` deletes 3, 2, 2), a `.` whose command fails leaves the old count, and the counts given multiply first (`2d2w` then `3.` is `d3w`). A count on a change belongs to the operator, so a change has no further copies. A register typed before `.` is ignored and the repeat keeps its own. Vim does that when the command had a register, and writes the typed one when it had none.
  - The further copies of one replay hold at most 20,000 inputs (`maxReplayedInputs`), a run counting one for each key, and 120 Delete keys (`maxReplayedDeletes`), and stay within the bounds of a put of the same text. The count is lowered to fit. The copies of a stay that is one run go in as one run, so `9999999ix<Esc>` and `9999999ia<CR><Esc>` are a few inserts: in headless Chromium the first takes about 40 ms to the next frame on an empty note and on 120,000 lines, and a `9999999.` after `ia<CR><Esc>` 65 ms on both, where `x.` takes 34 ms (the two frames the measure waits). Played as 20,000 steps the first took 9.3 s in Node on 120,000 lines, because each step copies the lines array (0.46 ms). The copies of any other stay play step by step, and on a note of over 5,000 lines their bound is 100,000,000 over the line count (`maxReplayedLineCopies`), 833 on 120,000 lines: `9999999.` after `ia<BS>b<Esc>` takes 350 ms on an empty note (19,998 steps) and 133 ms on 120,000 lines (831 steps). A Delete waits one frame for the layout, so 120 take 2.0 s.
  - The first copy of a `.` has the same bound, counted in steps (`mostReplayed`), and a `.` whose stay plays more steps does nothing. With the record's 10,000 entries that bounds a `.` whatever was typed. In headless Chromium a `.` after a stay of 8,000 typed letters takes 36 ms to the next frame, and 7 to 8.6 s when the record was a list of inputs copied and checked on every key. In Node, typing the 10,000 keys of one stay costs the core 44 to 51 ms (34 to 47 on main), a letter typed after 100,000 keys of a stay about 6 µs (3.5 to 7 on main), and the `.` after it 0.8 to 1.5 ms. The slowest stay is one that never folds, such as `x` and Backspace in turn or IME commits, because each key copies the list of entries: at 10,000 entries a key costs the core 18 to 21 µs (3 on main), and in headless Chromium a `.` after 9,999 of them takes 231 ms on an empty note and after 800 of them 92 ms on 120,000 lines. A Backspace that folds, a Tab and longer text from one key read the run, which makes V8 flatten the string, where a letter only appends: `x` and Backspace in turn after 100,000 letters of one run cost 11 to 17 µs a key (6 on main), and after 1,000,000 letters 270 µs (22 on main).
- Accepted differences from `vim -u NONE -N`: `d` with Space or Backspace at a line edge acts as `dl` or `dh` (Vim crosses the line); a word object on an empty or blank line, in leading indent or reaching past a line end may differ (Vim moves the cursor when it fails); quote objects know no backslash escapes; counts on quote and bracket objects may differ; on a note that is one empty line, `d` and `c` keep the store as it was (Vim does this only when the buffer was emptied by a delete or never filled); a counted `b` under an operator that fails after stopping on an empty first line leaves the cursor where it was (Vim moves it to 1:1); `p` and `P` put at most as many copies as keep the added text within 50,000 UTF-16 units when the register is letters with no line feed, and otherwise within 4,000,000 units and 200,000 lines, and always one, where Vim builds any size and fails only on overflow (a bigger put crashed `String.repeat` or made a note too big to save; 4,000,000 units stays under the about 5,200,000 that Chrome's localStorage holds, so a reload still brings back a draft of a put on a small note; and the browser lays out one long line slowly: in headless Chromium a put that makes one line of 50,000 letters takes about 80 ms to the next frame and each key after it about 60 ms, where 1,000,000 letters take 1.2 s and then 1.5 s for every key); emoji, flags and accented letters are one letter each; no `o_v`, `gp` or `]p`, no `R` in NORMAL; arrows, Home, End and clicks in a stay do not split it, so `.` repeats all its typed text at one place (Vim repeats what was typed after the move); a paste and IME text in a stay are repeated; one `.` or counted insert is bounded as above, where Vim plays any count; after a stay that records more than 10,000 entries, and when its stay plays more steps than the note's bound, `.` does nothing, where Vim repeats a stay of any length; a stay ended by vim off or by opening another note is not what `.` repeats; no numbered registers (`"1` to `"9`), no small delete register (`"-`), no read-only registers (`".`, `":`, `"%`, `"/`) and no `q` macros, so those names drop the pending keys; `"+` and `"*` are one clipboard; a put from the clipboard waits for the browser, up to 3 seconds, and a refused one shows the notice where Vim puts nothing in silence; text read from the clipboard is whole lines exactly when it ends in a line break (the Vim we compare with has no clipboard to ask).
- `rest` runs on every outcome in Normal, from `done` in `editor.ts`: the caret is the start of a cell, never past the last cell of a line with text, never at the end of a wrapped row. So a click, a Page key, a paste and the toggle land on a letter without a rule of their own.
- Toggling is `Queued.ToggledVim`, queued with the inputs, so it waits behind a pending locate and every key before it is read with the old setting. It is not an `Input`, so the finder and the read view never see it. `update` takes Ctrl-, before it routes an input, so the chord toggles over the finder and the read view too, and the mode applies when the editor returns. `update` writes the setting whenever a message leaves vim on where it was off, or off where it was on. Ctrl-P and Ctrl-E are fed to the editor as well, in order, so they drop pending keys. A click drops them too.
- In Normal, typed text of one grapheme is a key, whatever key made it, so a dead key's `^` works. Longer text and IME text (`Preedit`, `Commit`, `Erase`) change nothing. Text the core swallowed is still in the EditContext, so `Editor.discards` counts it, the port carries it as `data-discards`, and `keyboard.ts` sets the EditContext's text again when it changes. Without that, an IME conversion in Insert erases letters counted from a text that holds the swallowed keys.
- The cursor is the block in Normal and with vim off, and a 2 px bar in Insert (`Frame.caret.shape`, carried as `data-caret-shape`). It does not blink. A space that hangs past a full row at a soft wrap draws one cell wide in the right padding of `.sheet`.
- `script()` names keys as Vim writes them, so `Editor.feed` over `script('3w')` or `script('ix<Esc>')` runs vim in Node, and the answers can be checked against `vim -u NONE -N -es` (`-N`, because Vi-compatible mode fails `9j` on a three-line note instead of going to the last line). Feed Vim the keys with `feedkeys(keys, 'xt')`: `:normal` drops every key after the first command that fails, where a person's later keys still run. A `"+p` in Node returns a `Need`, and `Editor.clipboardRead` with its ticket and the text, or `None`, lands it. Vim's `getreg` and `getregtype` give a register's text and kind to compare.
- A cell of an ASCII line is one UTF-16 unit and is never segmented. On a 120,000-line note `9999999w` takes about 0.5 s to the next frame in headless Chromium, a `j` about 2.3 ms when keys come back to back, and a `j` held at 30 Hz makes no long task. Segmenting every line made the first far jump take 3.9 s. On the same note `dG` from line 1 takes about 50 ms to the next frame, `p` of the 120,000 lines back about 100 ms, `1000dd` about 65 ms and `p` of 10,000 lines about 35 ms (a `gg` costs about 35 ms there), a `dd` about 8 ms when keys come back to back, and `d` held at 30 Hz makes no long task and lands 11 ms after the last repeat. Checking for an empty note by joining its text doubled the cost of a `dd`. `yy` then `9999999p` on a 100-letter line puts its 39,603 copies in about 80 ms, and on 120,000 lines of `line N é😀` with no brackets, `di(` from line 60,000 takes about 65 ms the first time and 35 ms after, where cutting every line it passed into cells took 1.5 s.
- A new key is a row in `normal` in `src/core/vim/keymap.ts`. A new motion is a case of `MotionName`, an entry in `motions`, its reach in `reachOf` in `targets.ts` (exclusive, inclusive or linewise) and a row in `motionRows`, which makes its operator rows too. A new text object is a case of `ObjectName`, an entry in `objects` in `objects.ts` with its `find` and `pick`, and a row in `objectRows`, which makes its operator rows and its VISUAL row. Every row carries `about`, which a which-key view will draw from `next`.
- A test may read `.status .mode` (`EDIT`, `NORMAL`, `INSERT`, `VISUAL`, `V-LINE` or `READ`), `.status .pending` (the count, register and keys waiting, such as `2g`, `d`, `2d3`, `ci` or `2"a3`, empty otherwise), `.status .notice` (absent when there is none), `.status .toggle-vim`, and the selection as drawn (see Visual mode).

### Visual mode

`v` in NORMAL selects letters and `V` whole lines. The mode reads `VISUAL` or `V-LINE`. There is no blockwise mode: Ctrl-V still pastes.

- `Mode.Visual` holds `kind` (`Letters` or `Lines`), `anchor`, the end that stays, and `column`. The cursor end is `buffer.caret`, so every path that moves the caret moves the selection. In VISUAL the caret may rest on the line break, the column that equals the line's length: `l`, Space and `$` reach it, and `v` on an empty line is on it. `rest` clamps only in Normal. The motions are one table built twice, `motionsOn('LastLetter')` for NORMAL and `motionsOn('LineBreak')` for VISUAL.
- `Keymap.visual` is VISUAL's table, a list of `Binding<VisualCommand>`. `advance` is generic over the command, so counts, the register prefix and the pending keys work as in NORMAL and `.status .pending` shows them. The rows:
  - every row of `motionRows` as `Move`, and every row of `objectRows` as `Pick`;
  - `o` (`Swap`), `v` and `V` (`Select`: the same kind leaves, the other kind switches and keeps both ends);
  - `d x` and Delete, `y`, `c s` (`Operate` on the selection), and `X D Y C S R` (`Operate` on its whole lines);
  - `p P` (`Replace`), `I A` (`Insert`);
  - Esc, Ctrl-[, Ctrl-C, Ctrl-E and Ctrl-P (`Leave`). Ctrl-E and Ctrl-P then open the read view and the finder. Ctrl-C leaves with the cursor where it is and copies nothing, as in Vim. Ctrl-X does nothing.
  - A key that takes an argument in Vim (`r`, `f`, `F`, `t`, `T`, `m`, `'`, a backtick, `@`, `q`, `z`, `[`, `]` and Ctrl-W) is an `Ignore` row that swallows the next key, so `rx` does not delete. Any other key matches no row and drops the pending keys with it: `J ~ u U > < = : /` do nothing and stay in VISUAL.
  - Esc with a count or a register name pending leaves VISUAL (`v2<Esc>`, `v"a<Esc>`). Esc after `i`, `a`, `g` or a lone `"` drops that key and stays, as in Vim.
- `selection.ts` says what a selection covers, and nothing in it knows a key. `endsOf` gives both ends as cells, `shown` what the screen draws, `rangeOf` the `Range` an operator takes. A selection builds its own `Range` and does not pass `rangeOf` in `targets.ts`, whose rules are for motions:
  - `Letters`: from the first end through the letter under the last end.
  - With the last end on the line break the range takes the line break too: it ends at the start of the next line, and at the line end on the last line.
  - `Lines`, and `X D Y C S R` in either kind: the whole lines from the first end's to the last end's.
- An operator returns to NORMAL, or to INSERT for a change, with Vim's cursor and registers. A count before an operator is ignored. `p` and `P` put the register's text in place of the selection (`putOverStep`): `p` leaves the replaced text in the unnamed register and `P` leaves the registers as they were. Whole lines over letters, and letters over whole lines, go on lines of their own. A count puts that many copies. `V"_p` puts one empty line for each count, and a put from any other empty register only deletes the selection, each as Vim does.
- A paste in VISUAL is our call, since Vim in a terminal has no paste key: it erases the selection as a change into no register, then pastes as INSERT's paste does, and lands in NORMAL. In V-LINE the text goes on a line of its own. It is one undo change, writes no register and leaves `dot`.
- `I` enters INSERT at the start of the anchor's line when the cursor end is past it, and at the cursor end otherwise. `A` enters INSERT after the cursor end's letter when the cursor end is past the start of the anchor's line, and after the anchor's letter otherwise. A count types the text that many times. The stay records `Command.InsertAsSelected`, so `.` inserts at the cursor or after it with the stay's own count, and a count before that `.` is ignored, as in Vim.
- `Pick` runs the object's `pick` on both ends and takes the ends and the kind it returns. A selection of one cell picks as NORMAL's object does. A longer one grows: a word object adds the next word, toward the cursor end; a paragraph object adds paragraphs; a quote object works within one line; a bracket object that would not grow takes the block around it. `ip` and `ap` make whole lines, the word, quote and bracket objects make letters, and an object that fails leaves the selection (a word object that fails moves the cursor end as Vim does).
- `.` after a VISUAL `d x X D`, `c s C S R` or a put repeats on the same amount of text from the cursor, as Vim does. `dot` holds `Command.OperateAmount` with the operator and a `Selection.Amount`, measured when the operator ran (`amountOf`): `Lines` (a count of whole lines), `Width` (on one line, screen columns, so a tab counts its columns and a wide letter two), `Through` (several lines: the count, and the screen column of the last letter) and `ToLineEnd` (the end was set by `$`). `rangeFrom` builds the range from the cursor and cuts it short where the note is short. The dot of a put only deletes that amount, as in Vim. A count before the `.` is ignored. A VISUAL `y` leaves `dot`.
- `gv` in NORMAL brings back `Vim.last`: the kind, a `Selection.Mark` for each end (the line's id, its number and a column) and the column `j` and `k` kept. A mark follows its line by id through later edits. An operator moves the marks itself to where Vim leaves them (`movedBy`): after a put they span the text put, and after a put of nothing both sit where the delete began. When the operator took out the line an end was on, the mark also keeps that end as it was (`removed`), and while that line is in the note again, as after `u`, `gv` selects from there (`broughtBack`): `ggVdugvd` deletes the first line again. Each end lands on the start of a cell (`marked`), so an edit that joined letters under a mark cannot leave an end inside a letter. A mark on a line past the end of the note never comes back, so `gv` then does nothing. `last` is dropped when the note is shown again from the store, and with vim off.
- The screen column `j` and `k` keep follows Vim's cursor column. `v` and `V` keep NORMAL's column. A cursor on a tab is in the tab's last column in NORMAL and, in VISUAL, in its first column while the cursor end is at or before the anchor. `column` says which holds: `AsInNormal` until the cursor end moves, since Vim works the column out when the cursor moves, and `AsInVisual` after. `o` on one cell, Esc, `y` and an object that fails read the column from it (`Selection.columnOf`). Esc and `y` then keep that column in NORMAL when the cursor did not move, and leaving with `v` or `V` keeps the column VISUAL had.
- A click, Ctrl-E, Ctrl-P, the vim toggle, opening another note and a change to the note from another tab leave VISUAL with nothing selected, and the editor comes back in NORMAL. IME text and longer typed text change nothing. Page Up and Page Down take the plain path and move the cursor end.
- Drawing. `Editor.paint` returns `Frame.selection` (`kind`, `from`, `to` and whether the last line break is in it), which costs the same for one letter and for 120,000 lines. `.surface` carries it as `data-selected`, and holds a `#selection` element with `data-kind` (`letters` or `lines`) only while there is a selection. After each patch `draw` in `src/surface.ts` reads the rects of the selected text on the drawn lines within one screen above and below the view, one `Range` for each line, then the caret's rect and the surface's scroll, and only then writes the boxes and the caret, so a key lays out twice in every mode (a write between the reads cost VISUAL two more layouts a key, and NORMAL one). The boxes are absolutely placed `div`s kept in a pool. Rects on one row join only where they touch (`joinedWhereTouching`), so in a line of mixed direction, where a selection is several runs on screen, no box covers a letter outside it, and a row holds at most a box for each run. A line whose selected letters all have no width, such as a ZWNJ, gets one box 2 px wide. A selected line break is a box one cell wide, marked `data-break`, so an empty line shows one cell. `lineBreakBox` places it: after the line's last letter, on that letter's row, and no further right than the view's edge, so the cell of an exactly full row is in the right padding and the cell after spaces that hang past a wrap stays in view. In VISUAL the caret on a line break takes the same box, so the cursor is a block on the highlight's cell. NORMAL, INSERT and vim off place the caret as before. A scroll of more than half a screen draws the boxes again. The cursor block is drawn over the boxes.
- Chrome snaps each box to CSS pixels and then scales, so at 125% and 175% two boxes that meet inside a device pixel each cover half of it and the page shows through. Each box carries a 2 px strip over its bottom edge, as wide as it shares with the boxes of the row below (`withSeams`, `--seam-left` and `--seam-width`), and a box of letters runs 1 px under the line-break box at its right. In forced colours the boxes are the system `Highlight` mixed with `Canvas`, since the letters over them keep the text colour, and `.line` takes `forced-color-adjust: preserve-parent-color`: Chrome otherwise paints a plate of the page colour behind forced-colour text, over a highlight drawn under the letters.
- A test may read `#selection` (present only while there is a selection), its `data-kind`, and the union of the client rects of its boxes. The fixture's `nullpad.selection()` returns the selected text as drawn: the letters whose centre a box covers, and `\n` for each line-break box, so every line of a `V` selection ends in `\n` and `v$` ends in one. A letter with no width is read as selected when a box holds its place, so one that touches the highlight from outside is read too. On the note's last line the highlight and `selection()` show a line-break cell that an operator does not take, since no line break is there (Vim draws that cell too). It reads only the lines drawn near the screen, and returns `''` when nothing is selected. An `expect` step of `e2e/steps.ts` takes it as `selection`.
- The comparison with Vim: `verify-out/vc/harness.py` generates about 13,800 rows for each seed from VISUAL keys mixed with motions, objects, operators, puts, registers, counts, `.`, `u`, Ctrl-R, `gv`, `o` and kind switches, over seven notes with tabs, wide letters, emoji, blank lines, brackets and quotes. It feeds Vim the keys one command at a time and has Vim work out the cursor's screen column between commands (a key mapped to `<Cmd>call wincol()<CR>`), as Vim does when it draws the screen for a person. Run with `-es` and no screen, Vim works the column out late, in whatever mode it is in by then, and a cursor on a tab reads another column. A row in which Vim reports an error is not counted, because Vim throws away the keys typed after it (E353, a put from an empty register). Of three seeds, 35,459 rows counted, about 320 a seed differ and each is one of the accepted differences below.
- Accepted differences from Vim in VISUAL:
  - A count before `v` or `V` is ignored, so `3v` is `v` (Vim selects the size of the last selection, three times).
  - `gv` in VISUAL does nothing (Vim swaps to the selection before).
  - `gv` after `u` or Ctrl-R brings back an end only when the selection's own operator took out its line and the line is in the note again. Vim keeps the marks with every undo step: an undo past an earlier selection's operator brings back that selection, its kind included, and an undo of a put inside one line brings back the ends from before the put, where ours selects where the marks are now. After a later command took out the line that held an end, `gv` keeps that end's line number (Vim moves the mark to the next line). After an operator on a line with letters outside ASCII the ends keep their letter columns (Vim keeps byte columns). After a `.` repeated a VISUAL `I` or `A`, Vim's `gv` selects whole lines, and ours keeps the kind.
  - `A` follows the rule above. Vim's answer differs when the cursor end is not past the start of the anchor's line, after `$`, over several lines with the cursor end in the first screen column, in the `.` after an `A` over several lines or after another operator, and after an earlier operator: there Vim reads a column that the earlier operator left, which looks like a Vim bug.
  - `.` after a `v` operator on one line whose end `$` set takes text to the line end. From the third screen column on, Vim adds the column to its largest number, which overflows, and takes other text.
  - `u`, `U`, `~`, `J`, `r`, `>`, `<`, `=`, `:` and `/` are not built in VISUAL. `u` and `U` change case there in Vim.
  - No `gn`, no `:'<,'>`, no `'<` and `'>` marks, no select mode, no selection by mouse drag.
  - A paste replaces the selection (Vim has no such key).
  - Ctrl-End keeps the line end as the column for `j` and `k`, in NORMAL too, where Vim keeps the last letter's column: Ctrl-End then `k` from `xyz` up to `abcdef` is on `f`, and on `c` in Vim. So Ctrl-End, an `l` that cannot move and then `k` goes to the line end.
  - What NORMAL already differs in holds here: `d` or `c` on a note that is one empty line, a `u` after a command that changed nothing, puts above the bounds, and emoji, flags and accented letters as one letter each.
- In Node the keys cost what they cost on main (microseconds a key, the least and the median of 21 samples, main then this build): one `x` after 10,000 held keys of an INSERT stay 3.62 and 4.66, then 3.27 and 4.69; after 100,000 held keys 2.92 and 4.58, then 3.12 and 4.26; `l` or `h` in NORMAL on 40 lines 4.92 and 5.91, then 4.58 and 5.69, and on 120,000 lines 5.34 and 7.02, then 5.03 and 6.24. In VISUAL `l` or `h` costs 4.16 and 5.15 on 40 lines and 4.13 and 5.37 with all of 120,000 lines selected, and `j` or `k` in V-LINE with 120,000 lines selected 4.57 and 5.64. No key copies or checks anything that grows with the selection.
- In headless Chromium on a 120,000-line note, `V` then `G` takes about 35 ms to the next frame and draws 104 boxes for the 52 lines near the screen at 1000x600, and 256 boxes at 2560x1440. `j` held at 30 Hz in V-LINE makes no long task at either size and lands 21 ms after the last key, and `k` held with all 120,000 lines selected lands in 5 to 11 ms. `vgg` from the last line, every letter selected, takes 50 to 100 ms, and the `d` after it 90 to 160 ms. On one line of 50,000 letters, `v$` takes about 40 ms and draws 53 boxes, one for each row within a screen of the view, and `h` held at 30 Hz with the 50,000 letters selected makes no long task.

## Undo

With vim off Ctrl-Z undoes and Ctrl-Shift-Z or Ctrl-Y redo (Cmd on a Mac). With vim on `u` undoes and Ctrl-R redoes in NORMAL, each with a count. Both read one history, `Editor.history`, so a change made in one mode undoes in the other.

- `src/core/history.ts` holds `past` (newest last), `future` (the next redo last), `base`, `open` and `units`. A `Change` is `at`, the Line records it `removed` and the ones it `added`, the cursor `before` the change and the caret `after` it. A change is found when its group closes: the lines between the longest shared prefix and suffix of `base` and the lines now, compared by identity, since every `Buffer` edit copies only the lines it touches. Undo puts the removed Line records back with `Buffer.spliceAll`, so ids, joins and the drawn rows' keys return, and undoing to the start gives the note exactly as it was opened. `nextLineId` never goes back.
- A change whose removed and added lines have the same texts and joins, such as a cancelled IME composition (its empty commit copies the caret's line), is not recorded and keeps the redo list. Only an INSERT stay is recorded even then, since Vim spends a `u` on `ixy<BS><BS><Esc>`.
- `base` is the lines the newest change left. When the lines differ from `base` and no group is open, some path changed the text without the history, and `record` makes that a change of its own, so a missed path costs a boundary, never a wrong splice.
- Every text change passes one choke point: `planOf` wraps each plan's outcome, and a layout answer's `land`, in `tracked`, and `overwrite` (the task box) calls `recorded`. An undo or redo changes the history itself, and the steps of a replay (`.`, a counted insert) each record themselves, so such a plan says `recordsItself` and `planOf` records nothing for it. `groupingOf` is the one table of boundaries, and each grouping names the kinds of open group it joins (`joinsOnto`) and whether its group stays open after it (`staysOpen`): an input in INSERT, or one that enters or leaves it, is `InsertStay` and joins the stay it is in; a step in NORMAL, a toggle and a click with vim off are `Command`, alone; with vim off a letter, a space or Tab is `Typing`, Enter is `Typing` that starts a new group, Backspace is `Backward`, Delete is `Forward`, `Erase` is `Replace`, which a following letter or composition joins, so an autocorrect's Erase and the text that replaces it are one change, `Preedit` is `Compose` and `Commit` closes the composition's group, and a paste is alone. A group continues only while each input joins its kind, so a move, a click, a change of kind, Enter and a paste end a typing change, with no time limit. A group opens at the first input that changes a line, so `i<Esc>` is no change and `o<Esc>` is one. One `.` and one counted insert are one change with no rule of their own: a replayed delete or put is a `Command`, and a replayed stay is an `InsertStay` that stays open through its copies until `Leave`.
- The cursor after `u` and Ctrl-R follows Vim's `u_undoredo`. Each change keeps where it began: for an operator `Vim.Step.began` (the range's start; for a one-line `dd`, `cc` or `S` the earlier of the cursor and the first non-blank; for a linewise change of several lines the line below the range's start), and otherwise the caret before the first changed line, so after `a` or `A` it is the caret after the placement. When that line is from the line above the changed lines to the line below them, the cursor goes there with that column, and otherwise to the first line whose text changed, at its first non-blank. Past the last line it is the last line's first non-blank. `rest` then clamps the column. With vim off, undo puts the caret where the change began and redo where it ended. The reveal is `Nearest`, so the cursor's line is on screen.
- The history keeps at most 1,000 changes (`maxChanges`, Vim's `undolevels`) and 64,000,000 units (`maxUnits`), a unit being one UTF-16 unit of a removed or added line plus 32 for each line. Past either bound the oldest changes drop. The newest change always stays, however large, so one `u` after `ggdG` brings back a note of any size. In headless Chromium a change of a fresh 120,000-line set costs about 1.03 bytes a unit (20 MB per `dG`, `P`, `Gdd` cycle on 120,000 lines of 49 letters), so the bound holds the history near 72 MB; 1,000 one-line changes cost 1.4 MB.
- `reopen` builds on `open`, so opening a note from the finder, coming back to one, another tab's change, a conflict copy and boot all start an empty history. A move from another tab keeps the text and the history. Undo and redo change `buffer.lines`, so the shell saves them as typing; a note that `ggdG` emptied and its save removed comes back with `u` and is saved anew.
- On a 120,000-line note in headless Chromium, `u` after `x` and after `dG` each take about 34 to 40 ms to the next frame (two frames), Ctrl-R of the `dG` 34 ms, Ctrl-Z after 200 typed letters 73 ms, and `x` or `u` held at 30 Hz makes no long task. `1000u` after 1,000 one-line changes takes 34 ms and `1000` Ctrl-R 38 ms (2.1 s and 1.3 s when each step copied the lines array): a counted undo or redo copies the lines once and splices each change into that copy. A typed letter costs the core 0.46 ms on that note before and after the history.
- Accepted differences from Vim: no `U`, no undo tree (`g-`, `g+`, `:undo N`) and no `Ctrl-G u`; arrows, Home, End, a click, a paste and IME text in INSERT stay in the stay's change (Vim splits at a move); Ctrl-Z, Ctrl-Shift-Z and Ctrl-Y do nothing in NORMAL and INSERT; a task-box click during an INSERT stay splits that stay's change; after `u` or Ctrl-R onto a line with letters outside ASCII the cursor keeps its letter column, where Vim keeps a byte column; a command that changes nothing, such as `x` on an empty line, `X` at a line start or `cc<Esc>` on an empty line, is no change, where Vim records an empty one that a `u` then spends; emoji and accented letters are one letter each.
- Feed Vim the keys of an undo row with `feedkeys(keys, 'xt')` and `--cmd 'set backspace=indent,eol,start'`. Keys read with `vim -s` merge undo steps (`xxx2u` undoes all three), and an empty `backspace` keeps INSERT's Backspace from deleting text typed before the stay.

## Markdown

The parser is written for nullpad, uses no library and follows CommonMark 0.31.2. It reads a note's lines and returns a tree in which every node knows its place in the note. The read view draws the tree. The default screen is the editor.

- `src/core/markdown.ts` is the whole public surface: `parse(lines)`, `toHtml(document)`, `outline(document)`, `positionOf(placed, point)` and the tree's types. The parts live under `src/core/markdown/`.
- A `Document` holds `lines`, `sections` and `definitions`. A section is one top-level block and the blank lines after it, so it holds whole lines. A place in a section is a `Point`: `lineInSection` and a UTF-16 `column`. `positionOf` is the one function that adds the section's first line. Every node has a half-open `span`. A paragraph or a heading keeps one slice per line.
- `parse` makes two passes. The block pass in `blocks.ts` folds over the lines with an immutable state and returns the sections. The inline pass in `inlines.ts` then reads each paragraph and heading: tokens, a delimiter stack for emphasis in `emphasis.ts`, and a bracket stack for links. A link reference definition is a block in the tree, and `toHtml` leaves it out.
- The parser has no `for`, no `while` and no `let`. A walk whose length follows the note is a fold or a regex, and no regex nests one quantifier in another. Recursion stops at `deepestNesting`, so parsing time grows in line with the note.
- `deepestNesting` is 100. It counts the levels of the tree: a block quote, a list and a list item are one level each, and so are emphasis, strong emphasis, a link and an image. A marker that would open level 101 stays text.
- `toHtml` writes the HTML of the spec's examples, character for character. nullpad draws that string as text and never puts it in the page as markup.
- `/?pane=html` and `/?pane=outline` draw `Editor.html` or `Editor.outline` as text in a `<pre class="pane">` under the editor. The `flags` Effect in `src/main.ts` reads the flag once at boot into the Model. The pane is there for tests. Without the flag the page has no pane, and the parser runs only when the read view opens.

### Outline

`outline` prints one row per node, in the order of the note. A line feed ends every row but the last.

```
<two spaces per level><tag> <line>:<column>-<line>:<column>[ <JSON string>]
```

```
Paragraph 3:0-4:12
  Text 3:0-3:4 "see "
  Emphasis 3:4-3:10
    Text 3:5-3:9 "this"
  SoftBreak 3:10-3:10
  Link 4:0-4:12 "/url"
    Text 4:1-4:5 "here"
```

- A top-level block has no indent. A child is one level under its parent.
- The tag is the node's `_tag`. A block is a `Paragraph`, `Heading`, `ThematicBreak`, `CodeBlock`, `HtmlBlock`, `Definition`, `Quote`, `List` or `Item`. An inline is a `Text`, `Escape`, `Entity`, `SoftBreak`, `HardBreak`, `Code`, `Emphasis`, `Strong`, `Link`, `Image`, `Autolink` or `Html`.
- The two places are the node's `span`, and the end is half open. The line is the note's line number as the gutter shows it, counted from 1. The column is a UTF-16 offset into that line, counted from 0.
- A `Text`, `Escape`, `Entity`, `Code`, `Html`, `Autolink`, `CodeBlock` or `HtmlBlock` shows its text as a JSON string. A `Link`, `Image` or `Definition` shows its destination. No other node shows a string.
- A JSON string holds no raw line feed, and the tag and the places hold no space. So the pane splits into rows at line feeds, and a row without its indent splits into tag, places and string at its first two spaces.

### Differences from commonmark.js

`commonmark@0.31.2` is the reference parser, a dev dependency that tests may call and `src` never imports. These are the known differences in the HTML.

- The nesting limit. commonmark.js nests without a limit. This is the one difference we chose.
- Emoji and other punctuation or symbols outside the Basic Multilingual Plane count as punctuation next to `*` and `_`, as sections 2.1 and 6.2 of the spec say. commonmark.js reads one UTF-16 unit there and takes them for letters.
- A paragraph and a heading lose only spaces and tabs at their ends, as sections 4.2 and 4.8 say. commonmark.js also takes off a form feed, a no-break space and other Unicode whitespace.
- `&#128;` to `&#159;` are the characters U+0080 to U+009F, as section 2.5 says. commonmark.js reads them as Windows-1252.
- A space written as `&#32;` before a line ending stays. commonmark.js drops it as it drops a typed space.
- The first definition of a label in the note wins, as section 4.7 says. In commonmark.js a later definition wins when it opens a paragraph that becomes a setext heading.
- A paragraph that holds only definitions and ends at a `---` line leaves no paragraph. commonmark.js leaves `<p></p>`.

## Testing

The only tests are end-to-end tests: Playwright Test drives the production build in headless Chromium with trusted input, the way a person types, clicks and scrolls. Write no unit tests and no Foldkit story or scene tests, and ignore the Testing section of `FOLDKIT.md`.

A test reads only the screen: the drawn rows (`[data-line-id]`, `[data-start]`, `[data-n]`, with `[data-ghost]` spans left out as not text), the drawn cursor `#caret`, the drawn selection (`#selection`, its `data-kind` and its boxes), the status line's `line:column NL`, its mode (`.status .mode`), pending vim keys (`.status .pending`), notice (`.status .notice`) and vim button (`.status .toggle-vim`), the text of the pane (`.pane`) on a page opened with `/?pane=html` or `/?pane=outline`, and pixels from a screenshot. It never reads app state or a window global. It sends input only through `page.keyboard`, `page.mouse` and CDP `Input.*` (paste, IME, raw key events). A test may listen for an event on `window` to see what the browser was left to do, such as whether a keydown was cancelled. A test may add an element outside the app, such as an `<input>` that takes the keyboard, to stand for the rest of a page. The system clipboard is outside the app too: a test may grant or deny the clipboard permission on its browser context (`allowClipboard`), and read or write the clipboard from a second page to see what another app would (`outside`). Headless Chromium shows no permission prompt and refuses at once, so a test that needs a read to stay open holds the page's `navigator.clipboard.readText` (`holdClipboardReads`), the one browser function a test replaces.

nullpad keeps notes across reloads, so a test that loads the page again in the same browser context does it with `openFresh(page)` from `e2e/nullpad.ts`. It leaves the page, then clears the notes database and the localStorage drafts the leaving page wrote, as a fresh browser profile would. A plain reload brings the last note back, unsaved text included.

A bug fix starts with a scenario that fails on the bug. Run it on the broken build, see it fail, fix the code, see it pass.

### Run

```sh
pnpm test:e2e                       # builds, then runs the push gate: scenarios, named scripts and the every-push sweeps
pnpm test:all                       # builds, then runs everything, on demand only
pnpm test:e2e -g "huge wheel"       # tests whose name matches
pnpm test:e2e --trace on            # keeps a trace of each test; open one with pnpm exec playwright show-trace
NULLPAD_DIST=/path/to/dist pnpm test:e2e   # tests a build made elsewhere, such as an old commit, without building
```

Without `NULLPAD_DIST`, Playwright builds the working tree into `dist/` first, so a run always tests the current source. Traces are off by default. Pass `--trace retain-on-failure` to keep them for failing tests only.

Playwright runs one and a half workers for each core (`workers: '150%'` in `playwright.config.ts`). A test spends much of its time waiting for frames, so one worker for each core left about a quarter of the CPU idle. With 8 workers on 4 cores the slowest scenario took 49 of its 60 seconds.

On a machine without Playwright's Chromium, install it once with `pnpm exec playwright install chromium`. Cloud sessions have it at `/opt/pw-browsers` already. The `@playwright/test` version in `package.json` must match that browser's revision.

### Add a scenario

Put it in the spec file of its feature, or a new `e2e/<feature>.spec.ts`. Import `test` and `expect` from `./nullpad` and take the `nullpad` fixture. The test name says what a person sees, and each assertion message names the step. Expected values come from what the feature promises, not from a run of the app.

```ts
test('Backspace at a line start joins it to the line above', async ({
  nullpad,
}) => {
  await nullpad.paste('ab\ncd')
  await nullpad.press('Home')
  await nullpad.press('Backspace')
  expect(await nullpad.text()).toBe('abcd')
  expect(await nullpad.status()).toEqual({ line: 1, column: 3, lineCount: 1 })
})
```

The fixture fails any test whose page logs an error or throws. A known bug that is not fixed yet gets a scenario marked `test.fail(true, 'known bug: ...')`. It passes while the bug stays and fails once the bug is gone, so whoever fixes it removes the mark.

### Robot typist

The typist types a script into nullpad and into a `<textarea>`, each in its own browser context, and compares the text, the cursor (line and grapheme column) and where each line breaks into rows after every step. The textarea is in nullpad's font and exactly as wide as nullpad's text column, so it wraps at the same edge. Rows are compared while nullpad's screen shows the whole text.

A script is a list of steps. A `text` step types one code point, or an ASCII run key by key. An `insert` step puts a whole string in at once, as an IME does. A `key` step presses Left, Right, Up, Down, Home, End, Ctrl+Home, Ctrl+End, Backspace, Delete or Enter. Page Up, Page Down and Tab are left out.

Backspace is judged against a bare EditContext element in a third browser context, not against the textarea. Before each Backspace the typist reads the textarea's own text nodes over the DevTools protocol, because Chrome keeps the halves of a joined line in separate nodes as nullpad keeps a join. The text node before the cursor goes into the EditContext, with the cursor moved to the next grapheme boundary, and the EditContext takes a real Backspace. The textarea takes its own Backspace too. Where the EditContext took more, the rest of that letter is deleted from the textarea as a selection, so the textarea holds the EditContext's result for the comparison and the steps after it. At a line start the textarea joins the lines itself.

Two kinds of script run. Named scripts run on every push. Sweeps run on demand, with `pnpm test:sweep` or `pnpm test:all`.

#### Named scripts

`namedScripts` in `e2e/typist/script.ts` holds every script that once broke, each as its shortest form. `pnpm test:typist` plays them.

#### Sweeps

A sweep covers one class of bugs with a grid of scripts. It plays the same scripts on every run, so a failing row fails again until the bug is fixed. `e2e/typist/sweeps.ts` holds the table and `e2e/sweep.spec.ts` plays it.

A sweep has a `name` that states its rule in plain words, `runs` that says whether it plays on every push or on demand, and these lists.

- `documents`. Each has a name and the steps that build it.
- `placements`. Each has a name, the steps that put the cursor in a document, and its `moves`. A move is a short script, such as one key and then `y`, so the text shows where the cursor stood.

A row is one document, one placement and one move. Its script is the document's steps, the placement's steps and the move, in that order. `scripts` holds the number of rows as a literal. A test fails when the grid has another size, so a grid that shrinks shows as a changed number in the diff.

A row types every step before its last placement step back to back, without comparing. It then compares after that step, where the placement left the cursor, and after each step of the move. A comparison at the end of the row alone would cost about as much: nullpad answers one layout key a frame, so the move's keys take their frames anyway, and a single wait after a burst of them reads a caret that has not landed yet. A row passes when nullpad and the textarea agree each time, or when an accepted difference covers the text. A failing row prints as `document | placement | move | differs after step N of M | nullpad L:C textarea L:C | text same: true`. A row that throws prints `threw:` and the error in place of the step. The rows go round-robin to `TYPIST_SHARDS` shards (8 by default), and each shard prints how many rows it checked, how many differ, and how many differences each accepted difference covered.

The sweeps today:

- Up or Down, any key, Up or Down lands where a textarea lands. Runs on demand. 6 documents (three short lines, a wrapped line of words, a long word that moved to the next row, one word longer than a row, a full row that ends in spaces, and rows of emoji and accents), 7 placements, and 52 moves in each: Up or Down, then any of 13 keys, then Up or Down. 2,184 rows, about 3 minutes on 4 cores.
- One Backspace, Delete, Left or Right takes what a textarea takes around emoji, flags and accents. Runs on demand, as two sweeps. The documents are twelve pieces (a letter, an accent, two flag letters, a thumbs up, a skin tone, a man, a ZWJ, a heart, a variation selector, a Devanagari letter and a virama) in every ordered pair, and seven fixed documents (two of Hangul, a keycap, a family of three, a family of four and a kiss with skin tones, which are letters of 11 and 15 UTF-16 units, and a flag split by an x). Each move is one key and then `y`.
  - Typed in order: 151 documents, 3 placements (at the end, at the start, one Right from the start). 906 rows.
  - Met at a line join, or typed one in front of the other: 302 documents, the same 3 placements and where the build left the cursor. 3,020 rows.

The second rule has 54 named scripts on every push. Add a row only for a shape the grid does not reach. When a bug turns up, run the sweep on the broken build first and see the new row fail.

1. If the bug fits a sweep's rule, add the document that shows it. If the bug needs a cursor spot or a key the grid lacks, add a placement or a move too. Set `scripts` to the new count.
2. If the bug breaks another rule, add a sweep to `sweeps` with its own name, documents, placements, `scripts` and `runs`.
3. Add the shortest failing script to `namedScripts`. The sweep finds the neighbors of the bug, and the named script keeps the bug itself.

`pnpm test:sweep` plays every sweep alone.


#### Accepted differences

Where a malformed sequence makes Chrome's textarea or EditContext disagree with `Intl.Segmenter`, nullpad follows `Intl.Segmenter`. A mismatch counts as accepted, not failed, only when the text before the step, the textarea's text after it, or the piece a Backspace was judged on holds one of these. A piece that starts at a line join can be malformed where the whole line is not, such as a ZWJ that starts one. nullpad's own text after the step does not count, so a bug that leaves a broken letter behind is not excused. They are listed in `acceptedDifferences` in `e2e/typist/script.ts`:

- ZWJ next to a non-pictograph.
- A mark, ZWJ or skin tone on a flag letter.
- A skin tone after a character that takes none.
- A virama with no letter before it.
- A variation selector not after a pictograph.
- A mark on a space.

Each sweep shard reports how many mismatches each accepted difference covered.

### The nullpad MCP server

`.mcp.json` registers `nullpad`, a stdio MCP server (`node e2e/mcp.ts`). It keeps one headless Chromium open on the build in `dist/`, so a key press answers in about 50 ms, where a `drive.ts` run spends several seconds on a build, a server and a browser first. It is not a test. Use it to explore, then replay its recording with `drive.ts` as the proof.

- **One driver.** The server plays each step with `play` from `e2e/steps.ts` and the fixture's driver, the code that `drive.ts` runs. `type`, `press`, `paste`, `compose`, `commit`, `click`, `wheel`, `resize` and `screenshot` each play one step, and `batch` plays a list. A new kind of step goes in `e2e/steps.ts`. It gets a row in `tools` in `e2e/mcp.ts` only if it needs a tool of its own.
- **Recording.** The server appends each step that plays to `verify-out/mcp-<time>-<pid>/<n>/steps.json`, and `checkpoint` appends an `expect` of the current screen. `node e2e/drive.ts <that file>` replays the recording on a fresh build. A recording belongs to one page. `reset` and a reload each start the next recording in the next numbered folder, so every recording starts from an empty editor. `reset` takes `steps_file` to write the recording elsewhere. A step that throws and an `expect` that fails are not recorded.
- **Reload.** Every `vite build` ends by writing `dist/build-stamp` (`scripts/build-stamp.ts`), the first 12 hex digits of the SHA-256 of the built `index.html`. Before each tool call the server compares that file with the stamp of the page it has open. If they differ, it opens a fresh page and starts its result with `reloaded:`. A `batch` is one call, so no reload lands inside it. While a build is being written, `dist/` has no stamp, and the server waits up to 10 seconds for one.
- **No build.** The server never builds. While a file under `src/` is newer than the stamp, each result ends with `stale:` and the fix, `pnpm build`.
- **Page errors.** A result that carries `PAGE ERROR` is marked as an error, because a `drive.ts` replay of that recording fails.
- **Another build.** `NULLPAD_DIST=/path/to/dist` serves that build, which needs its own `build-stamp`.

The `verify-nullpad` skill lists the tools and their arguments.

#### Grids against the reference

A grid has a `name` that states its rule in plain words, `rows` as a literal that the test checks, and `units`, the notes that are pasted. A test fails when the grid has another size, so a grid that shrinks shows as a changed number in the diff. `e2e/markdown/grids.ts` holds the table and `e2e/markdown-sweep.spec.ts` plays it.

A unit is one paste. Where a case cannot reach its neighbour, many cases share a note, each followed by a blank line, a sentinel block (`<!-- -->`) and a blank line. The note's HTML is compared with the reference's HTML for the same note, and both are cut at the sentinel's HTML into one piece per case. The first pieces that differ are printed with their source. A case joins a batch only when the reference shows it alone with the sentinel after it as its own HTML plus the sentinel's, so no case can open a comment or a list that swallows the next. A case that fails this test is pasted alone in the definition grid, and left out of the raw HTML, entity and link grids. Every stack of line shapes is pasted alone. A row passes when the pane shows the reference's HTML, or an accepted difference covers the case.

- Raw HTML parts: `<a`, `</a`, `<!--`, `-->`, `<?`, `?>`, `>`, `/>`, ` b`, `=`, `"x"`, `'x'`, `x`, `!` and `--`, one to three of them after `x `.
- Entities: every name of the entity table spelt seven ways (with and without the semicolon, with a letter after it, case flipped, in a link title and destination and in a code span), and 90 numeric references at the edges of their ranges, each alone, between letters and in a link title.
- Definition parts: one to three lines of `[a]: /u`, `[a]:`, a bare and a pointy destination, three kinds of title, two broken titles, a definition with a title, `[a]`, `a`, a blank line, and a definition indented by two spaces, by four and in a quote.
- Line shapes: `a`, a blank line, tabs at the start, after a space, after `-`, after `> ` and after `1.`, a quote, a bullet, an indent, `1.`, `0.` and `2.` items, `---`, `===` and a definition.
- Link parts: `[a](` or `![a](`, one of 9 destinations (none, bare, pointy, an unclosed pointy, empty pointy, with a space, with parentheses, with an escaped parenthesis), a gap of none, a space, a tab, a line end or both, one of 6 titles (none, three kinds of quote, an unclosed one, one followed by `x`) and a space, a line end or nothing before `)`, with and without a definition of `[a]`. A gap between the destination and a title is the case the grid is for: `[a](<b>"t")` is text.

`MARKDOWN_SHARDS` sets the number of parallel tests per grid (4 by default). Each shard prints how many rows it checked, how many differ, and how many differences each accepted difference covered. The grids take about 3.7 minutes on 4 cores, and with the slow inputs and the every-push tests the markdown files take 4.6 minutes. The every-push markdown tests alone take 33 s.

When a bug turns up, first ask whether a spec example, a place rule or a scenario catches it. Add the shortest note to the grid whose rule it breaks only when none can, and set `rows`.

#### Accepted differences from the reference

`acceptedDifferences` in `e2e/markdown/differences.ts` has an entry for each difference under "Differences from commonmark.js" that a grid can meet: the numeric references from U+0080 to U+009F (entities), and a definition repeated before a setext heading and a paragraph of only definitions that ends at a `---` line (line shapes). The nesting limit, a symbol outside the BMP beside `*` or `_`, Unicode whitespace at the end of a line and a `&#32;` before a line ending have no entry, because no grid has a note that shows them. An entry has a `covers(markdown)` that reads the note the case came from, never nullpad's output, and an `example` that the spec text decides. A test pastes each example, and the pane must show the spec's HTML where the reference shows something else. Another test checks that no entry covers an example of the spec, so an entry cannot grow wide unseen. A mismatch that no entry covers fails the row. A grid that can meet another difference gets its entry in the same diff.

#### Outline places

`e2e/markdown/places.ts` reads the outline pane by its documented format and checks each row against the note that was pasted. The notes are the 652 spec examples, grouped into notes of up to 40 that the reference shows do not run into each other (the rest alone). The rules:

- Every place lies in the note, and the start is not after the end. Only a `SoftBreak` is empty.
- A top-level node is a block, and each node sits under a parent that can hold it. A child lies inside its parent, and siblings are in order and do not overlap.
- Every character of a `Paragraph`, a `Heading`, an `Emphasis` or a `Strong` is under a child or is a marker, a space, a tab or a `>`.
- The first child of a `Paragraph` starts where it starts and the last ends where it ends. The children of `Emphasis` and `Strong` lie between their delimiters, and those of a `Link` or an `Image` after its opening bracket.
- The source under a `Text` is its text. An `Escape` is a backslash and one ASCII punctuation character. An `Entity` starts with `&`, ends with `;`, and its text is what the entity table decodes. A `Code` starts and ends with backtick runs of one length, and its text is its source less the runs and less one space at each end when both have one. A `SoftBreak` is empty or one space, and a `HardBreak` is a backslash or two or more spaces.
- `Emphasis` starts and ends with one `*` or `_` and `Strong` with two. A `Link` starts with `[`, an `Image` with `![`, both end with `)` or `]`. An `Autolink` and an `Html` start with `<` and end with `>`.
- A `Quote` starts with `>`. An ATX `Heading` (one line) starts with `#`, a setext one ends at its underline. A `ThematicBreak` is three or more of one of `- * _` and spaces. An `Item` starts with its marker, and the items of a `List` share a bullet or a delimiter. A `Definition` starts with `[`, and an `HtmlBlock` with `<` after up to three spaces that belong to it.
- Every line with text lies in a top-level block.

#### Scenarios with an exact value

`e2e/markdown-limits.spec.ts` holds the checks whose expected value is not in a reference. Each assertion message gives its derivation.

- A setext heading ends where its underline ends (section 4.3 lets spaces and tabs follow the underline), so `Foo` over `===   ` is `Heading 1:0-2:3`.
- The nesting limit is 100 levels, and a quote, a list and an item are one level each. A quote and 49 lists make 99 levels and the 50th list marker stays text. 50 lists alone make 100. 100 quote markers open 100 quotes and the 101st stays text.
- An autolink scheme is 2 to 32 characters (section 6.5), so 32 letters make a link and 33 stay text.

#### Slow inputs

`e2e/markdown/slow.ts` holds the generators: unclosed pointy destinations, unclosed comments, block quote markers on one line, many definitions, a run of `*` around a letter, backtick runs of growing length, a run of n backticks and then `a` and one backtick, a backtick and a letter n times, n openers `*a ` then n closers `b_ `, nested list markers and blank lines, nested brackets, unclosed brackets before links, alternating openers, unclosed attribute values, links opened inside destinations, entity-like runs, and a lazy line under deep quotes. Each is pasted at n and 4n, three times each on a page with the pane and on a page without it, from the paste to the status line showing the line count. The parser's share is the best time with the pane less the best time without. A test fails when the share at 4n is over 8 times the larger of the share at n and 200 ms, so the editor's own cost, which is large on one very long line, cancels and tiny shares cannot flake. An input that nests deeper than the limit has its growth judged only, and every other input must show the reference's HTML at both sizes, except one whose reference is itself quadratic at 4n. A quadratic parser that costs under about 0.2 s at n is not caught. n is 1,250 for the two inputs that the editor itself draws slowly (5,000 `>` on one line takes about 0.6 s, 5,000 `*` about 0.3 s, and 20,000 of either 2 to 7 s), 40,000 for the backtick and letter input, 2,500 for the opener and closer input and 5,000 for the rest. On this build the backtick and letter input shares 504 ms at 40,000 and 2,040 ms at 160,000, and the opener and closer input 94 ms at 2,500 and 305 ms at 10,000. A parser that is quadratic on them takes about 17 s at 160,000 backticks and 50 s at n=20,000 openers, which is over 8 times the share at n.

## Process

- Tests are end-to-end only. See Testing.
- Prove a change in the running app with the `verify-nullpad` skill (`node e2e/drive.ts`) before calling it done. The `nullpad` MCP server is for trying things out. Its recording is a proof once `drive.ts` replays it.
- Every PR passes the pre-push hook: quick checks and the push gate, about 3 minutes. Nothing else runs as a gate. `pnpm test:all` runs on demand, such as after a change to the area a sweep covers.
- A PR adds a test only when it fixes a real bug (one scenario that fails on the bug) or opens a kind of bug no test can catch. Most PRs add none.
- A PR that changes app behavior gets one break-it pass: an agent that did not write the change drives the app, about 10 minutes, and reports what broke. A PR that only changes tests or tooling skips it.
- A PR that changes app behavior gets a recording: its proof with `caption` steps, replayed by `node e2e/drive.ts <steps.json> --record`. The break-it pass, the recording and the no-comments pass do not wait for each other.
- No planted-bug runs, random scouts or nightly runs.
- Few comments. Name things better instead. Keep a comment only for a fact we cannot change, such as a browser rule. Skip the `// MODEL` section headers that `FOLDKIT.md` suggests.
- Before a PR is ready, a no-comments pass (`/pstack:no-comments`) runs on its diff.
